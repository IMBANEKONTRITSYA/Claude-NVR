## Что доведено до end-to-end

### 1. Хранилище архива — [#74](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/74)

Четыре требования §5/§21, которых не было в коде. Ротация умела ровно
одно — общий срок на весь архив.

**Глубина хранения по камерам.** `cameras.retention_days` nullable, и NULL
значит «следовать за глобальной настройкой», а не «ноль дней»: камера без
своего срока должна продолжать следовать за глобальным и **после его
изменения**, чего копия значения в момент создания камеры не дала бы.

Тонкость, которую легко сделать неправильно: отбор кандидатов в
`cleanup_old()` идёт по **минимальному** из действующих сроков. По
глобальному камера с более коротким сроком не попадала бы в выборку вовсе,
и её сегменты не удалялись бы никогда — сколько бы раз ротация ни шла.
Сторож на это написан отдельно.

**Прогноз** считается по фактическому расходу за последние сутки, а не по
номиналу `Mbps × 10.8`: SPEC §21 сам называет номинал завышенным
(«фактически ~1.6–2 ТБ/сутки» против 2.6 ТБ на 120 камерах), и прогноз по
нему занижал бы срок примерно в полтора раза. Источник факта — новая
колонка `video_segments.size_bytes`. Номинал остаётся в ответе рядом — для
калибровки, которую §21 и требует.

**Циклическая перезапись** независима и от retention, и от порогов алертов.
Она аварийная: срабатывает, когда расчёт не сошёлся с фактическим
битрейтом, и не даёт записи встать целиком. Идёт по всему архиву по
времени, а не по камерам, — решение «чьей записью жертвовать»
администратор уже выразил через retention. Связать её с порогом алерта
значило бы, что понижение порога молча отключает перезапись.

Проверка заполнения — каждые ~10 с, а не раз в час вместе с ротацией:
между часовыми проходами 120 камер успевают записать ~108 ГБ. На здоровом
диске это два `statvfs` и ни одного запроса к БД.

**Интерфейс:** карточка «Хранилище архива» и калькулятор в «Мониторинге»,
поле глубины в карточке камеры, пороги в «Настройках».

### 2. Мониторинг слоя записи — [#75](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/75)

`MediaMTXClient.runtime_paths()` был написан циклом 24 и **ни разу не
вызван**: SPEC §14 требует «статус каждого RTSP-потока слоя записи
(120 шт.)», и данные для этого лежали ровно в одном неиспользованном методе.

Воркер собирает состояние каждый проход и кладёт в Redis (`record:layer`,
TTL 120 с). Бэкенд к Control API не ходит намеренно — доступ к нему равен
доступу к RTSP-адресам всех камер с учётными данными (решение цикла 24).
TTL нужен, чтобы при остановленном воркере интерфейс показал «данных нет»,
а не застывшую картину.

Три решения о поведении:

* **недоступный Control API — `unknown`, а не «120 потоков потеряно»**:
  показать 120 аварий вместо «состояние неизвестно» значило бы
  спровоцировать реакцию на аварию, которой нет;
* **алерт на ПЕРЕХОД `online → offline`**, а не на факт «сейчас offline»:
  иначе выключенная камера слала бы алерт каждые десять секунд, и
  алертинг перестали бы читать. Переход из `unknown` потерей не считается
  — рестарт MediaMTX иначе давал бы пачку из 120 ложных алертов;
* **пропуск сегмента — отдельный алерт и только для онлайн-потоков**:
  поток может быть жив, а файлы не расти (нет места, прав, сбой записи), и
  это другая авария, которую §14 называет отдельной строкой.

**Интерфейс:** карточка «Слой записи» — сводка, таблица потоков с фильтром
«проблемные / все» (на 120 камерах список целиком нечитаем), баннер о
пропуске сегментов.

## PERFORMANCE PASS (обязательная секция)

`perf/bench.py` — новый, раньше бенчмарков в проекте не было вовсе. В CI
добавлена джоба `perf`, складывающая результат в артефакт.

**Измерено в песочнице** — 4 ядра, Intel Xeon @2.80GHz, **AVX2 есть**.
Бенчмарк печатает флаг AVX2 отдельной строкой именно затем, чтобы числа с
такого хоста нельзя было принять за числа целевого E5-2670, у которого
AVX2 нет.

| Горячий путь | Результат | Вывод |
|---|---|---|
| Декод 720p H.265, OpenCV `VideoCapture` | **296.7 FPS** | **быстрейший — оставлен** |
| Декод, ffmpeg → пайп (raw BGR) | 225.6 FPS | медленнее на 24% |
| Декод, ffmpeg → пайп с ресайзом до 640 | 251.1 FPS | медленнее на 15% |
| Префильтр MOG2 | **3.52 мс/кадр** (потолок 284 FPS) | **дефолт подтверждён** |
| Префильтр KNN | 4.46 мс/кадр (потолок 224 FPS) | на 27% дороже |
| Инференс, ONNX Runtime CPU, 1 поток | 0.91 мс/лицо (p95 1.04) | синтетическая сеть |

**Что это значит для цикла.** Задание требует «измерь альтернативы
декодирования и оставь быструю». Быстрая уже стоит: `cv2.VideoCapture`
обгоняет обе альтернативы через пайп, и переписывать декодирование (в том
числе на GStreamer или на Rust-демон с shared memory, что задание
разрешает) **оснований нет** — узкого места в декоде на этих числах не
видно. То же с MOG2 против KNN: текущий дефолт оказался и быстрее.

Это результат, а не его отсутствие: цикл не сделал перф-изменений, потому
что измерение показало, что делать нечего, — а не потому, что не измерял.

**База для сравнения — числа с раннера CI**, а не из песочницы: сравнивать
циклы имеет смысл только на одинаковом железе, а песочница от сессии к
сессии разная. Прогон джобы `perf` на `AMD EPYC 9V74` (4 ядра, AVX2 есть):

| Метрика | Значение на раннере CI (цикл 25) |
|---|---|
| `decode.opencv_videocapture.fps` | **404.6** |
| `decode.ffmpeg_pipe.fps` | 324.5 |
| `decode.ffmpeg_pipe_scaled_640.fps` | 336.3 |
| `prefilter.MOG2.ms_per_frame` | **3.53** |
| `prefilter.KNN.ms_per_frame` | 5.36 |
| `inference.ms_per_face_mean` | **1.09** (p95 1.11) |

Со следующего цикла деградация > 15% против этой таблицы = carryover P2.
Артефакт `perf-results` прикладывается к каждому прогону.

**Порядок величин совпал на двух разных CPU** (Xeon песочницы и EPYC
раннера): OpenCV быстрее обоих ffmpeg-вариантов, MOG2 дешевле KNN. Вывод
«менять нечего» опирается на два независимых замера, а не на один.

Джоба `perf` намеренно `continue-on-error` и не гейтит мердж: раннер
мощнее целевого сервера, и порог, взятый с него, на целевом железе не
значил бы ничего.

**Чего эти числа НЕ говорят** (см. known gaps): реальный decode на
целевом CPU без AVX2; ms/лицо для настоящей `buffalo_s`; задержку live;
поведение под 120 потоками записи одновременно.

## Дефекты, найденные по дороге

**1. `SUM()` по `bigint` роняет прогноз (#74).** Postgres возвращает
`numeric`, драйвер отдаёт `decimal.Decimal`, и деление на float падало с
`TypeError` — на первом же сегменте с ненулевым размером. Найдено
интеграционным тестом на настоящей БД; мок на `func.sum` этого не показал
бы. Приведение к `int` на границе запроса.

**2. `ended_at.timestamp()` на naive-UTC (#75).** Трактует значение как
локальное время хоста. На непустой `TZ` (обычное дело — логи в местном
времени) проверка «сегмент не пишется дольше N минут» уехала бы ровно на
смещение пояса: восточнее UTC молчала бы всегда, западнее — алертила бы
всегда. Тот же класс, ради которого существует `fileage.py`. Поймано при
написании, до первого прогона.

**3. `Metric` терял пропсы `warn`/`crit` (#75).** Полоса заполнения диска
красилась по умолчаниям компонента (75/90) вместо настроенных порогов, то
есть меняла цвет не на том значении, на котором приходит алерт.

## Carryover на цикл 26

**Функциональное (приоритет по §30):**

1. **§5 «экспорт фрагментов»** — единственный незакрытый гэп §3-13. Сейчас
   архив отдаёт сегмент целиком (`/api/archive/file/{id}`); ТЗ требует
   экспорт **фрагмента** по границам времени, в том числе поверх нескольких
   сегментов. Делается remux'ом (`ffmpeg -ss -to -c copy`) — перекодирование
   §24 запрещает. Самый дешёвый оставшийся гэп, стоит брать первым.
2. **§4 задержка live и §12 поиск на 100k** — обе функции есть в коде и в
   интерфейсе, но **числовое требование ТЗ ни разу не измерено**. Поиск
   измерим прямо в песочнице: засеять 100k эмбеддингов и замерить с HNSW и
   без. Это ближе всего к «функция проходит тесты, но не проверена в
   реальности» из задания.
3. **§19/§29.10 профили производительности** — описаны в терминах
   N100–Ryzen 9 и применяются к обоим слоям; по ТЗ относятся **только к
   слою аналитики**, пороги надо пересчитать под целевой сервер. Теперь
   есть чем: `perf/bench.py` даёт числа, от которых считать.
4. **§23 NUMA-привязка** — `numactl --cpunodebind/--membind`, камеры 1–60
   на node 0, 61–120 на node 1. Написать и задокументировать можно, проверить
   — только на сервере.
5. **Мультипроцессность камер-воркеров** (задание, п. 1 секции
   производительности): сейчас камеры — нити в одном процессе, GIL общий.

## Методологические заметки

### Сработало

**Начать с вопроса «что из §3-13 не работает», а не «где уязвимость».**
Оба PR цикла — прямое следствие. Проход по чек-листу функций против кода
**и интерфейса** занял минут двадцать и дал шесть гэпов; предыдущие циклы,
идя от аудита, находили по одному-два дефекта в уже работающем коде.

**Искать написанный, но не вызванный код.** `runtime_paths()` — метод,
написанный циклом 24 «на будущее» и не подключённый ни к чему.
`grep -rn "runtime_paths"` дал одно попадание — определение. Это дешёвый
способ найти незаконченную функцию: приём стоит повторять
(`grep` определения против вызовов) в каждом цикле.

**Сверять поля стороннего API с апстримом, а не с предыдущим отчётом.**
Отчёт цикла 24 называл `readyTime`; в `openapi.yaml` MediaMTX v1.20.0 это
поле **deprecated**, актуальное — `onlineTime`. Отчёт был написан
добросовестно, но за два цикла успел устареть. Проверка — один `curl` к
`raw.githubusercontent.com`.

**Интеграционный тест на настоящей БД вместо мока.** `Decimal` из `SUM()`
— ровно тот дефект, который мок пропускает по определению: мок вернул бы
`int`, потому что его писал тот же человек, что и код.

### Не сработало / стоило дороже

**Первая версия теста ротации сносила бы схему бэкенда.** Модели воркера
носят те же имена таблиц (`cameras`, `video_segments`), и `create/drop` на
общей БД — тот же класс кросс-сервисного загрязнения, на котором цикл 21
потерял прогон. Поймано попыткой прогнать тест против настоящего Postgres:
на SQLite он проходил. **Урок:** тест воркера, который создаёт таблицы,
обязан прогоняться против той же БД, что и бэкенд, — иначе он выглядит
безобидным ровно до первого запуска в общей среде. Изоляция — отдельная
схема Postgres с `search_path`.

**Асинхронный `get_redis()` в тестах.** Клиент один на процесс и привязан
к циклу событий, в котором создан, а `TestClient` крутит свой на каждый
запрос — попытка писать им из теста даёт «Future attached to a different
loop». Правильный способ — синхронный клиент, как `pg_conn` для Postgres.
Стоило одной итерации.

**`pytest` из окружения uv не видит `site-packages`.** В песочнице
`which pytest` указывает на инструмент uv со своим venv, и прогон падал с
`ModuleNotFoundError: pydantic_settings` на здоровом дереве — то есть
выглядел как поломка кода. Запускать надо `python -m pytest`. Стоило
трёх ложных прогонов в начале цикла; **стоит записать как первый шаг
setup'а любого будущего цикла.**

**Гейт перезаписи по уровню алерта.** Первая версия вызывала
`enforce_disk_quota()` только при `critical`, связав два независимых
порога. Понижение порога алерта тогда молча отключало бы перезапись.
Разнесено; в коде оставлен комментарий, почему связывать нельзя.

## Sandbox limitations

Postgres 16 + pgvector, Redis, nginx, ffmpeg, OpenCV, ONNX Runtime — всё
через `apt`/`pip` без демона Docker. Полные сьюты бэкенда, воркера и
апскейла прогнаны на настоящих сервисах.

Впервые за все циклы **воркер прогнан без единого пропуска**: установка
`opencv-python-headless`/`numpy`/`scikit-learn` и настоящий `DATABASE_URL`
сняли 8 graceful-скипов (`254 passed` вместо `223 passed, 8 skipped`).
Стоит делать так каждый цикл — скипы прятали, в частности, все тесты
`camera_worker()`.

Docker и GPU по-прежнему недоступны; GPU для базовой конфигурации по §23
**не требуется**.
