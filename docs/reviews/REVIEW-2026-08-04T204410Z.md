## P0 — XML-инъекция username в ONVIF WS-Security заголовке (PR #33)

`worker/onvif_client.py::_username_token_header()` подставлял `username`
(вводится администратором в форме камеры — `CameraIn.onvif_username` /
`OnvifProfilesRequest.username`) прямо в XML без экранирования:

```python
f"<Username>{username}</Username>"
```

Значение вида `"><Injected/>` разваливает структуру заголовка
`UsernameToken` и позволяет внедрить произвольные SOAP-элементы в запрос,
уходящий к ONVIF-камере. Непоследовательность с остальным модулем:
`profile_token` в `get_stream_uri()` уже экранировался через
`xml.sax.saxutils.escape` (данные с сети, пусть и локальной) — `username`
проходит тот же путь подстановки в XML-тело, но не был защищён тем же
образом. `password` не нуждается в экранировании: участвует только в
вычислении SHA1-дайджеста, не подставляется в XML напрямую.

**Фикс:** та же функция `_xml_escape`, что уже импортирована в модуле,
применена к `username`. Тест
`test_username_token_escapes_username_from_camera_form` — тот же паттерн,
что существующий `test_get_stream_uri_escapes_profile_token_from_camera`.

## P0 — отсутствие Content-Security-Policy (PR #34)

`nginx-locations.conf` уже задавал `X-Frame-Options` /
`X-Content-Type-Options` / `Referrer-Policy` / HSTS (ТЗ 13, циклы 1-6), но
не CSP — прямое требование ТЗ ("OWASP Top 10: защита от XSS") оставалось
частично не закрытым на уровне самого прямого браузерного барьера против
XSS.

**Фикс:** CSP-заголовок в общем location-snippet (применяется к HTTP и
HTTPS listener). Фронтенд не использует ни одного внешнего хоста (весь
JS/CSS собран Vite в свой бандл, без CDN) — `default-src 'self'` не
требует исключений.

**Как проверялось (не просто дописан на глаз):** собран production-бандл
(`npm run build`) и прогнан через headless Chromium (Playwright,
предустановленный в окружении) со статическим сервером, отдающим тот же
CSP-заголовок, что nginx будет отдавать в проде.

- Страница логина рендерится без единого CSP-нарушения в консоли —
  `script-src 'self'` не блокирует собственный бандл, `style-src 'self'
  'unsafe-inline'` не блокирует inline-стили React (bbox-рамки на
  LiveGrid, цвета Recharts).
- **`worker-src 'self' blob:` — найдено эмпирически, не по интуиции.**
  `LiveGrid.tsx` использует `hls.js` с дефолтным `enableWorker: true`,
  который создаёт demuxer-воркер через `URL.createObjectURL(new
  Blob(...))`. Первая версия CSP без `worker-src` была протестирована
  через фейковый `.m3u8`+`.ts` на статическом сервере — браузер
  заблокировал создание воркера с точным сообщением:
  `Refused to create a worker from 'blob:...' because it violates ...
  "script-src 'self'". Note that 'worker-src' was not explicitly set, so
  'script-src' is used as a fallback.` Без этой директивы **видео на
  LiveGrid не воспроизводилось бы вообще**, независимо от того, насколько
  правильно настроен сам HLS-поток — тихий регресс, который не поймать
  без реального браузера. С добавленной директивой тот же тест доходит до
  реального разбора сегмента (ошибка "found no media" — ожидаемо для
  фейкового бинарного мусора вместо настоящего TS, не для CSP).

**Тест:** `test_nginx_hardening.py::test_csp_header_present_and_permits_hls_worker`
— статическая проверка текста конфига, тот же паттерн, что и для
остальных заголовков в этом файле (реальный nginx не поднимается в
юнит-тестах, слишком тяжело — см. docstring файла).

## P1 — self-lockout и удаление последнего администратора (PR #32)

`DELETE /api/users/{user_id}` безусловно удалял любого пользователя,
включая самого вызывающего admin'а и последнего оставшегося админа
вообще. После такого удаления управление пользователями/камерами/
настройками становится недоступно никому до перезапуска backend —
`main.py:lifespan` досеивает `admin` только если такого username вообще
не существует, а не по фактическому количеству администраторов, так что
переименованный/другой-по-имени последний админ не восстановился бы
автоматически.

**Фикс:** две проверки в `delete_user()` — запрет удаления собственной
учётной записи (реалистичный путь к нулю админов через этот эндпоинт,
поскольку сам эндпоинт требует роль `admin`) и подсчёт по роли как
defense-in-depth (математически недостижим через этот же эндпоинт при
работающем self-check, но фиксирует инвариант на случай будущих изменений
— задокументировано в комментарии кода, чтобы не выглядело мёртвым
кодом без объяснения).

**Тесты:** новый `test_integration_users.py` — self-lockout блокируется
для сидового admin'а, проверка не срабатывает ложно при двух админах,
403 для оператора, 404 для несуществующего пользователя, успешное
удаление обычного пользователя.

## Аудит без находок (проверено целевым пересмотром, не переоткрывать без новых изменений кода)

Полный проход по RBAC каждого защищённого эндпоинта во всех роутерах
(`cameras`, `persons`, `archive`, `search`, `reports`, `audit`, `settings`,
`system`, `users`, `ws`, `stats`, `events`) — включая новые с цикла 8
(`onvif/discover`, `onvif/profiles`, `onvif/stream-uri`) и новые
конфиг-поля циклов 9-11 (`record_bitrate`, `record_iframe_only`,
`FACEWATCH_HW_DECODE`):

- RBAC-матрица соблюдена везде, включая "ссылочные" эндпоинты с токеном в
  query (`archive/file`, `reports/*`, `audit/export.*`,
  `system/prometheus`) — у каждого свой `_check_token`/`jwt.decode` с
  проверкой роли.
- SQL — везде параметризованные запросы (ORM или `text()` с bind-параметрами
  через словарь `params`), включая `search.py` (вектор pgvector строится
  из `embedding: list[float]`, передаётся как bind-параметр, не
  интерполяцией строки).
- `worker/onvif_api.py` — внутренний HTTP API воркера (порт 9000) без
  собственной аутентификации, но не публикуется наружу
  (`docker-compose.yml`: у сервиса `worker` нет секции `ports`) — тот же
  контракт, что у `/embed`, уже принятый в предыдущих циклах.
- Bcrypt, JWT с коротким access TTL + ротацией refresh с детекцией
  повторного использования (кража токена → отзыв всех сессий), brute-force
  лимиты на `/login` и `/change-password` (Redis, по IP+логину и по
  user.id соответственно) + отдельный `limit_req` на уровне nginx —
  всё на месте, без изменений с циклов 6-7.
- RTSP/ONVIF-URL валидируются схемой (`rtsp(s)://` с обязательным хостом)
  на уровне Pydantic-схемы (`_check_rtsp_scheme`) — покрывает и
  `/api/cameras/test` (ffprobe запускается через `subprocess_exec` с
  списком аргументов, не через shell — инъекция команд ОС через это поле
  невозможна).
- Аудит-лог: нет ни одного DELETE-эндпоинта или иного пути удаления строк
  `AuditLog` в кодовой базе (`grep` по всем `.py`) — "защищён от удаления"
  соблюдено отсутствием возможности, а не отдельной проверкой.
- `npm audit` (frontend): 2 предупреждения (esbuild dev-server CSRF — не
  применимо, продовая сборка не запускает dev-сервер; react-router RSC
  Mode CSRF bypass — не применимо, приложение использует классический
  `BrowserRouter`, RSC-режим не подключён). Оценено и сознательно не
  тронуто в эту сессию — оба фикса `npm audit fix --force` помечены как
  breaking change, автономный breaking-change бамп зависимостей без
  возможности полного regression-теста фронтенда — риск, который не
  оправдан для неприменимых в данном приложении CVE. См. рекомендации.
