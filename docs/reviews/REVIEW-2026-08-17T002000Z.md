## 3. Что доведено до end-to-end

### 3.1 §11 SMTP + §6 почта и звук — [#90](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/90)

`grep -i smtp` по дереву давал **ноль совпадений**, при том что почту
требуют три раздела сразу: §6 (алерты), §8 (авто-отправка отчётов), §11
(настройки уведомлений). Из трёх каналов §6 работал один — Telegram.

Транспорт `mailer` — только stdlib, копия в воркере сверяется с
оригиналом по AST (`test_mailer_parity.py`): у воркера нет зависимости от
пакета `app`, а расхождение копий — класс регрессии, который в проекте
уже случался с ORM-моделями.

Решения, за которыми поведение:

1. **Кулдаун снимается один раз на событие и общий для каналов.** Наивная
   реализация «каждый канал берёт свой `SET nx=True`» выглядит правильной
   и молча ломает почту при включённом Telegram: первый канал забирает
   ключ, второй видит занятый и выходит. Проявилось бы только на объекте
   с двумя включёнными каналами.
2. **Каналы независимы** — один неверный пароль не выключает оповещения
   целиком.
3. **Пароль SMTP шифруется** наравне с токеном бота (§14).
4. **Звук — WebAudio без файла**: строгий CSP nginx и §24 о лицензиях.
   Тротлинг 5 с общий по вкладке, потому что кулдаун воркера считается
   **по персоне**: пять watchlist-персон в секунду — пять законных
   алертов и пять накладывающихся гудков.
5. **`GET /api/settings/client`** — белый список несекретных настроек для
   любой роли. Пересечение списка с секретами роняет импорт модуля.

### 3.2 §19 детекция — [#91](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/91)

### 3.3 §8 шаблоны и расписание — [#92](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/92)

Шаблон и расписание — одна сущность: шаблон без расписания это
сохранённый набор параметров с кнопкой «Отправить», расписание без
шаблона бессмысленно.

Планировщик написан руками, без брокера (§26 требует пакет из четырёх
юнитов, а не из пяти). Два свойства ломаются беззвучно и потому вынесены
в чистые функции с тестами на фиксированных датах:

* **ровно один раз**: перезапуск в 08:00:30 не шлёт повторно, вторая
  реплика (§17) не шлёт параллельно — строки берутся `FOR UPDATE`;
* **ни одного пропуска**: простой с 07:50 до 08:10 не теряет отчёт, при
  этом неделя простоя даёт **одно** письмо, а не семь (слот считается
  назад от `now`, а не проходом вперёд от `last_sent_at`).

Края, каждый закрыт тестом: отказ отправки не закрывает слот (иначе одна
сетевая ошибка отменяла бы отчёт до следующих суток) и показывает причину
в карточке; кнопка «Отправить» не трогает `last_sent_at`; правка шаблона
открывает слот заново; число месяца ограничено 28 (расписание «31-го»
молча не срабатывало бы в феврале).

Попутно шесть почти одинаковых обработчиков выгрузки свелись к одному, с
сохранением путей буква в букву — общий код здесь ради гарантии, что
пришедший на почту отчёт **совпадает** со скачанным вручную.

## 4. Производительность

### 4.1 Находка цикла: три лишние модели на каждом лице

`FaceAnalysis` создавался без `allowed_modules`, поэтому insightface
поднимал **пять** моделей и прогонял четыре из них на каждое лицо
каждого кадра: `detection`, `landmark_3d_68`, `landmark_2d_106`,
`genderage`, `recognition`. Воркер читает из результата ровно два поля —
`bbox` и `normed_embedding`. Возраст, пол и лицевые точки не используются
нигде: ни в событиях, ни в поиске, ни в кластеризации, ни в апскейле.

Замер: `buffalo_s`, `det_size` 640, один поток, клип 720p H.265 с шестью
лицами в кадре.

| | до | после | |
|---|---|---|---|
| детектор + эмбеддинг | 697.9 мс/кадр | **106.8 мс/кадр** | 6.5× |
| цепочка целиком | 1.39 FPS/канал | **8.39 FPS/канал** | 6.0× |

Набор результатов идентичен: шесть лиц найдено и до, и после.

**Почему не нашли раньше.** Прежний бенчмарк мерил шаги по отдельности и
инференс — на синтетической сети. Она показывала 0.9 мс/лицо до правки и
показывает столько же после: меряется одна модель, а проблема была в
четырёх лишних. Находка видна только замером всей цепочки.

**Регрессия невидима без теста:** без `allowed_modules` система остаётся
полностью корректной и просто становится в шесть раз медленнее. Сторожит
`worker/tests/test_face_modules.py` (статический, идёт в лёгкой CI-джобе
без cv2); третий тест там же ловит обратную сторону — чтение
`.age`/`.sex`/`landmark_*` даст невычисленные значения.

считается на каждое лицо, поэтому на объекте смотреть надо самую людную
камеру, а не среднюю.

### 4.3 Горячие пути: сравнение с циклом 28

| Метрика | Цикл 28 | Цикл 29 | Дельта |
|---|---|---|---|
| decode OpenCV VideoCapture | 376.6 FPS | 328–367 FPS | −3…−13 % |
| decode ffmpeg pipe | 340.7 FPS | 252–269 FPS | −21…−26 % |
| decode ffmpeg + scale 640 | 294.1 FPS | 267.1 FPS | −9 % |
| префильтр MOG2 | 2.369 мс/кадр | 3.22–3.29 мс/кадр | +36…+39 % |
| префильтр KNN | 3.591 мс/кадр | 4.533 мс/кадр | +26 % |
| инференс (синтетическая сеть) | 0.75 мс/лицо | 0.89–0.92 мс/лицо | +19…+23 % |

Формально это деградация больше 15 % по трём метрикам, но **P2-carryover
по ней не заводится, и вот почему.** Ни одна строка кода на этих путях в
этом цикле не менялась (правки — SMTP, набор модулей insightface,
планировщик отчётов). Три последовательных прогона на одном хосте дали
разброс 328–367 FPS по `decode_opencv` — 12 % **внутри** сессии. То есть
хост песочницы этой сессии просто медленнее хоста прошлой, а контейнер
пересоздаётся между сессиями на другом железе и с другими соседями.

**Методологический вывод для будущих циклов:** сравнивать абсолютные
числа между сессиями песочницы бессмысленно, и прошлые отчёты делали это
зря. Базой для отслеживания деградации должен быть артефакт CI-джобы
`perf` — он снимается на одинаковых раннерах GitHub. Это и есть то, что
докстринг `perf/bench.py` называет «на одинаковом железе раннера».
Занесено в carryover.

## 6. Carryover

### Функциональные гэпы (по §22 — приоритет над остальным)

Порядок — как их стоит брать следующими циклами:

4. **§5 покадровый просмотр** в плеере архива.
5. **§16 автоконфигурация при первом запуске**: определить ресурсы →
   предложить пределы камер записи и analytics.
6. **§12 ONVIF Profile G.**
7. **§26 .deb + systemd + install-тест в CI** — по объёму самый большой
   гэп, но §22 ставит production-упаковку на последнее, 7-е место в

### Новое в carryover этим циклом

* **База для сравнения производительности — артефакт CI, а не песочница.**
  См. 4.3. Абсолютные числа между сессиями песочницы несравнимы (разброс
  12 % внутри одной сессии, до 26 % между сессиями без единой правки
  кода). Следующему циклу стоит начать складывать числа из джобы `perf`.
* **CSV выгружается без BOM** — Excel под Windows читает кириллицу как
  cp1251. Чинить надо разом для всех выгрузок (отчёты §8 и журнал аудита
  идут разными путями), поэтому в PR #92 сознательно не тронуто: разнобой
  между двумя видами CSV хуже одинакового поведения обоих.
* **Группа `chain` бенчмарка не гоняется в CI** — тянет модель ~125 МБ.
  Регрессию набора модулей сторожит статический тест, но абсолютные числа
  цепочки между циклами никто не отслеживает.

## 7. Known gaps — что проверить на сервере

Все пункты в `docs/DEPLOY_CHECKLIST.md` (добавлен раздел 7.1
«Оповещения», расширен раздел 3).

* **Доставка почты боевым релеем** — в песочнице проверен весь путь до
  SMTP-сервера, но сертификат, SPF/DKIM и спам-фильтр не воспроизводятся.
* **Реальный watchlist-алерт по обоим каналам на одном событии** —
  регрессия «первый канал забрал ключ» видна только при обоих включённых.
* **Звук на Стене в браузере** — WebAudio и autoplay-политика логикой не
  покрываются.
* **Часовой пояс сервера для расписания отчётов** — слоты считаются по
  локальному времени процесса.
* **§19 на целевом CPU без AVX2** — первый норматив к перепроверке; запас
  1.7× может быть съеден целиком.
* **FPS на самой людной камере**, а не на средней — эмбеддинг считается
  на каждое лицо.
* Норматив CPU/RAM, RTO, доступность, задержка live, remux.
* .deb-пакет и systemd-юниты — когда появятся.
