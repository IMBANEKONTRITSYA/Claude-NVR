## 3. Гэп 1 (§12, §9): штатный Bearer отвергался кодом 422

### 3.1 Что было

`get_user_from_query_token` объявлял `token: str = Query(...)` —
**обязательным**. Клиент, отправляющий токен так, как предписывает §12 для
всего остального API, получал 422 **от валидатора FastAPI**, до всякой
проверки подписи.

Замерено через nginx **до** правки:

| Транспорт | `/api/system/prometheus` | `/api/reports/cameras.csv` | `/api/audit/export.csv` |
|---|---|---|---|
| `Authorization: Bearer` | **422** | **422** | **422** |
| `?token=` | 200 | 200 | 200 |

Затронуто 16 эндпоинтов (список получен из `openapi.json`, а не грепом):
выгрузки §8 (6), экспорт/файл/кадр архива §5 (3), экспорт аудита §10 (2),
выгрузка камер и снимок §3 (2), скачивание копии §11 (1), медиа (1),
Prometheus §9 (1).

### 3.2 Почему шесть циклов не находили

Из кода это читается как намеренное решение — «токен в query, потому что
браузерная ссылка не может поставить заголовок». А юнит-тесты всегда ходили
сюда **с `?token=`**, то есть покрывали ровно тот транспорт, который
работал. Гэп существует только для клиента, написанного по документации, —
и виден только когда такой клиент делает запрос.

Отдельно: `docs/ADMIN_GUIDE.md` **прямо противоречил** коду («требует
Bearer-токен», «готов к подключению `scrape_config` без дополнительного
экспортёра»). Противоречие документа и кода тоже не ловится ни тем, ни
другим по отдельности.

### 3.3 Правка

`get_user_from_query_token` принимает оба транспорта: заголовок первым (не
попадает ни в access-log, ни в историю браузера, ни в `Referer`), `?token=`
следом. Схема сверяется регистронезависимо (RFC 7235 §2.1); чужая схема и
пустые учётные данные — «токена в заголовке нет». Нет ни одного — **401** с
`WWW-Authenticate`, а не 422.

**Матрица прав §18 не расширена.** Оба пути сходятся в `user_from_token`,
роль читается из БД. Проверено живым опросом (viewer → 403 на обоих
транспортах) и тестом на разжалование по **не истёкшему** токену.

### 3.4 Проверка

| Проверка через nginx | Результат |
|---|---|
| `Authorization: Bearer` на всех 16 | 200 |
| `?token=` | 200 (не сломан) |
| без учётных данных | 401 (было 422) |
| негодный токен в заголовке | 401 |
| `Authorization: Basic ...` | 401 (не 500) |
| viewer, оба транспорта | 403 |

**Верификация откатом:** 47 новых тестов; с возвращённым `Query(...)`
падают **39 из 47**, проходят ровно 8 — те самые query-транспортные,
которые и не были сломаны. Набор ловит именно этот дефект.

## 4. Гэп 2 (§19): nginx ходил к бэкенду по HTTP/1.0

### 4.1 Что было

Апстрим объявлялся прямым `proxy_pass http://facewatch-backend:8000` — без
блока `upstream`, без пула. В таком виде nginx проксирует по **HTTP/1.0 с
`Connection: close`**: каждый запрос к `/api/` открывает новое
TCP-соединение и закрывает его. Закрывает активно nginx, поэтому порт
уходит в **TIME_WAIT на 60 с** (2×MSL, в Linux не настраивается).

### 4.2 Замер до/после

Настоящий nginx 1.24 перед настоящим бэкендом, 1000 запросов, 8 клиентов,
`/api/health`. Клиент держит keepalive до nginx — меряется именно участок
nginx→бэкенд:

| | было (1.0) | стало (1.1 + пул) | дельта |
|---|---|---|---|
| запросов/с | 318.6 | 350.7 | **+10 %** |
| медиана | 18.86 мс | 16.06 мс | **−15 %** |
| p95 | 22.95 мс | 21.69 мс | в пределах шума |
| p99 | 26.72 мс | 52.55 мс | **шум** (см. ниже) |
| **TIME_WAIT / 1000 запросов** | **+1037** | **0** | **−100 %** |
| ESTABLISHED к бэкенду | 0 | 16 (пул) | — |

**Честно про p99:** он гуляет между прогонами в обе стороны (в трёх
контрольных раундах было 23→56, 28→80, 26→20 мс). На петле в общей
песочнице это шум, и выводов из него не делается. Выигрыш по задержке тоже
скромный — TCP-connect по loopback дёшев.

**Суть находки не в задержке, а в исчерпании ресурса.** 28232 эфемерных
порта (32768-60999) при TIME_WAIT 60 с дают потолок устойчивого темпа
**~470 запросов/с** к бэкенду, после чего nginx перестаёт мочь подключиться
(`EADDRNOTAVAIL`) и отвечает **502** — под нагрузкой, когда это дороже
всего. На объекте §1 столько дают мониторинг, дашборд и опрос статусов
вместе, а сабреквест `/internal/hls-auth` идёт на **каждый** `.ts`-сегмент
каждого зрителя стены.

### 4.3 Правка и её ловушка

Блок `upstream facewatch_backend` с `keepalive 32`, и в трёх проксирующих
location'ах — `proxy_http_version 1.1` + `proxy_set_header Connection ""`.

**Все три директивы нужны вместе, и ошибка здесь молчаливая.** Проверено
откатом на живом nginx: с одним лишь `keepalive 32` в upstream (без 1.1 и
без обнуления `Connection`) — **TIME_WAIT +1014 на 1000 запросов и НОЛЬ
соединений в пуле**, то есть ровно как без правки, при этом `nginx -t`
проходит и конфиг выглядит правильным. Поэтому класс сторожится тестом, а
не комментарием.

`/ws/` намеренно не тронут по существу: там `Connection` несёт `upgrade`, и
соединение после апгрейда в пул вернуться не может. `/hls/` по-прежнему
идёт в MediaMTX.

### 4.4 Что не сломалось (проверено вживую)

| Проверка | Результат |
|---|---|
| апгрейд `/ws/faces`, `/ws/cameras` | OPEN, приходит `{"type":"ping"}` |
| `/ws/faces` без токена | отказ |
| `/hls/` без куки / с валидной | 401 / проксирование в MediaMTX |
| security-заголовки на `/` | все 4 на месте |
| rate limit `/api/auth/login` | 429 после burst |
| версия протокола к бэкенду | `HTTP/1.1` |

**Верификация откатом:** 5 новых тестов конфига; снятие любой из четырёх
директив (`proxy_http_version`, `Connection ""`, `keepalive`, `proxy_pass`
мимо пула на `host:port`) роняет ровно один тест, восстановление — зелено.

## 8. Carryover

### Функциональные гэпы
1. Отсутствующих функций §3-13 нет. Но **вывод «гэпов нет» по чтению кода
   недостаточен** — этот цикл нашёл два дефекта первым же живым опросом
   через настоящий nginx. **Опрос через nginx должен стать регулярным**, а
   не разовым: конфиги `frontend/nginx*.conf` до цикла 62 ни разу не
   исполнялись, их сторожили только статические тесты по тексту. P1.

### Производительность
2. Замер нагрузки на бэкенд идёт по петле в общей песочнице: p99 гуляет
   между прогонами в обе стороны, выводы можно делать только по rps,
   медиане и **детерминированным** величинам (счётчик сокетов). P2.
3. Потолок «~470 запросов/с» посчитан от диапазона портов песочницы
   (28232). На объекте диапазон может быть шире или уже — сверять
   `sysctl net.ipv4.ip_local_port_range`. P3.
4. `prune_motionless_segments` — 900-секундная санкция. P2. *(с цикла 59)*
5. `FACE_APP` общий и лежит на ноде менеджера. P2. *(цикл 41)*
6. Сравнивать между циклами только внутри одной модели CPU и только `chain`.
7. §17: выигрыш NUMA-привязки в песочнице не измерим (одна нода).
8. §13: доступность 99.5 % требует суток наблюдения.
9. Стоимость replay под нагрузкой не измерена. P2.
10. Задержка live не измерена на H.265 и под нагрузкой. P2.
11. Опрос камер по именам хостов резолвится блокирующе внутри нитей. P2.
12. Непрерывность записи измерена только на локальной петле. P2.
