## P0 — Безопасность

### P0-1: `/hls/` (живое видео) отдавался вообще без авторизации (PR #22)

Найдено прицельным security-скан-агентом в начале цикла (RBAC на каждом
эндпоинте, инъекции, шифрование секретов, CORS/cookie-флаги, upload-пути,
brute-force защита логина — задание было явно НЕ повторять уже закрытые
пункты чек-листа, а искать новое). Пять прошлых циклов не поднимали
конкретно `/hls/`, потому что предыдущие security-аудиты (циклы 1, 3, 5)
фокусировались на API-эндпоинтах backend, а не на media-проксировании через
MediaMTX — `location /hls/` в `nginx-locations.conf` проксировал напрямую в
MediaMTX **без единой проверки**:

```nginx
location /hls/ {
    proxy_pass http://facewatch-mediamtx:8888/;
    ...
}
```

Все остальные media-эндпоинты (`/api/archive/file/{id}`,
`/api/cameras/{id}/snapshot`, `/api/system/prometheus`) требуют валидный
JWT. ID камер — маленькие последовательные целые числа, поэтому **любой,
у кого есть сетевой доступ к nginx (без логина вообще), мог посмотреть
видео с любой камеры**, просто перебирая `/hls/cam1/index.m3u8`,
`/hls/cam2/...` и т.д. Для системы видеонаблюдения это сводит на нет всю
модель RBAC/JWT для самого чувствительного актива продукта.

**Фикс:**
- nginx `auth_request` на новый внутренний location `/internal/hls-auth`,
  проксирующий в backend;
- новый эндпоинт `GET /api/cameras/hls-auth`, переиспользующий существующую
  зависимость `get_current_user` (тот же контракт, что у всех остальных
  защищённых эндпоинтов); роль не проверяется намеренно — матрица прав ТЗ
  разрешает просмотр видео онлайн всем трём ролям;
- транспорт токена — **cookie** `hls_auth` (`path=/hls/`), не заголовок и
  не `?token=`: HLS-плеер (что нативный `<video>`, что hls.js) дёргает не
  только `index.m3u8`, но и `.ts`-сегменты по **относительным URI из
  плейлиста** — query string исходного запроса на них не переносится, а
  cookie браузер прикрепляет к каждому запросу автоматически независимо от
  того, как получен URL. Cookie несёт тот же access-токен, что уже
  используется для `Authorization`-заголовка (не новый секрет), обновляется
  синхронно с login/refresh в `setAuth()`.

Тесты: `test_hls_auth_rejects_missing_or_invalid_token`,
`test_hls_auth_accepts_any_authenticated_role` (backend),
`test_hls_location_requires_auth_request` (статическая проверка nginx-конфига,
по образцу существующего `test_nginx_hardening.py`).

Этой же сессией сразу отправлено push-уведомление пользователю о находке —
не стали ждать конца цикла, учитывая критичность.

## P2 — Производительность / SPEC 18.7 (ONVIF)

### P2-1: ONVIF-клиент событий движения/присутствия (PR #23)

Пять предыдущих циклов откладывали **весь** пункт ТЗ 18.7 с одним и тем же
обоснованием: нет реальной ONVIF-камеры в песочнице для сквозной проверки.
Это исполнимо для end-to-end проверки полного пользовательского сценария,
но не мешает написать и покрыть тестами сам протокольный клиент — решение
этого цикла: разделить задачу на то, что тестируется без камеры (сам
клиент), и то, что без неё не тестируется осмысленно (автообнаружение).

**Сделано:**
- `worker/onvif_client.py` — ONVIF-клиент только на stdlib (`urllib`,
  `hashlib`, `xml.etree`), без `onvif-zeep`/`suds` (тянут zeep/lxml —
  тяжёлые транзитивные зависимости, которых больше нигде в воркере нет):
  WS-Security UsernameToken (PasswordDigest) по спецификации,
  `CreatePullPointSubscription`, `PullMessages`, классификация топиков
  ONVIF Event Topic Namespace в движение/присутствие человека.
- `worker/worker.py`: камеры с `onvif_enabled` получают фоновую нить
  `onvif_poll_worker` параллельно с RTSP-циклом. Пока подписка здорова
  (недавний успешный pull), `camera_worker` **полностью пропускает
  MOG2-префильтр** — это и есть смысл экономии ресурсов в ТЗ 18.7 ("камера
  делает предобработку на своём чипе"). Любой сбой ONVIF в пределах одного
  health-window (30с) прозрачно возвращает на обычный MOG2-путь — детекция
  не останавливается ни при каких сетевых проблемах с камерой.
- Camera model/schema/CRUD: `onvif_enabled/host/port/username/password` по
  тому же принципу шифрования, что и RTSP-учётки (Fernet, admin-only,
  никогда не возвращаются в list/read-ответах).
- `frontend/Cameras.tsx`: поля конфигурации ONVIF на камеру, бейдж ONVIF.

**Сознательно не сделано:** WS-Discovery автообнаружение камер в сети
(тоже упомянуто в ТЗ 18.7 для UI) — уже по объёму, чем сам клиент событий,
и по-настоящему выигрывает от реального устройства/эмулятора для проверки
discovery-ответов (широковещательный multicast-протокол сложнее осмысленно
замокать, чем request/response SOAP), в отличие от PullPoint-клиента выше.
Оставлено на следующий цикл — см. рекомендации.

Тесты: `worker/tests/test_onvif_client.py` — 19 новых тестов (WS-Security
digest пересчитан независимо и сверен по формуле спецификации, парсинг
`CreatePullPointSubscriptionResponse`/`PullMessagesResponse`, ошибки сети/
таймаута/невалидного XML, классификация топиков движения, включая
регистронезависимость и `State=false`); `test_camera_onvif_config_roundtrip`
(backend, CRUD + шифрование + `has_onvif`).

## Рекомендации на следующие циклы (по приоритету)

1. **ONVIF WS-Discovery автообнаружение** (остаток ТЗ 18.7) — единственная
   оставшаяся часть пункта. В отличие от PullPoint-клиента (протестирован
   без камеры на статичных SOAP-фикстурах), WS-Discovery — широковещательный
   UDP multicast-протокол, осмысленно протестировать который сложнее без
   хотя бы эмулятора (`onvif-simulator` в Docker, как предлагал цикл 5) —
   решить на уровне заказчика, предоставить ли эмулятор или явно перевести
   в roadmap.
2. **Удаление смерджённых веток** — шестой цикл подряд `git push --delete`
   получает HTTP 403 от прокси песочницы, отдельного `delete_branch` в
   GitHub MCP-инструментах нет. Требует решения на стороне оркестрации
   (либо расширение прав прокси, либо MCP-инструмент для удаления веток) —
   не решается изнутри сессии ни при каком количестве попыток, дальше
   повторять эту рекомендацию без изменений на той стороне бессмысленно.
3. **Разночтение назначенной ветки харнесса vs фактической** — шестой цикл
   подряд один и тот же паттерн (см. раздел выше). Стоит проверить, почему
   сессии для этой конкретной recurring-задачи не получают в качестве
   стартовой ветку `claude/pensive-brown-28588t` напрямую, а получают
   пустую ветку, которую промпт задачи затем переопределяет.
4. Полноценный проход по производительности не проводился с цикла 3 (кроме
   ONVIF) — если появятся сигналы деградации на реальном железе (N100/
   Ryzen 9), стоит перезамерить FPS/CPU по профилям с текущим кодом, а не
   полагаться на замеры трёхлетней (в терминах циклов) давности.
