## 5. §12: ONVIF Profile G — сервер поиска записей (#107)

**Что требует ТЗ.** §12 перечисляет «ONVIF Profile S (стриминг) и Profile G
(хранение)». Profile S работал (стриминг, PTZ, автообнаружение — worker/
onvif_client.py). Profile G — интерфейс, по которому **внешний VMS**
(Milestone/Genetec/NX Witness) находит записи регистратора и их границы во
времени — отсутствовал вовсе.

**Что сделано — «поисковая» половина, целиком и проверяемо.** Четыре
SOAP-эндпоинта поверх `video_segments`:

| Сервис | Операции |
|---|---|
| Device | GetServices, GetSystemDateAndTime, GetServiceCapabilities |
| Recording | GetRecordings (запись = камера, трек = видеопоток), capabilities |
| Search | GetRecordingSummary, FindRecordings → токен, GetRecordingSearchResults, EndSearch, capabilities |
| Replay | GetReplayUri, capabilities |

Модель: **Recording = камера** (токен `cam{id}`, тот же префикс, что у пути
MediaMTX и файла сегмента §20), **Track = видеопоток** (`VIDEO_{id}`),
границы — агрегаты `min(started_at)`/`max(ended_at)`. Область `FindRecordings`
фильтрует по камерам; неизвестный источник даёт «нет записей», а не чужие.

**Ключевые решения:**

* **SOAP собирается шаблонами, вход разбирается `defusedxml`.** Серверных
  ONVIF-SOAP-фреймворков в проекте нет, операций четыре, форма ответа
  фиксирована WSDL — шаблоны честнее лишней зависимости. Вход из сети —
  `defusedxml`, а не stdlib `xml.etree` (billion laughs, §14/OWASP), тот же
  пакет и по той же причине уже в `worker/onvif_client.py`.
* **WS-Security против отдельной ONVIF-учётки, не таблицы `users`.**
  UsernameToken Digest = `SHA1(nonce+created+password)` требует пароль в
  открытом виде, а `users` хранит bcrypt-хэши. Поддержаны Text и Digest,
  проверяется свежесть `Created` (±5 мин), сравнение constant-time.
* **Fail-closed.** Фича выключена по умолчанию (`ONVIF_G_ENABLED`) —
  выключенные эндпоинты отдают 404. Включена без пароля — отказ всем
  (`ter:NotAuthorized`, Receiver fault), не анонимный доступ.
* **Replay честно необязателен.** MediaMTX не отдаёт ONVIF-replay по
  времени (RTSP с Range/Rate-Control) сам. `GetReplayUri` без
  `ONVIF_G_REPLAY_URI_BASE` отвечает `ter:NotSupported`, а не выдаёт
  ссылку, которую нечем воспроизвести. Боевой replay-источник настраивает
  оператор — это в DEPLOY_CHECKLIST 7.2, не заглушка в коде.
* **Эндпоинты — в `NOT_AUDITED`.** Субъект обращений — ONVIF-учётка, не
  пользователь FaceWatch: колонки `username`/`role` общего `audit_log`
  заполнить нечем, а VMS вдобавок опрашивает GetRecordingSummary
  периодически (тот же довод, что у автопродления сессии).

**Верификация:** 24 теста на production path (настоящий SOAP-конверт →
эндпоинт → разбор ответа; данные в том же Postgres). Покрывают авторизацию
(нет токена / чужой пароль / fail-closed без учётки), полный цикл
find→results→end (+ токен освобождён EndSearch), исключение чужих камер
областью, replay (не настроен/настроен/чужой токен), кривой XML,
capabilities, WS-Security Digest и протухший Created.

## 6. Производительность (обязательная секция)

### 6.1 Горячий путь нового кода — поиск Profile G (§12, родственно §7)

Микробенчмарк на **240 000 сегментах / 120 камер** в Postgres 16 песочницы
(запросы и индексы production, синтетические строки):

| Операция | Запрос | Медиана | Макс |
|---|---|---|---|
| GetRecordingSummary | `min/max/count(distinct)` по всей таблице | **27.3 мс** | 28.1 мс |
| GetRecordingSearchResults (область 3 камеры) | group-by по 3 камерам | **26.7 мс** | 30.7 мс |
| GetRecordings (все камеры) | group-by min/max по всем 240k строк | **1014 мс** | 1059 мс |

Обычный путь VMS (FindRecordings с областью → GetRecordingSearchResults) —
**27 мс**, внутри §7 «≤ 5 с» с запасом ~180×. `GetRecordings` без области —
полный group-by-агрегат по всей таблице, **~1 с на 240k**: внутри норматива
§7, но на E5-2670 без AVX2 и на миллионах сегментов вырастет. Оптимизация —
покрывающий составной индекс `video_segments(camera_id, started_at,
ended_at)` под index-only min/max — **в carryover P2** (не регресс, внутри
норматива; отдельным PR после мерджа #107, чтобы не смешивать с фичей).

   Осталось: воспроизведение через RTSP-источник записей (MediaMTX сам

2. **§26 .deb + systemd + install-тест в CI** (issue #86) — по §22 7-й
   приоритет.
3. **Хардкод числа камер** (§22 «Запрещено»): `routers/system.py:311`,

   загрузке), `profiles.py`, `loadtest/`, `test_loadtest_scale.py`,

4. **Класс отказа «сервис жив и не отвечает» не закрыт ничем** (из цикла

### Прежний carryover, оставшийся в силе

неприменимые к production-сборке. Числа §19 циклов 29 и 34 недействительны
(сняты на 4 ядрах, см. отчёт цикла 36).
