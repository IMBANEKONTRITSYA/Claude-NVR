## 5. §3: выгрузка конфигурации теряла расписание и зоны (#104)

**Находка.** Файл конфигурации выглядел полным — имя, локация, режим,
оба RTSP-URL, retention, ONVIF, — но не нёс расписания детекции (§6) и
полигонов ROI (§11 «Настройки по камерам: retention, ROI, режим»).

**Почему не поймали раньше.** Круговой сценарий «выгрузил → поправил →
загрузил назад» проходит чисто: импорт обновляет существующую камеру и
не трогает то, чего нет в файле. Ломается второй сценарий, заявленный в
преамбуле самого модуля, — перенос конфигурации на другую установку.
Там камера заводится файлом с нуля, подставить сохранённое неоткуда, и
весь парк приезжает с «детекция круглосуточно по всему кадру»: ночная
детекция там, где её отключали, и потеря зон, нарисованных руками.

**Приём, который стоит переиспользовать:** *спросить, для каких
сценариев функция заявлена, и проверить каждый отдельно*. Здесь тест
существовал ровно на один из двух, и второй — тот, ради которого §3
вообще написан («перенос с тестового стенда на боевой сервер»), — не
проверялся ничем.

**Решение.** Две колонки с JSON в ячейке (структуры вложенные — плоских
колонок потребовалось бы переменное число). Отсутствие колонки и пустая
ячейка разведены: файл прежней версии колонок не содержит вовсе, и
трактовка «нет колонки — стереть» сняла бы расписания со всего парка
при загрузке старого файла ради правки одной локации. ROI намеренно не
добавлен в `CameraIn` — зоны правятся отдельным эндпоинтом, и поле в
общей модели стирало бы полигоны при каждом сохранении формы камеры
(мина, уже срабатывавшая с полями ONVIF и расписанием).

**Верификация откатом** — 6 мутаций, каждая роняет свои тесты: колонки
убраны из выгрузки (1), «нет колонки» = стереть (1), пустая ячейка =
сохранить (3), `cam.roi` не записывается (2), ROI не валидируется (1),
словарь не сериализуется в ячейку (2).

## 6. §19 RTO ≤ 5 минут — измерено (в PR не оформлено)

Замер проведён на настоящем стеке песочницы (Postgres 16 + pgvector +
Redis из apt), бэкенд поднимался как отдельный процесс `uvicorn`,
здоровьем считался `GET /api/health` с `ok: true` — глубокая проверка,
где БД и Redis реально отвечают, а не открытый TCP-порт.

| Сценарий | Факт | Норматив | Дельта |
|---|---|---|---|
| Старт на пустой схеме (все миграции с нуля) | **2.07 с** | ≤ 300 с | 0.7 % норматива |
| `SIGKILL` → снова здоров (3 прогона) | **1.41 / 1.54 / 1.57 с** | ≤ 300 с | 0.5 % норматива |
| Postgres упал и вернулся | отказ виден в `/api/health` (503, `db: Connection refused`); пул восстановился **сам за 0.04 с** | — | перезапуск не требуется |
| Redis упал и вернулся | отказ виден (503, `redis: Connection refused`); восстановление **0.01 с** | — | то же |

Норматив по классу «процесс упал» **выполняется с запасом в два порядка**.
Оговорки: хост песочницы быстрее E5-2670, база пуста (на объекте
`face_events` — миллионы строк, и проверка схемы идёт дольше).

**Ложно-зелёный результат в первой редакции замера — и как он поймался.**
Первый прогон отчитался `reported_unhealthy: false` для обоих сценариев
отказа: якобы остановка Postgres не видна в `/api/health`. Причина
оказалась в самом замере: `/api/health` отвечает **503** с телом, а
`urllib` возбуждает на 503 `HTTPError`, который ловился в одном `except`
с обрывом связи. Замер при этом оставался «успешным» — он просто не
подтверждал, что было от чего восстанавливаться. Проверено прямой
командой (`service postgresql stop` + `pg_isready`), что остановка
работает, — и только это отличило дефект замера от дефекта системы.

**Приём в carryover:** *у сценария «сломалось и починилось» проверять
отдельно, что поломка вообще наблюдаема*. Без этой проверки сценарий
измеряет восстановление после ничего.

### Две находки по смерженному `perf/bench_rto.py` (цикл 34)

Чужой замер меряет только прогрев, а остальные слагаемые RTO берёт из
конфигурации. В этой части — две ошибки, обе занижают риск:

1. **Константы не соответствуют `docker-compose.yml`.**
   `DETECT_HANG_SEC = 30 * 3` с пояснением «healthcheck бэкенда
   `interval: 30s`, `retries: 3`». Фактически у бэкенда `interval: 15s`,
   `retries: 5` — то есть 75 с, а не 90 с. Число цитирует конфигурацию,
   которой нет.
2. **Строка «RTO при зависании» описывает восстановление, которого никто
   не выполняет.** Docker перезапускает контейнер по **выходу процесса**;
   по неудачному healthcheck он не перезапускает **ничего** —
   `restart: unless-stopped` на unhealthy не реагирует. Ни `autoheal`, ни
   аналога в `docker-compose.yml` нет (проверено грепом). Значит для
   класса «процесс жив и не отвечает» RTO **не ограничен ничем**, а
   отчёт цикла 34 записал по нему «уложились».

Правильная формулировка для чек-листа: класс отказа «зависание» на
сегодня не закрыт ничем и должен закрываться на объекте — внешним
мониторингом, `autoheal` либо (в режиме 2 §26) systemd с `WatchdogSec`.

  «сломалось → починилось» (раздел 6). Готовая проверка на этот класс

* **Приём: сверять функцию со всеми сценариями, которые она заявляет**
