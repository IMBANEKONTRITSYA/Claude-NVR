## P1 — Раскрытие access-токена в access-логи (PR #27)

`archive`/`reports`/`cameras/snapshot`/`system/prometheus`/`ws/*` принимают
access-токен как `?token=...` в query string — осознанный компромисс
транспорта там, где запрос не может нести заголовок `Authorization`
(прямые ссылки/скачивание, WS handshake браузера, сторонний monitoring;
решение задокументировано ещё в цикле 6 при переводе `/hls/` на cookie).
Цикл 7 отметил, что раскрытие этих токенов в access-логи nginx/uvicorn не
было проверено предметно — этот цикл проверил и закрыл: по умолчанию оба
пишут полную query string в открытом виде, токен оседает в docker-логах
(json-file драйвер, ротация которого настроена с цикла 6) на неопределённый
срок, отдельно от TTL самого JWT.

**Фикс:** `frontend/nginx.conf` — `map` на `$args` вырезает значение
`token=...` (regex на `(?:^|&)token=`, не путает с `mytoken=`), новый
`log_format redacted` вместо родного `$args` в обоих `server{}` (80/443).
`backend/app/logging_utils.py` — `RedactedAccessFormatter` поверх
`uvicorn.logging.AccessFormatter`, подключен через `--log-config`
(`backend/app/logging_config.json`), тот же приём на уровне backend, чтобы
токен не осел в логах ни на одном хопе.

Проверено вручную (`nginx -t` + живой nginx + curl, живой uvicorn с
`--log-config` против `app.main`) и 4 юнит-тестами
`RedactedAccessFormatter` (маскирование в середине query string, токен как
единственный параметр, `mytoken`/`notoken` не задеты, путь без `token` не
тронут).

## P2 — ONVIF WS-Discovery автообнаружение камер (SPEC 18.7, PR #28)

Единственный оставшийся пункт SPEC 18.7 ("автообнаружение камер в сети") —
семь циклов откладывали его с обоснованием «нет реальной
ONVIF-камеры/эмулятора в песочнице». Как и с PullPoint-клиентом событий
(цикл 6), это верно для end-to-end проверки на реальном оборудовании, но
не мешает написать и протестировать сам протокольный клиент.

**Фикс:**
- `worker/onvif_client.py::discover_devices()` — WS-Discovery Probe
  multicast на `239.255.255.250:3702`, сбор `ProbeMatch`-ответов в течение
  `timeout`. Сборка запроса и разбор ответа — чистые функции; сама UDP-
  рассылка тестируется через внедряемую `socket_factory` (без реального
  multicast — CI-раннеры и песочницы часто его блокируют).
- `worker/onvif_api.py` (новый модуль) — внутренний HTTP-эндпоинт
  `GET /onvif/discover` на порту 9000. Отдельно от `embed_api.py`
  намеренно: тот тянет `cv2`/`insightface`, недоступные в CI worker-job;
  `onvif_api.py` зависит только от `fastapi`+`onvif_client`, поэтому
  тестируется `TestClient`'ом в CI (`.github/workflows/ci.yml` дополнен
  лёгкими `fastapi`/`httpx`, тяжёлые зависимости по-прежнему не ставятся).
  Discovery выполняется в `run_in_threadpool`, чтобы не блокировать
  `/embed` на время ручного сканирования сети.
- `backend/app/routers/cameras.py::GET /api/cameras/onvif/discover` —
  admin-only, проксирует к воркеру (у backend нет прямого сетевого пути
  для UDP multicast к камерам, у воркера есть).
- `frontend/src/pages/Cameras.tsx` — кнопка «Найти камеры в сети» (видна
  при включённом ONVIF), список найденных устройств с именем из ONVIF
  Scopes, клик подставляет host/port в форму.

**Не входит в этот цикл:** «получение профилей потоков» (вторая часть
SPEC 18.7 — `GetProfiles`/`GetStreamUri` ONVIF Media-сервиса) — за
пределами этого PR; автообнаружение уже закрывает основную функциональную
дыру (раньше host/port вводились только вручную).
