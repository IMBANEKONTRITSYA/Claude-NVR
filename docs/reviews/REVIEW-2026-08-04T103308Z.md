## P1 — Стабильность/корректность

### P1-1: WS-соединения не перевалидировали токен после подключения (PR #25)

`/ws/faces` и `/ws/cameras` (`backend/app/routers/ws.py`) проверяли JWT
только один раз при `ws.accept()`. nginx держит `/ws/` с
`proxy_read_timeout 3600s`, а сам обработчик каждые ~30с сам себе шлёт
`ping`, если нет свежих сообщений из Redis — то есть соединение практически
никогда не простаивает и не закрывается по таймауту. Каждый REST-эндпоинт
перепроверяет токен на каждый запрос через `get_current_user` (истечение +
существование пользователя в БД) — у WS такой гарантии не было вообще: ни
истечение 30-минутного access-токена, ни удаление пользователя не закрывали
уже открытый сокет. Тот же класс проблемы, что раньше нашли и почини­ли для
`/hls/` (PR #22, цикл 6, другой транспорт — HTTP-прокси вместо WS).

**Фикс:** `_still_valid(token, db)` перепроверяет `exp` и существование
пользователя на каждом цикле пинга; при первом провале — `ws.close(code=4401)`.

Тесты: 5 юнит-тестов `_still_valid` на in-memory SQLite (валидный/истёкший/
без `sub`/мусорный токен, удалённый пользователь). Полноценный
end-to-end тест "сокет закрывается через ~30с после истечения токена" не
добавлен — потребовал бы реально ждать 30 секунд в тесте, что не
соответствует конвенции остального набора; логика, которая единственная
меняет поведение, покрыта юнит-тестами исчерпывающе.

### P1-2 и попутная находка: `/api/auth/change-password` без лимита попыток + скрытый 500 (PR #26)

`POST /api/auth/change-password` не имел лимита попыток, в отличие от
Redis-счётчика `/login`, и не покрыт nginx-зоной `login` rate-limit (она
ограничена `location = /api/auth/login`). Держатель украденного или просто
короткоживущего access-токена мог подбирать `old_password` без
ограничений — превращая ограниченную по времени компрометацию токена в
постоянный, переживающий отзыв refresh-токенов секрет.

**Фикс:** тот же стиль Redis-лимита, что уже есть у `/login` (5 попыток /
5 минут), но по `user.id`, а не IP+логин — обладание валидным access-
токеном уже сильнее идентифицирует атакующего, чем IP.

**Попутно пойманный собственным тестом баг:** тест лимита (регистрация →
логин → change-password с неверным `old_password`, затем с верным) упал с
500 на настоящем Postgres — `user.password_changed_at =
datetime.now(timezone.utc)` пытался записать timezone-aware datetime в
колонку `TIMESTAMP WITHOUT TIME ZONE`, которую asyncpg отвергает. Эндпоинт
был **полностью сломан в проде** для любого клиента, вызывающего смену
пароля не через `/login`-эмулирующие моки — просто ни один из предыдущих
шести циклов не писал интеграционный тест на этот путь против настоящей
БД. Тот же класс бага, что уже задокументирован и починен для
`refresh_tokens` в `app/auth.py::_utcnow_naive` (см. рекомендацию №4 цикла
5/цикла 6 "проверить остальной код на баги того же класса" — в тот раз
проверялся только raw SQL, этот баг был в ORM-присваивании datetime, не в
SQL, поэтому предыдущий целевой грep его не поймал).

Тесты: `test_change_password_locks_out_after_repeated_wrong_old_password`,
`test_change_password_succeeds_and_resets_counter_below_limit`.

## Проверено прицельно и признано чистым (не найдено новых проблем)

Полный список направлений из промпта аудита, проверенных отдельным
security-скан-агентом сверх уже закрытых шестью циклами пунктов чек-листа:

- SSRF через пользовательские URL/host (cameras.py, ONVIF host, snapshot-
  прокси) — RTSP-схема уже валидируется с цикла 1, ONVIF host/port не
  проксируют произвольные запросы наружу.
- Path traversal в archive/exports/snapshot-эндпоинтах —
  `os.path.basename()` guard уже на месте.
- IDOR на by-ID эндпоинтах (камеры/персоны/события/отчёты) — RBAC-проверки
  из циклов 1-3 покрывают.
- Инъекции через `subprocess`/f-string/SQL-конкатенацию — все найденные
  `subprocess`-вызовы используют list-формат аргументов, raw SQL
  параметризован.
- Утечка секретов в структурированные JSON-логи (цикл 6) — пароли/токены
  не логируются; RTSP/ONVIF-учётки шифруются до записи в БД и не попадают
  в логи в открытом виде.
- Актуальность зависимостей — `pip-audit -r backend/requirements.txt` и
  `-r worker/requirements.txt` (тот же флаг `--ignore-vuln PYSEC-2026-1325`,
  что и в CI) — чисто, известных уязвимостей не найдено.

Отдельно замечено (не заведено как отдельная проблема, т.к. осознанный
компромисс, а не забытый недосмотр): access-токен передаётся как
`?token=` на нескольких GET/WS-эндпоинтах (архив, snapshot, prometheus,
отчёты, WS) — необходимо, потому что эти запросы либо инициируются не
JS-кодом (прямые ссылки/скачивание/WS-handshake браузера, который не может
слать кастомные заголовки на этапе подключения), либо тянутся
сторонним monitoring-инструментом (prometheus). Сам токен при этом не
раскрывается нигде, кроме стандартных access-логов nginx/uvicorn (не
инструментировано отдельно в этом цикле) — тем не менее это тот же
уровень раскрытия, что cookie-транспорт для `/hls/` (PR #22) уже сознательно
избегал по этой же причине. Стоит оценить на следующем цикле: либо
редактировать query-string в конфигурации access-логов (nginx
`$request`/uvicorn access log format), либо мигрировать оставшиеся
`?token=`-эндпоинты на cookie-транспорт по образцу `/hls/`.

   получает 403 от прокси песочницы. Не повторяю рекомендацию искать
   обходной путь внутри сессии (цикл 6 уже отметил это бессмысленным) —
   решение только на стороне оркестрации.
3. **Разночтение назначенной ветки харнесса vs фактической** — семь циклов
   подряд один и тот же паттерн, см. раздел выше.
