## Конкурентный запуск — почему цикл остановлен

Сессия `2026-08-05T232816Z` (цикл 21) была активна в момент старта цикла 22 и
находилась в фазе ожидания CI по собственному PR.

### Доказательство активности, а не остаточных следов

Проверка `pull_request_read(method=get_status, pullNumber=63)` вернула
`"state": "pending"` при `"total_count": 0` — CI-проверки на момент наблюдения
ещё не зарегистрировались. Это не след завершившейся сессии: открытый PR с
незапущенным CI означает, что сессия A прямо сейчас находится в шаге 6h/6i
своего протокола («жду CI, потом мерджу»). Ни один из трёх прошлых циклов не
наблюдал пересечение настолько однозначно — циклы 19 и 20 восстанавливали его
постфактум по `[session:...]`-штампам в коммитах.

### Ключевое наблюдение цикла: пересечение означает дублирование работы

Циклы 19–20 пересекались по мерджу чужого PR — неприятно, но без потери
работы. Здесь риск качественно иной.

Сессия A шла **ровно по списку carryover из отчёта цикла 20**:

| Carryover цикла 20 | Закрыт сессией A |
|---|---|
| 1. Логирование апскейлера (`print()` → JSON) | PR #61 |
| 2. Graceful shutdown апскейлера | PR #61 |
| 3. `pool_size` апскейлера | PR #61 |
| 4. Изоляция тестов бэкенда | PR #63 (в полёте) |

Цикл 22, не остановившись, взялся бы за тот же список — он единственный общий
источник задач для обеих сессий, и протокол обеих (шаг 5, «CARRYOVER FIRST»)
предписывает начинать именно с него. **Две сессии на одной ветке не просто
конфликтуют по файлам — они детерминированно выбирают одну и ту же работу.**
Это довод в пользу abort сильнее, чем риск конфликта мерджа: конфликт виден и
чинится, а дублирующий PR к уже исправленному коду проходит CI и мерджится
незамеченным.

### Интервал планировщика сократился до 46 минут

| Переход | Интервал между стартами |
|---|---|
| цикл 19 → 20 | ≈ 3 ч 09 мин |
| цикл 20 → 21 | ≈ 5 ч 14 мин |
| **цикл 21 → 22** | **≈ 46 мин** |

Наблюдаемая длительность сессии — от ~50 мин (цикл 21 к моменту abort ещё не
закончил) до ~3 ч 10 мин (цикл 19). Интервал в 46 минут короче даже нижней
границы, то есть пересечение при текущем расписании не вероятностное, а
гарантированное. Это новая информация относительно issue #56: раньше интервалы
были «на грани», теперь заведомо за ней.

### Оценка самой проверки

Проверка «открытый PR моложе 30 минут» сработала здесь **истинно-положительно
впервые за три пересечения**, но полагаться на неё по-прежнему нельзя:

- цикл 20 наблюдал **ложноотрицательный** результат той же проверки — сессия A
  была жива, но открытых PR и новых коммитов не было (она ушла в анализ);
- сессия оставляет следы в GitHub API только в окне «PR открыт, CI не прошёл» —
  минуты из десятков минут работы. Цикл 22 попал в такое окно с запасом менее
  двух минут, то есть по существу случайно.

Грубая оценка: у цикла 21 таких окон было ~3 по ~5 минут на 50+ минут работы —
проверка пропускает пересечение чаще, чем ловит. Вывод для issue #56 не
изменился: надёжен только распределённый лок; эвристика — снижение
вероятности, не гарантия.

### Уточнение по пункту 5 (единственная содержательная работа цикла)

`backend/app/audit.py:121-130` — `_extract_user()` возвращает
`payload.get("sub"), payload.get("role")`, то есть **роль в журнал аудита
пишется из claim'а токена**, а не из БД. Осознанный долг цикла 19: PR #53
перевёл на резолв из БД авторизацию на 13 эндпоинтах, но middleware аудита
остался на claim'е.

**Последствие.** Разжалованный из админов пользователь до истечения access-токена
продолжает записываться в `audit_log` с ролью `admin`. Доступа это ему не даёт
(авторизация с цикла 19 идёт из БД), но журнал — контроль из ТЗ 13, и поле
`role` в нём в этот период недостоверно. Приоритет P3, не P0: искажается запись,
не решение о доступе.

**Почему это дёшево починить (для цикла 23).** Middleware уже открывает сессию
БД для самой записи — `audit.py:170`, `async with SessionLocal() as db`. Роль
резолвится в той же сессии одним `select(User.role).where(User.username == sub)`
до `db.add(AuditLog(...))`, без второго подключения и без изменения сигнатуры
`_extract_user` (она остаётся синхронным разбором токена и отдаёт только `sub`).
Отдельного цикла не требует — правка на десяток строк плюс тест «роль в журнале
меняется после `PATCH` роли, а не после истечения токена».

## Методологические заметки

**Что сработало.**

1. **Порядок проверок в протоколе оказался верным.** Concurrency-проверка стоит
   шагом 3, до аудита (шаг 4) — цикл потратил ~15 запросов и ноль правок кода,
   чтобы установить, что работать нельзя. Если бы проверка стояла после аудита,
   цена ошибки была бы в десятки раз выше, а соблазн «раз уж нашёл — почини»
   почти неодолим.
2. **`get_status` по открытому PR отличает живую сессию от завершившейся.**
   `state: pending` при `total_count: 0` — это «CI только что запущен, владелец
   ждёт», однозначный признак активности. Открытый PR сам по себе такого не даёт:
   он мог остаться от упавшей сессии. Стоит добавить этот вызов в шаг 3
   протокола явно, а не ограничиваться листингом PR по времени создания.
3. **Сверка списка carryover с уже смерджёнными PR** — за две минуты чтения
   `REVIEW-2026-08-05T181442Z.md` и заголовков #61/#63 стало видно, что сессия A
   идёт по тому же списку. Это превратило абстрактный «риск конфликта» в
   измеримый «дублирование конкретных четырёх пунктов» и сняло вопрос, не стоит
   ли всё-таки поработать над чем-то другим.

**Что не сработало.**

4. **Эвристика по времени сама по себе ненадёжна** — см. раздел «Оценка самой
   проверки»: цикл 20 получил на ней ложноотрицательный результат. Здесь она
   сработала с запасом менее двух минут; при старте на 15 минут позже цикл 22
   начал бы дублировать работу, не заметив ничего.
5. **Штампа `[session:...]` в заголовке PR по-прежнему нет** (пункт 4
   рекомендаций issue #56, не внедрён). Владельца PR #63 пришлось устанавливать
   косвенно — через штампы в уже смерджённых `9d0a191`/`7e29abf`. Со штампом в
   заголовке проверка свелась бы к сравнению строк.
