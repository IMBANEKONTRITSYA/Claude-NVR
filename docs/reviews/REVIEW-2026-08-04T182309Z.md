## P2 — Аппаратное ускорение декодирования видео (SPEC 18.2, PR #31)

ТЗ 18.2 требует двух независимых вещей: (1) инференс нейросетей на GPU и
(2) декодирование самих видеопотоков через GPU. Первое было закрыто до
этого цикла (`detect_providers()` — автовыбор CUDA → DirectML → OpenVINO →
CPU для onnxruntime). Второе оставалось программным: `cv2.VideoCapture`
открывался без единой попытки задействовать HW-декодер, несмотря на явную
формулировку ТЗ («снижает нагрузку на CPU в 5–10 раз»).

**Фикс:**
- `worker/hwaccel.py` (новый модуль) — `hw_decode_requested()` (читает
  `FACEWATCH_HW_DECODE`, по умолчанию включено) и
  `detect_hw_accelerator_name()` (best-effort диагностика для лога: ищет
  `nvidia-smi` в PATH → вероятно NVDEC; `/dev/dri/*` → вероятно
  VAAPI/QuickSync; иначе «не обнаружен»). Намеренно без импорта
  `cv2`/`onnxruntime` — тестируется в CI-джобе "pure-logic worker tests",
  которая ставит только `pytest fastapi httpx`, без тяжёлых ML-зависимостей
  (тот же приём, что `backoff.py`/`shutdown.py`, устоявшийся с первого
  цикла).
- `worker/worker.py::open_capture(url)` — новая функция, оборачивающая
  создание `cv2.VideoCapture`: создаёт объект, выставляет
  `cap.set(cv2.CAP_PROP_HW_ACCELERATION, cv2.VIDEO_ACCELERATION_ANY)` **до**
  `cap.open(url, cv2.CAP_FFMPEG)` (после открытия потока OpenCV это
  свойство больше не применяет — важная деталь API, которую легко
  пропустить). `VIDEO_ACCELERATION_ANY` — единственный режим, который
  одновременно (а) заставляет ffmpeg-бэкенд OpenCV попробовать доступный
  VAAPI/QuickSync/NVDEC и (б) прозрачно откатывается на программное
  декодирование, если ускоритель не найден или конкретный поток с ним
  несовместим, — без падения открытия потока. Заменил оба прежних места
  прямого вызова `cv2.VideoCapture(analyze_url, cv2.CAP_FFMPEG)` (первый
  запуск камеры и переподключение после разрыва RTSP) на общий вызов
  `open_capture()`, заодно устранив дублирование кода между ними.
  Обнаруженный ускоритель логируется один раз при первом открытии потока.
- `FACEWATCH_HW_DECODE=0` — явный fallback-флаг форсирования программного
  декодирования (на случай, если HW-путь окажется нестабильным с
  конкретной моделью камеры на конкретном железе — тот же принцип, что
  `hw_decode_requested()` уже читает).
- `docs/ADMIN_GUIDE.md` — новый раздел с инструкцией по пробросу
  `/dev/dri` в `docker-compose.yml` для реального VAAPI внутри контейнера.
  **Сознательно не включено в `docker-compose.yml` по умолчанию**:
  обязательная директива `devices:` с несуществующим путём ломает
  `docker compose up` целиком, а `/dev/dri` есть не на каждом хосте
  (включая, вероятно, большинство CI-раннеров) — то же соображение, что
  раньше применялось к другим опциональным аппаратным зависимостям в этом
  проекте.

**Не входит в этот цикл:** проверка на реальном HW-декодере (VAAPI/
QuickSync/NVDEC) — GPU по-прежнему недоступен в песочнице, как и для
инференс-провайдеров в более ранних циклах. `VIDEO_ACCELERATION_ANY`
выбран намеренно как режим, чьё поведение без GPU (не ломает открытие
потока) — это и есть то, что проверяемо в текущем окружении; поведение *с*
GPU остаётся недоказанным до цикла с реальным железом.

## Как проверялось

Docker daemon недоступен и в этот раз — тестировался только
worker-модуль изменений (`worker/hwaccel.py`), которому реальная БД/Redis
не требуются: `pip install pytest fastapi httpx` (ровно то, что ставит
CI-джоба `worker`) + `pytest tests/ -q` → 83 пройдено локально до пуша.
`python -m py_compile` на изменённых `.py`-файлах — синтаксис/импорты
валидны. Backend/frontend в этом цикле не менялись, локальный прогон не
требовался — подтверждено зелёным CI на реальных GitHub Actions.

Замечено: CI на PR #31 отработал **дважды** параллельно (workflow runs
`30938182243` и `30938224116`, оба на одном и том же коммите
`c7d69dc`) — оба набора job'ов (backend/worker/frontend/dependency-audit)
завершились успешно независимо, мердж выполнен после того, как зелёными
стали оба запуска. Это похоже на обычное поведение GitHub Actions при
двух событиях триггера (`push` в ветку + событие `pull_request` на только
что созданный PR) — а не на паттерн «конкурентная сессия» из циклов 9-10
(тот описывал два независимых экземпляра **этой автономной сессии**,
пишущих коммиты от первого лица, а не два обычных CI-триггера на один и
тот же пуш). Уточняю здесь, чтобы не спутать с находкой циклов 9-10 в
последующих отчётах.

## Рекомендации на следующие циклы (по приоритету)

1. **Конкурентный запуск сессий на одной ветке** — без новых находок в
   этом цикле, но остаётся неразрешённым системно (это находка про
   оркестрацию расписания, не про код) и статистически может повториться
   в любой будущий момент. По-прежнему приоритет №1 для стороны
   оркестрации — стоит проверить интервал между срабатываниями расписания
   и добавить блокировку параллельных запусков на одной ветке.
2. **Разночтение назначенной ветки харнесса vs фактической ветки с кодом**
   — 11-й цикл подряд один и тот же паттерн; должно быть тривиально
   починить на стороне оркестрации (харнесс должен либо переиспользовать
   `claude/pensive-brown-28588t`, либо промпт должен обновляться под
   назначенную ветку).
3. **Удаление смерджённых веток** — 11-й цикл подряд 403 от прокси
   песочницы; решение только на стороне оркестрации (расширение прав
   прокси или ручная периодическая чистка).
4. Полноценный проход по P0/P1 не проводился с цикла 7 — учитывая, что с
   тех пор добавлено четыре новых эндпоинта (ONVIF discovery/events/
   profiles/stream-uri) и несколько конфигурационных полей (битрейт
   записи, I-frame-only), стоит сделать освежающий целевой проход в
   ближайшем цикле, а не откладывать дальше.
5. **Аппаратное декодирование и инференс-провайдеры (ТЗ 18.2 целиком)** —
   ни разу не проверялись на реальном GPU за 11 циклов; если у проекта
   появится доступ к машине с Intel iGPU или NVIDIA GPU, это единственный
   способ содержательно подтвердить пятикратное-десятикратное снижение
   нагрузки на CPU, которое обещает ТЗ.
