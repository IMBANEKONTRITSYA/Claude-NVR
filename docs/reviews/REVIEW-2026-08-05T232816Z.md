## Найденное и исправленное

### 1. Сервис апскейла: нет JSON-логов, нет graceful shutdown, дефолтный пул — [#61](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/61) (P1)

Carryover цикла 20, все три пункта — в `upscaler/upscaler.py`.

- Весь вывод шёл через `print(..., flush=True)`: единственный сервис без
  структурированных логов (ТЗ 12).
- `main()` крутил `while True` — вернуться не мог в принципе.
  `docker compose stop` добивал SIGKILL'ом по истечении grace period.
  Убийство посреди `process_event()` попадает в промежуток между
  `cv2.imwrite` улучшенного файла и `ev.snapshot_path = enh_rel`:
  `enh_*.jpg` остаётся сиротой, на который не ссылается ни одна строка
  `face_events`.
- `create_engine` без `pool_size`: 5+10 соединений под однопоточный
  сервис, которому одновременно нужно ровно одно.

**Побочная находка, важнее исходных трёх.** `upscaler/Dockerfile` нёс
поимённый `COPY upscaler.py .` — тот самый взрыватель, на котором воркер
несколько раз собирался успешно и падал в CrashLoop с
`ModuleNotFoundError` (регрессионная проверка на него живёт с цикла 18).
Проверка знала только о воркере, а у апскейла мина не была наступлена
только потому, что он был одним файлом без локальных импортов. Новый
`logging_utils.py` подорвал бы её при первом `docker compose up`.
Dockerfile переведён на `COPY *.py ./`, проверка параметризована по
сервисам (`test_worker_dockerfile_modules.py` → `test_dockerfile_modules.py`).

### 2. Необрезанные числовые параметры на 12 эндпоинтах — [#62](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/62) (P1, класс)

`days`/`limit`/`threshold` принимались как голый `int`/`float` без
`ge`/`le` и уходили прямо в `timedelta(days=...)` и в SQL `LIMIT`.
Проверено пробой на живом приложении — **шесть входов дают
необработанный 500 вместо 422**:

```
GET /api/stats/by-day?days=999999999        OverflowError: date value out of range
GET /api/stats/heatmap?days=99999999999999  OverflowError: int too large to convert to C int
GET /api/stats/top-persons?limit=-1         LIMIT must not be negative
GET /api/archive/segments?limit=-1          LIMIT must not be negative
GET /api/persons/{id}/gallery?limit=-1      LIMIT must not be negative
GET /api/reports/appearances.csv?days=...   OverflowError: date value out of range
```

Три из них (`/api/stats/*`) висят на `get_current_user` без проверки
роли — доступны **наблюдателю**, самой низкой роли матрицы прав.

Вторая половина проблемы отвечает 200 и честно делает, что просили:

- `POST /api/persons/{id}/enhance?limit=<много>` ставит в `upscale:queue`
  столько задач с `force=True`, сколько у персоны событий, **минуя
  ограничение в 500 элементов**, которое воркер соблюдает при штатной
  постановке (`worker.py`: `if want and r.llen("upscale:queue") < 500`);
- `threshold=-1` в поиске по лицу превращает
  `1 - (embedding <=> :vec) >= :threshold` в тавтологию — вместо
  совпадений отдаётся вся таблица `face_events`.

Границы вынесены в `backend/app/params.py`: `MAX_LIMIT=200` совпадает с
`page_size` серверной пагинации, то есть контракт «не больше 200 строк за
запрос» теперь один на всех списочных эндпоинтах. Фронтенд не изменился —
границы подбирались под него.

### 4. Заголовки безопасности пропадали на `/hls/` — [#64](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/64) (P1)

`add_header` в nginx **не накапливается по уровням**: директивы
наследуются с предыдущего уровня, только если на текущем уровне нет ни
одного собственного `add_header`. У `location /hls/` их два своих
(`Cache-Control`, `Access-Control-Allow-Origin`), поэтому всё, что стояло
в `server{}`, для видеопотока пропадало.

Замерено на настоящем nginx 1.24:

```
GET /                     → X-Frame-Options, X-Content-Type-Options,
                            Referrer-Policy, Content-Security-Policy
GET /hls/cam1/index.m3u8  → Cache-Control, Access-Control-Allow-Origin
                            — и больше ничего
```

`.m3u8` и `.ts`, проксируемые из MediaMTX, шли без `nosniff` (а их
содержимое приходит **от камеры** — наименее доверенный источник в
системе), без `X-Frame-Options` и, на HTTPS-хосте, без HSTS.

Обход авторизации это не даёт — `auth_request /internal/hls-auth`
(P0 цикла 6) на месте. Это пробел в защите в глубину, заметный только при
сравнении двух ответов рядом.

Заголовки вынесены в `frontend/nginx-security-headers.conf` и включаются
дважды (единственный способ «унаследовать и дополнить» в nginx). HSTS
переведён с расположения на значение (`map $https $hsts_value`), потому
что сниппет один на оба `server{}`; прежнее поведение — «только по
HTTPS» — сохранено ровно.

### 5. Роль в журнале аудита из claim'а токена — [#65](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/65) (P1)

Последний открытый пункт класса цикла 18. Цикл 19 (PR #53) перевёл на БД
всю *авторизацию*; журнал аудита остался на `payload.get("role")`.

Замерено на живом приложении:

| Состояние | Действие | Что писал журнал |
|---|---|---|
| разжалован `admin` → `operator` | экспорт отчёта → 200 | `role='admin'` |
| учётка **удалена** | тот же запрос → 401 | `role='admin'` |

Окно расхождения — до 30 минут (TTL access-токена). Последствие не в
доступе (закрыт циклом 19), а в достоверности контроля: журнал,
приписывающий действие не той роли, хуже отсутствующего — он выглядит
достоверным. Удалённая учётка теперь получает явное `(удалён)`.

Находка передана циклом 22, остановившимся на проверке конкурентности.

## Методологические заметки

### Сработало

**1. Поднять настоящий сервис вместо статического анализа — главный
приём цикла.** Двадцать циклов исходили из того, что без Docker-демона
проверить можно только текст. Это неверно:

```
apt-get install postgresql-16-pgvector   # + initdb от непривилегированного
apt-get install nginx-light              # пользователя (root не может)
redis-server --port … --daemonize yes
```

Эффект измеримый. Прогон бэкенда без БД — 110 passed / 117 **skipped**;
с БД — **227 passed**. То есть больше половины тестов бэкенда в песочнице
все прошлые циклы молча не выполнялись, и «зелёный прогон» означал
существенно меньше, чем выглядел. Все находки #62 и #65 получены
запросами к работающему приложению, а не чтением.

nginx дал находку #64 напрямую: `curl -D-` по двум URL рядом, и разница
в наборе заголовков видна мгновенно. Прочитать её в конфиге можно было
все 20 циклов — цикл 12 этот конфиг писал и не увидел, потому что
правило про ненакопление `add_header` надо помнить, а `curl` его
показывает.

**2. Спросить «что будет с крайним значением», а не «нет ли инъекции».**
Находка #62 — это один вопрос, заданный к каждому числовому параметру:
`days=999999999`, `limit=-1`. Ни один построчный проход этого не даёт:
код `limit: int = 200` выглядит совершенно нормально. Пробник на 10
строк, прогнанный по живому приложению, нашёл 6 отказов за минуту.
Стоит держать в чек-листе рядом с вопросом цикла 15 («что если этот код
никогда не завершится / выполнится дважды»).

**3. Проверить, покрывает ли существующая регрессионная проверка все
сущности своего класса.** `test_worker_dockerfile_modules.py` стерегла
инвариант «модули попадают в образ» — только для воркера, при том что
апскейл нёс ровно тот же поимённый `COPY`. Формулировка вопроса:
*«эта проверка защищает один экземпляр или весь класс?»* Тот же приём
дал общее правило в `test_nginx_security_headers.py` вместо проверки
единственного `location /hls/`.

**4. Позитивный контроль в каждом наборе тестов.** В #62 из 17 тестов
при откате падают 16 — уцелевший и есть контроль на пережатие границ.
Без него «исправлением» могло бы оказаться отбраковывание всего подряд,
и негативные тесты всё равно бы прошли. То же в #65 (2 негативных + 2
позитивных). Это дешёвая страховка от фикса, который проходит
собственные тесты и ломает продукт.

### Не сработало / стоило дороже

- **`git checkout <file>` для отката фикса при верификации.** Дважды
  снёс работающие правки целиком вместо отката одной строки (Dockerfile,
  `nginx-locations.conf`), пришлось восстанавливать вручную. Правильный
  приём — `cp` файла в scratchpad до отката и `cp` обратно после, как
  делалось для `upscaler.py`.
- **Свой же тест с багом разбора.** `test_server_level_includes_the_snippet_once`
  резал конфиг по слову `location`, которое встречается в комментариях
  выше по файлу, и падал на здоровом конфиге. Поймано только потому, что
  прогон делался до и после отката; если бы прогонялся только откат,
  «падает» выглядело бы подтверждением. **Вывод: смотреть не только на
  то, что тест падает при откате, но и на то, что он проходит без него —
  обе половины, всегда.**
- **Кросс-сервисное загрязнение БД.** Прогон тестов апскейла перед
  тестами бэкенда по одной БД ломает бэкенд: `Base.metadata.create_all`
  апскейла создаёт `face_events`/`persons` по своей урезанной модели, и
  дальше бэкенд падает с `relation "users" does not exist`. В CI не
  проявляется (разные джобы, разные контейнеры). Занесено в carryover.

## Sandbox limitations

| Отложено | Что нужно для верификации | Рекомендация по локальной проверке |
|---|---|---|
| ТЗ 18.2 — аппаратное ускорение инференса и декодирования | реальный GPU (CUDA/OpenVINO/DirectML) и драйверы | код полностью реализован с цикла 11; на машине автора достаточно `docker compose up` и проверки `worker:fps` в Redis против CPU-режима |
| Конкурентность `FACE_APP` (insightface) на GPU-провайдерах | тот же GPU | CPU-провайдер закрыт чтением исходников в цикле 17; для GPU нужен прогон 16 нитей с проверкой на порчу выдачи |
| ТЗ §14 — нагрузка 16 камер на уровне RTSP/инференса | физические камеры или RTSP-эмулятор + GPU | API-слой закрыт с цикла 13 (`loadtest/`, в CI как `workflow_dispatch`). Для потоков — `mediamtx` + `ffmpeg -stream_loop -1 -re -i sample.mp4 -f rtsp` в 16 экземплярах: даёт настоящую декодировку без камер |
| `docker build` всех образов | Docker-демон (недоступен 12 циклов подряд) | инварианты «модули в образе» и «сниппет nginx в образе» стерегутся статически (`test_dockerfile_modules.py`, `test_nginx_security_headers.py`); сам build проверяется только на машине автора |
| Поведение `graceful shutdown` апскейла под `docker compose stop` | Docker-демон | сигнал проверен настоящим `os.kill(SIGTERM)` в тесте — это ровно то, что посылает Docker; непроверенным остаётся только соблюдение grace period целиком |

**Снято с этого списка в цикле 21:** «Postgres+pgvector и Redis
недоступны» и «nginx нельзя поднять». Оба доступны через `apt`, см.
методологические заметки. Следующим циклам не нужно считать бэкенд
непроверяемым.
