## P1 — Стабильность/корректность

### P1-1: Ручное добавление персоны (watchlist по фото) было полностью сломано (PR #20)

При написании интеграционного теста на **полный** успешный путь
`POST /api/persons` (не только 503-деградацию без worker'а, которую уже
проверяли предыдущие циклы, а реальную вставку в БД — сетевой вызов к
worker'у подменён monkeypatch'ем `httpx.AsyncClient.post`, всё остальное
идёт по-настоящему) тест сразу упал:

```
asyncpg.exceptions.NotNullViolationError: null value in column "alert_on_detection"
```

Причина: raw SQL `INSERT INTO persons (...)` в `routers/persons.py` не
указывал `alert_on_detection`. У колонки был только Python-side ORM
default (`Boolean, default=False` в модели) — он применяется, когда
вставка идёт через SQLAlchemy ORM, но **не создаёт DB-level DEFAULT**, и
голый SQL-инсерт падал на NOT NULL constraint. Это означает, что фича
"ручное добавление известной персоны по фото" (явно требуется ТЗ, раздел
10) **не работала в проде вообще, ни разу** — просто не было теста,
который прогонял бы этот путь на настоящей БД (предыдущие четыре цикла
явно фиксировали в отчётах: worker недоступен в CI, поэтому create-путь
не тестировался, и на этом останавливались, не подменяя сетевой вызов
моком, чтобы проверить путь до конца).

Отдельно проверено, что тот же класс бага **не** затрагивает основной
конвейер детекции: `worker/worker.py` создаёт `FaceEvent` через ORM
(`FaceEvent(...)`), а не raw SQL — там Python-side default отрабатывает
штатно. Баг был локализован строго к ручному добавлению персон через API.

**Фикс:**
- `alert_on_detection=false` добавлен явно в INSERT;
- `server_default` добавлен в модель для всех аналогичных boolean-колонок
  с Python-side `default=` (`Person.alert_on_detection`,
  `FaceEvent.enhanced`/`is_known`, `Camera.enabled`,
  `RefreshToken.rotated`) — защита от того же класса бага в будущем на
  свежих инсталляциях (`create_all` теперь создаёт колонку с DB-level
  default);
- безусловный `ALTER TABLE ... ALTER COLUMN ... SET DEFAULT` добавлен в
  миграционный блок `main.py` — старое `ADD COLUMN IF NOT EXISTS ...
  DEFAULT false` оказалось no-op на уже развёрнутых БД (колонка уже
  существовала без DEFAULT), поэтому нужен отдельный безусловный шаг,
  чтобы починить и уже работающие инсталляции, не только свежие.

## P3 — Качество

### P3-1: Интеграционные тесты persons/search/reports/ws (PR #20)

Закрывает явную рекомендацию циклов 3–4. Четыре новых файла тестов:

- `tests/test_integration_persons.py` — RBAC (admin/operator), CRUD,
  merge с реассайном событий, gallery, enhance (постановка в очередь
  апскейла через Redis), создание персоны (503 при недоступном worker'е
  + **полный успешный путь** с моком сети + 422 при ошибке распознавания
  на стороне worker'а — этот путь и вскрыл P1-1 выше);
- `tests/test_integration_search.py` — auth, RBAC (admin/operator),
  деградация без worker'а, полный косинусный поиск по pgvector с моком
  сети (включая фильтр по `status`/similarity, JOIN на video_segments);
- `tests/test_integration_reports.py` — `?token=` auth (отсутствует
  → 422, невалиден → 401, роль `viewer` → 403 — репорты не используют
  Bearer-заголовок, отдельная ветка авторизации от остальных роутеров),
  CSV/XLSX для всех трёх видов отчётов (appearances/persons/cameras) на
  реальных данных;
- `tests/test_integration_ws.py` — auth на WebSocket (отсутствующий/
  невалидный токен → disconnect до `accept()`), доставка сообщений через
  настоящий Redis pub/sub для `/ws/faces` и `/ws/cameras` (не мок).

`tests/conftest.py` получил фикстуру `pg_conn` (sync psycopg2) для
сидинга persons/face_events/cameras напрямую, когда живого worker'а нет
(тот же compromise, что и раньше в проекте — CI не поднимает сервис
распознавания, слишком тяжёлые зависимости: OpenCV/InsightFace/ONNX).

Результат: **58.9% → 70.9%**, цель ТЗ (≥70% backend) достигнута.

## Рекомендации на следующие циклы (по приоритету)

1. **ONVIF-интеграция** (ТЗ 18.7) — единственный оставшийся
   содержательный функциональный пробел, отложен пять циклов подряд по
   одной и той же причине (нет реальной камеры в песочнице). Дальнейшее
   автоматическое откладывание без изменения условий не даёт прогресса —
   стоит решить на уровне заказчика: либо предоставить тестовую
   ONVIF-камеру/эмулятор (например, `onvif-simulator` в Docker) для
   следующей сессии, либо явно снять пункт с текущего цикла Tier-1 и
   перевести в roadmap.
2. **Удаление смерджённых веток** (19 штук) — `git push --delete`
   заблокирован правами git-прокси все пять циклов подряд, отдельного
   `delete_branch` в доступных GitHub MCP-инструментах нет. Это не
   решается изнутри сессии ни при каком количестве попыток — нужна ручная
   очистка либо расширение прав прокси/добавление MCP-инструмента для
   удаления веток на стороне оркестрации.
3. Поднять `--cov-fail-under` в CI с 55 до значения ближе к фактическому
   покрытию (сейчас 70.9%), чтобы порог CI не давал покрытию просесть
   обратно незамеченным — сейчас разрыв между полом (55%) и фактом (71%)
   в 16 п.п. слишком большой, чтобы ловить регресс.
4. При очередном общем проходе по ТЗ стоит целенаправленно искать баги
   того же класса, что P1-1: любой raw SQL (`text(...)`), который
   вставляет строки в таблицы с колонками, имеющими только ORM-side
   `default=` без `server_default` — грепом по `INSERT INTO` в
   `backend/app/routers/*.py` и `worker/*.py` и сверкой каждой колонки
   таблицы с текстом инсерта. В этом цикле проверен и починен только
   один такой инсерт (`persons`); гарантии, что это единственный,
   нет — просто это единственный, для которого нашёлся тест, доводящий
   путь до конца.
