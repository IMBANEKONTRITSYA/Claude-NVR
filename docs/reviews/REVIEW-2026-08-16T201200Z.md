## 3. Что доведено до end-to-end

### 3.1 §3 Импорт/экспорт конфигурации камер — [#87](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/87)

Функции не было вовсе: две сотни камер заводились по одной через форму,
а перенести конфигурацию с тестового стенда на боевой сервер было нечем
— RTSP-адреса лежат в БД зашифрованными.

`GET /api/cameras/export?format=csv|json` + `POST /api/cameras/import` +
вкладка «Импорт / экспорт» на странице камер. Три решения, за которыми
поведение, а не формат:

1. **Пароли в RTSP-URL по умолчанию вырезаны** (`rtsp://admin:***@…`).
   §14 требует хранить учётки только зашифрованными; файл, который
   монтажник кладёт в почту, не должен раздавать доступ ко всем камерам
   здания. Полная выгрузка — явным `include_secrets=1` и с записью в
   журнал аудита.
2. **Маскированный URL при импорте = «оставить сохранённый»**, иначе
   круг «выгрузил → поправил → загрузил» терял бы пароли всех камер.
3. **Всё или ничего**: файл с ошибкой хотя бы в одной строке не
   применяется целиком. Наполовину загруженная конфигурация на 200 камер
   хуже незагруженной.

Предел камер аналитики считается по итогу всего файла и блокирует только
импорт, который делает хуже: если предел уже превышен, файл, аналитики
не добавляющий, всё равно применяется — иначе конфигурацию нельзя было
бы починить тем же файлом.

### 3.2 §4 Мозаика 1/4/9/16 и цифровой зум — [#88](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/88)

**Найдено при сквозной проверке, а не в списке требований.** `LiveGrid`
рендерил **весь** список камер разом: на объекте из ста камер вкладка
поднимала сто HLS-плееров, каждый со своим буфером и соединением к
MediaMTX. Браузер вставал раньше сервера — то есть на целевом масштабе
страница live-просмотра не работала вовсе, при том что все её проверки
проходили.

Теперь на экране максимум 16 плиток, раскладка выбирается кнопками и
запоминается, остальные камеры — на страницах. Номер страницы
приводится к существующим при смене раскладки: страница 5 из 20 камер по
4 на экран после переключения на 16 становится 2-й, а не пустой стеной.

Цифровой зум — колесом до 8×, кадр тянется мышью, смещение ограничено
размером увеличенного кадра, зум двигает видео **вместе с рамками лиц**
одной трансформацией.

### 3.3 Первый JS-тестраннер в проекте

§21 перечисляет его в стеке; фактически логика интерфейса проверялась
только статическими проверками из `backend/tests`, которые видят текст
файла, а не поведение (carryover-пункт цикла 27). Добавлен **vitest**,
12 тестов на раскладку и зум, джоб `frontend` в CI гоняет их перед
сборкой.

## 6. Carryover

### Функциональные гэпы (по §22 — приоритет над остальным)

Порядок — как их стоит брать следующими циклами:

1. **§26 .deb-пакет + systemd + install-тест в CI.** Единственный
   production-режим по новой редакции, и в репозитории нет ни одного
   файла упаковки. Самый крупный гэп.
2. **§6 расписание детекции, запись только при движении, алерты e-mail и
   звуком** + **§11 настройки SMTP**. SMTP отсутствует во всём дереве, а
   его требуют сразу три раздела (§6 алерты, §8 авто-отправка отчётов,
   §11 уведомления) — разумно закрывать одним заходом.
3. **§4 PTZ-управление** (ONVIF PTZ: continuous move, stop, presets).
4. **§7 миниатюры кадров** в выдаче поиска по архиву.
5. **§8 шаблоны отчётов и авто-отправка по расписанию.**
6. **§16 автоконфигурация при первом запуске**: определить ресурсы →
   предложить пределы камер записи и analytics.
7. **§5 покадровый просмотр** в плеере архива.
8. **§12 ONVIF Profile G.**

### Хардкод числа камер (§22 «Запрещено»)

### Прежний carryover, оставшийся в силе

* **Полная цепочка аналитики одним замером** — нужна реальная ONNX-модель
  или целевое железо.
* **Поведение MediaMTX** — 12 циклов без Docker в песочнице; проверяется
  только чек-листом развёртывания.
* **`npm audit`**: 4 находки (react-router RSC, esbuild dev-server, два
  vite) — переоценены, неприменимы к production-сборке, фикс требует

* **GPU-провайдеры ONNX Runtime при конкурентных вызовах** — нужен
  реальный GPU.
* **Удаление смерджённых веток** — с цикла 26 включён auto-delete на
  стороне репозитория, ветки этого цикла удалились автоматически.
