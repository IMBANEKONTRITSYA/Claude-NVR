## Что доведено до end-to-end

### 1. §11 — зоны детекции не сохранялись почти ни для одной камеры ([#82](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/82))

`PUT /api/cameras/{id}/roi` по §11 («доступно только для камер в режиме
analytics») отвечает `400` на камеру `record_only`. Выпадающий список на
странице «Зоны детекции» при этом отдавал камеры **всех** режимов.

`record_only` — режим по умолчанию (§3). На объекте из 120 камер с двумя
аналитическими это **118 позиций списка, ведущих к отказу**, — и узнавал об
этом оператор только после того, как расставил точки полигона и нажал
«Сохранить». Список отфильтрован по режиму; при пустом списке страница
объясняет, что делать.

### 2. §8/§11 — пять мутирующих вызовов отказывали молча ([#82](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/82))

`req()` в `api.ts` бросает `Error` на любой `!res.ok`. Пять вызовов шли без
обработки:

| Место | Что видел оператор при отказе |
|---|---|
| ROI: сохранение зон | ничего — ни ошибки, ни подтверждения |
| Персона: переименование | ничего |
| Персона: слияние | ничего |
| **Персона: галочка watchlist** | галочка молча отскакивала — оператор считал, что Telegram-оповещение настроено |
| **Персона: заметки** | текст оставался в поле (`defaultValue`) и выглядел сохранённым |

Последние две строки — не отсутствие сообщения, а **расхождение картинки с
состоянием сервера**. Соседние обработчики в тех же файлах (`enhance`,
`remove`, удаление снимка, создание персоны) отказ обрабатывали — недосмотр,
не решение.

Регрессионная проверка написана **на класс**, а не на пять строк:
`test_ui_no_silent_failures.py` сканирует `frontend/src` на мутирующие вызовы
`api.*` вне `try/catch`.

### 3. §19 — профили описывали железо удалённой редакции ТЗ ([#84](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/84))

Carryover-пункт, не тронутый три цикла. Сначала проверено, работает ли
механика: **все 8 управляемых профилем ключей действительно читаются
воркером** — ни одного «пишется в settings и никем не используется».
Механика в порядке; сломано то, что видит администратор:

```
Экономный    — слабое железо (Intel N100), 4–8 камер
Стандартный  — Core i3 / Ryzen 3, 8–12 камер
Максимальный — Core i5+ / GPU, 12–16 камер
```

Это описание системы на 16 камер, где все они шли в аналитику. В Scale
Edition вводит в заблуждение дважды: числа читаются как относящиеся к 120
камерам записи (профиль касается только `analytics`, по умолчанию 2), а
«Core i5+ / GPU» — как несовместимость с целевым сервером (2× E5-2670 без
GPU, §23).

Подписи заменены описанием того, **что профиль делает**; добавлено
пояснение, которого не было нигде: профиль применяется только к слою
аналитики, запись от него не зависит (§19 дословно + §2).

**Числа внутри профилей намеренно НЕ пересчитаны** — см. «Чего не делал».

### Поиск по архиву — детали замера ([#83](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/83))

Новая группа `perf/bench.py --only archive` засевает боевой объём **по ТЗ**:
120 камер (§1) × 14 дней retention (§21) × сегменты по 5 минут (§20, нижняя
граница = больше строк = худший случай) = **483 840 сегментов, 73.6 МБ**,
плюс 100 000 событий лиц с 2 камер analytics (§6).

| Фильтр | Факт | План |
|---|---|---|
| без фильтров | 1.3 мс | Index Scan Backward |
| камера | 1.9 мс | Index Scan |
| камера + сутки | 1.4 мс | Index Scan |
| только даты | 1.0 мс | Index Scan Backward |
| тип события (редкий) | 25.6 мс | **Seq Scan** |
| персона (EXISTS по face_events) | 28.1 мс | Gather Merge |
| персона + камера + сутки | 1.2 мс | Nested Loop Semi Join |

**Норматив закрывается как достигнутый с замером**, запас ~178×.

**Индексы намеренно не добавлены.** Составной `(camera_id, started_at DESC)`
убирает Seq Scan на фильтре по `event_type`, но платить за него пришлось бы
на **каждой вставке сегмента** — 120 камер × 288 сегментов в сутки ≈ 34 560
вставок в день — ради запроса, укладывающегося в норматив с двумя порядками
запаса. Это оптимизация без выигрыша с постоянной ценой в слое записи,
которому §20 отводит 2–4 ядра из 64. Факт `Seq Scan` печатается бенчмарком,
а не скрыт: вырастет объём — следующий цикл увидит первым прогоном.

## Чего я намеренно не делал

**Не пересчитывал числа внутри профилей производительности.** Вывести их
можно только из фактического инференса на целевом CPU без AVX2. Бенчмарк в
песочнице гоняет **синтетическую** сеть на процессоре с AVX2 — задание прямо
запрещает опираться на синтетические модели. Подогнать значения «под Xeon»
по таким числам значило бы закрепить выдумку в коде и выдать её за расчёт.
Ограничение записано в docstring `profiles.py` и в раздел 3
`DEPLOY_CHECKLIST.md` отдельным пунктом.

**Не добавлял индексы под поиск по архиву** — обоснование выше.

## Carryover на цикл 28

**Функциональное (приоритет §30):**

1. **Метод проверки важнее списка гэпов.** Цикл 26 объявил §3-13 закрытыми
   по чтению кода; запуск живого приложения нашёл 6 отказов в двух функциях.
   Следующему циклу начинать так же — **поднять приложение и дёрнуть
   функции**, а не перечитывать роутеры. Скрипт сквозной проверки не
   коммитился (он одноразовый и завязан на тестовые учётки); если делать
   его постоянным — это отдельная задача, см. п. 4.
2. **Норматив «апскейл ≤ 200 мс/лицо» (§26)** — следующий кандидат на
   замер: он измерим в песочнице (CodeFormer CPU-light либо фактический
   fallback «бикубический + unsharp», §28), но требует установки модели.
   Взять его первым и мерить **фактическую** реализацию, а не ту, что
   описана в §28.
3. **§23 NUMA-привязка** (`numactl`, камеры 1–60 на node 0, 61–120 на
   node 1) — написать и задокументировать можно, проверить только на
   сервере. Не тронуто четвёртый цикл.
4. **Фронтенд-тестраннера в проекте нет вовсе.** SPEC §16 называет
   «Тесты: pytest, Jest, locust» — Jest/vitest отсутствует после 27
   циклов. Поэтому регрессия на UI-отказы этого цикла написана
   сканером исходников в `backend/tests`, а не поведенческим тестом:
   сканер ловит класс, но не проверяет, что тост действительно
   показывается. Завести vitest + @testing-library/react — отдельная
   задача с риском для `npm ci --legacy-peer-deps`, оценить в спокойном
   цикле.
5. **Мультипроцессность камер-воркеров** — **сначала замерить**. Без
   изменений с цикла 25.

**Инфраструктура и качество:**

7. **Изоляция тестов по БД.** Параллельный прогон по одной БД даёт сотни

## Методологические заметки

### Сработало

**Поднять приложение и дёрнуть функции, а не читать код.** Весь
функциональный результат цикла — отсюда. 26 циклов чтения кода и юнит-тестов
не нашли ни ROI-фильтр, ни пять молчаливых отказов, потому что **бэкенд во
всех шести случаях отвечает правильно**, и ни один backend-тест не мог их
увидеть в принципе. Дешёвый приём: ~150 строк на `httpx`, 36 проверок, 3
минуты работы.

**Сначала спросить «а работает ли механика вообще».** Прежде чем править
профили, я проверил, что все 8 ключей действительно читаются воркером.
Оказалось — читаются, и это сузило работу с «переписать профили» до
«исправить то, что видит администратор». Обратный исход (ключ пишется, но
никем не используется) был бы куда более серьёзной находкой, и проверка
стоила одного `grep`.

**Мерить норматив против плана, а не только против секунд.** Приём цикла 26
переиспользован: рядом с миллисекундами бенчмарк печатает признак `Seq Scan`.
Норматив по архиву достигнут честно, но один фильтр идёт полным перебором —
факт зафиксирован, а не утоплен в зелёной цифре.

**Верификация откатом по каждому сценарию отдельно.** Для теста на дрейф
бенчмарка (3 способа разойтись с моделью) откатывался каждый способ
отдельно, и каждый раз падала **своя** проверка, а остальные оставались
зелёными. Это сильнее, чем «тест падает при откате»: подтверждает, что три
проверки покрывают три разных случая, а не дублируют друг друга.

### Ошибки этого цикла

**Запустил pytest по БД, которую занимал другой прогон, и получил 164
ошибки на здоровом дереве.** Полминуты паники, что смерджённый PR что-то
сломал. Мораль: перед «регрессия!» проверить, чист ли стенд. Заодно это
испортило чистоту охоты за мерцающим тестом — см. выше.

**Первая версия сквозной проверки дала 11 ложных «гэпов»** — я слал JSON
туда, где ждут query-параметры, multipart и токен в query. Полезный побочный
эффект: 422 от FastAPI сразу показывает нужную форму запроса, и вторая
версия дала 34/36. Но выводы по первой версии были бы полностью ложными —
**перед тем как назвать что-то гэпом, убедиться, что зовёшь правильно**.
