## Конкурентный запуск — два экземпляра сессии на одной ветке одновременно

**Это главная находка цикла**, важнее конкретных фиксов.

Порядок событий этой сессии:
1. При старте (`git log` на `claude/pensive-brown-28588t`) последним
   коммитом уже был `bc1fce1` — PR #27 (`redact ?token= from access logs`),
   **смерджен до старта этой сессии**, но ещё не задокументированный в
   `REVIEW_LOG.md` (последняя запись на тот момент — цикл 7, PR #25-26).
2. Эта сессия обнаружила PR #28 открытым как **draft** с уже зелёным CI
   (создан в `12:48:57Z`), убрала draft и вызвала merge — GitHub API вернул
   `{"merged": true}`.
3. Эта сессия открыла и смерджила PR #29 (P2-фиксы, уникальная работа).
4. При синхронизации ветки после мерджа #29 в истории обнаружился коммит
   `e3ac71e docs(review): add report 2026-08-04T142453Z` — **этого коммита
   эта сессия не делала**. Отчёт в нём (`REVIEW-2026-08-04T142453Z.md`)
   подробно описывает работу над PR #27 и #28 от первого лица как
   «эта сессия», включая специфичные детали (проверка живым браузером
   Playwright с `page.route()`-моками для кнопки автообнаружения ONVIF),
   которые эта сессия не выполняла. Строка в `REVIEW_LOG.md` для этого
   цикла также добавлена не этой сессией.

Вывод: помимо этой сессии, на branch `claude/pensive-brown-28588t`
одновременно работала **как минимум ещё одна** независимая автоматическая
сессия того же расписания — вероятно, запущенная тем же cron/scheduler
дважды (или сессия из предыдущего срабатывания расписания ещё не
завершилась, когда стартовала эта). Она самостоятельно смерджила PR #27,
подготовила/проверила PR #28 (включая live-browser проверку, которую эта
сессия не проводила) и написала отчёт о цикле «8» независимо от того, что
делала эта сессия — при этом факт merge PR #28 (кто именно нажал merge)
неоднозначен: GitHub API этой сессии сообщил об успехе, но конкурентная
сессия тоже описывает мердж от своего имени с деталями, которые не
подделаешь постфактум простым чтением уже смерджённого PR.

Практических потерь в этот раз не было — PR #27/#28 не задублировались
(смерджены по одному разу каждый), а работа этой сессии (PR #29) не
пересекалась по файлам с тем, что делала другая сессия. Но это **везение,
а не гарантия**: два независимых экземпляра, одновременно создающие ветки
`fix/*` от одного и того же base и мержащие их в один и тот же целевой
branch, рано или поздно столкнутся конфликтом мерджа, дублирующим PR по
одной и той же проблеме или гонкой при одновременном `git push --delete`/
`merge`. Рекомендация ниже (раздел «Рекомендации», пункт 1) — приоритет
№1 на следующий цикл/на сторону оркестрации.

## P2 — Раздел 18 ТЗ (SPEC): полный пересмотр, не проводился с цикла 3

Отдельный research-агент прошёлся по всем пунктам 18.1–18.9 плюс смежным
(docker-compose лимиты, индексы БД, connection pooling) с конкретными
file:line. Итог: 6 из 9 пунктов раздела 18 полностью реализованы (18.1
двухпоточность, 18.3 адаптивная частота детекции, 18.4 префильтр движения
MOG2, 18.5 лёгкие модели, 18.9 профили производительности — все
подтверждены с точным указанием кода), 18.7 закрыт в этом/прошлом цикле
(PR #28). Найдено 3 частичных пробела, все закрыты в PR #29 (см. ниже),
кроме 18.2, требующего реального GPU:

### P2-1: 18.8 — запись поддерживала только фиксированный CRF 23, без битрейта и I-frame-only

ТЗ 18.8 явно требует настраиваемый битрейт и опцию «только ключевые
кадры», ни того ни другого не было. **Фикс (PR #29):** новые настройки
`record_bitrate` (0 = CRF/авто, >0 = потолок в кбит/с) и
`record_iframe_only` (GOP=1, без B-кадров), сборка ffmpeg-аргументов
вынесена в чистый `worker/record_encode.py` (тестируется в CI без
cv2/insightface, тот же приём, что `backoff.py`/`onvif_client.py`).

### P2-2: 18.6 — апскейлер не понижал приоритет процесса

`worker.py` уже вызывал `os.nice(10)` для транскода сегментов и
рекластеризации (ТЗ 18.6: «все фоновые задачи выполняются с низким
приоритетом»), но отдельный сервис `upscaler` — нет, хотя апскейл прямо
назван в ТЗ как одна из таких задач. **Фикс (PR #29):** `os.nice(10)` в
начале `upscaler/main()`.

### P2-3 (смежное, не из раздела 18 напрямую): пул соединений БД не был явно засайзен

И backend (`create_async_engine`), и worker (`create_engine`) работали на
дефолтном пуле SQLAlchemy (`pool_size=5, max_overflow=10`) — маловато под
целевую нагрузку ТЗ (до 16 камер, каждая с отдельным потоком и
короткоживущими сессиями). Признаков реального исчерпания пула не найдено
(весь доступ к БД короткоживущий, по-кадрово), фикс превентивный.
**Фикс (PR #29):** явные `pool_size=10/max_overflow=20` (backend),
`pool_size=20/max_overflow=10` (worker).

### Не входит в этот цикл: 18.2 — аппаратное ускорение декодирования

`detect_providers()` (`worker.py`) уже автоопределяет провайдер
ONNX-инференса (CUDA→DirectML→OpenVINO→CPU), но декодирование видео
(`cv2.VideoCapture`, republish-`ffmpeg`) нигде не использует GPU
hwaccel-флаги (QuickSync/NVDEC/VCE). Реальный пробел ТЗ, но корректность
`-hwaccel`-флагов ffmpeg нельзя содержательно проверить без реального GPU
в песочнице — та же логика, по которой предыдущие циклы откладывали
ONVIF-автообнаружение до появления протокольной части, тестируемой без
камеры. Оставлено на цикл с доступом к GPU-железу.

### 18.5 — расхождение в названии моделей (не заведено как проблема)

ТЗ называет YOLOv8n-face/CenterFace/UltraFace/MobileFaceNet, код использует
InsightFace buffalo_s/buffalo_l (лёгкая/тяжёлая, переключается в
настройках). Функционально эквивалентно требованию (лёгкая модель для
слабого железа, тяжёлая для мощного, настраивается), расхождение только в
названии конкретных архитектур — не стоит правки без измеренного
accuracy/CPU-компромисса на реальных данных.

1. **Конкурентный запуск сессий на одной ветке — приоритет №1.** Эта

   «циклом 8», обе описывают работу над одинаковыми/пересекающимися PR от
   первого лица). Пока это не привело к потере данных только по
   везению — сторону оркестрации стоит проверить: не запускается ли
   расписание чаще, чем предыдущий запуск успевает завершиться, и не
   стоит ли добавить блокировку (lock-файл в репозитории, GitHub
   Deployment lock, или проверка «есть ли уже открытый PR с меткой
   auto-fix за последние N минут» перед стартом нового цикла).
2. **Удаление смерджённых веток** — девятый цикл подряд 403 от прокси
   песочницы; решение только на стороне оркестрации.
3. **18.2 GPU hwaccel декодирования видео** — нужен цикл с реальным
   GPU-железом для содержательной проверки.
4. **Docker daemon недоступен четвёртый цикл подряд** — если не разовая
   случайность, стоит задокументировать `postgresql-16-pgvector` +
   системный `redis-server` как официальный fallback (уже трижды сработал
   эквивалентно docker-compose).
