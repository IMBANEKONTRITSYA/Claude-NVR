## ⚠️ Обнаружен конкурентный запуск сессий (циклы 9-10)
Цикл 9 нашёл прямые доказательства минимум двух независимых автоматических
сессий, работавших на `claude/pensive-brown-28588t` **одновременно** в одном
временном окне — обе датировали себя «циклом 8», обе описывают работу над
пересекающимися PR (#27/#28) от первого лица с деталями, которые не
подделать постфактум. Цикл 10 не нашёл новых прямых улик, но стартовал с
уже открытым и готовым (не самим им созданным) PR #29 — состояние,
согласующееся с тем же паттерном. Цикл 11 не нашёл новых улик (чистый
старт, чистый финиш — см. `REVIEW-2026-08-04T182309Z.md`), но это не
опровергает риск: находка остаётся вероятностной, зависит от того,
пересеклись ли по времени два расписания в конкретном окне. Подробности —
раздел «Конкурентный запуск» в `REVIEW-2026-08-04T161845Z.md` (полное
описание), `REVIEW-2026-08-04T163032Z.md` (подтверждение) и
`REVIEW-2026-08-04T182309Z.md`/`REVIEW-2026-08-04T204410Z.md` (циклы 11-12,
чистые, риск не снят). Цикл 13 тоже не нашёл новых улик (см. его отчёт) —
пять циклов подряд без дублирующих PR или конфликтов мерджа. Это везение,
не гарантия; **приоритет №1 для стороны оркестрации остаётся без
изменений.**

## Известные пробелы, перенесённые в следующие циклы
(из REVIEW-2026-08-05T023618Z — актуально до следующего аудита)
- **Конкурентный запуск сессий на одной ветке** — см. предупреждение выше, приоритет №1, чинится только на стороне оркестрации расписания; без новых находок 6 циклов подряд (10-15)
- Разночтение назначенной ветки харнесса vs фактической ветки с кодом на origin — устойчивый паттерн все 15 циклов, стоит проверить на стороне оркестрации сессий
- Удаление смерджённых веток `fix/*`/`docs/*`/`feat/*`/`test/*` — `git push --delete` получает HTTP 403 от прокси песочницы 15 циклов подряд; отдельного `delete_branch` в доступных GitHub MCP-инструментах тоже нет; нужна ручная очистка или расширение прав на стороне оркестрации (циклы 7-15 не повторяют попытку сверх однократной проверки за цикл, см. рекомендацию цикла 6)
- **TOCTOU-гонка дублей `Person`** в `find_or_create_person` (worker.py, найдено циклом 15): SELECT ближайшего центроида → сравнение с порогом → INSERT без блокировки — две камеры, видящие одного неизвестного человека в одном узком окне, могут создать два разных `Person` для одного физического человека. Нужен отдельный цикл с архитектурным решением (advisory lock/мьютекс-таблица/смирение с ручной дедупликацией через `merge_persons`), не однострочный фикс.
- **Отсутствие backoff у auto-restart `ffmpeg`-republish** (worker.py, найдено циклом 15): проверяется на каждой итерации цикла кадров, не throttled — риск fork/connect-storm при недоступном основном RTSP-потоке. Нужен небольшой рефакторинг структуры `camera_worker()` (отдельная переменная retry-attempt для republish).
- **Проверка конкурентного доступа к общему `FACE_APP`** (insightface) из до 16 нитей `camera_worker()` без блокировки — не проверяемо по исходному коду одному (зависит от внутренностей `insightface`/`onnxruntime`), нужен цикл с реальным GPU + нагрузкой 16 камер; объединить с пунктом ниже.
- `npm audit` (frontend): react-router RSC Mode CSRF bypass (GHSA-qwww-vcr4-c8h2), esbuild dev-server CVE, и с цикла 13 — две записи для `vite` (`GHSA-v6wh-96g9-6wx3` NTLMv2-хэш через UNC-путь, `GHSA-fx2h-pf6j-xcff` обход `server.fs.deny`, обе Windows/dev-server-only) — все оценены как неприменимые к фактическому использованию приложения (классический `BrowserRouter`, без RSC; production-сборка не запускает dev-сервер), сознательно не тронуты — фикс требует `npm audit fix --force` с мажорным бампом vite/react-router, breaking change. Переоценить при следующем значимом обновлении зависимостей фронтенда — без изменений с цикла 13 (переоценено циклами 14-15, те же 4 находки).
- ТЗ 18.2 (аппаратное ускорение — и инференс, и декодирование) реализовано полностью на уровне кода с цикла 11, но ни разу не проверялось на реальном GPU за все 15 циклов (песочница без GPU) — нужен цикл с реальным железом для содержательной проверки
- Docker daemon недоступен десятый цикл подряд (циклы 6-15); Postgres+pgvector+Redis через `postgresql-16-pgvector`+`redis-server` (либо, для воркера, отдельная установка полного `requirements.txt` вручную — см. цикл 15) в песочнице остаётся официальным fallback для циклов, где БД/тяжёлые зависимости нужны
- SPEC 18 (весь раздел «Оптимизация для маломощного оборудования») закрыт полностью на уровне кода — следующим циклам не нужно возвращаться к нему за новыми пробелами, только за подтверждением на реальном железе (18.2, см. выше)
- **Полноценный целевой P0/P1-проход бэкенда** выполнен циклом 15 (впервые с цикла 12) — расхождений с матрицей прав не найдено. Следующий полный проход можно отложить на несколько циклов; точечный recheck свежеизменённого кода (как в циклах 13-14) остаётся основным режимом между полными проходами. Отдельный полный проход **воркера** по 24/7-стабильности выполнен впервые с цикла 1 этим же циклом (нашёл обе находки P1 выше и утечку нитей/детект зависших потоков, см. таблицу) — стоит держать в уме, что воркер тоже нуждается в периодическом полном проходе, не только бэкенд.
- SPEC §14 «нагрузочное тестирование на 16 камер» закрыто циклом 13 на уровне API-слоя backend'а (`loadtest/`), с цикла 14 доступно и из CI как необязательный `workflow_dispatch`-джоб — но по-прежнему не покрывает реальную RTSP-декодировку/инференс воркера под нагрузкой 16 потоков (нужны физические камеры/эмулятор + GPU, которых нет в песочнице); объединено с carryover-пунктом ТЗ 18.2 выше
- **Общий урок цикла 15**: детект зависших потоков (ТЗ 12) и утечка нитей ONVIF — оба найдены не построчным чтением на предмет конкретной уязвимости, а вопросом «что произойдёт, если этот код никогда не завершится/никогда не вызовет соседнюю функцию успешно» applied к каждой нити/подключению в воркере. Этот вид вопроса стоит держать в чек-листе для будущих проходов по concurrency-коду отдельно от построчного поиска инъекций/RBAC-пробелов, которые ловятся другим способом чтения.
