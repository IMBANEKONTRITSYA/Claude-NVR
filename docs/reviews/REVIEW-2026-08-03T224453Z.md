## P0 — Безопасность

### P0-1: Реальные, не пропатченные CVE в запиненных зависимостях (PR #8)
`pip-audit`/`npm audit` не были подключены к CI вообще — до этого PR никто
не проверял уязвимости автоматически (ТЗ 13: "регулярное обновление
зависимостей — автоматическая проверка уязвимостей"). Первый же локальный
прогон нашёл реальные, действующие на момент цикла уязвимости:

- **python-jose 3.3.0** — алгоритмическая путаница JWT (PYSEC-2024-232/233,
  PYSEC-2025-185) → **3.5.0**.
- **python-multipart 0.0.9** — несколько CVE парсинга form-data → **0.0.32**.
- **cryptography 43.0.1** — несколько CVE вплоть до CVE-2026-69248/69249 →
  **50.0.0**.
- **starlette 0.38.6** (транзитивно через fastapi) — часть CVE пропатчена
  только в ветке 1.x, 0.x-ветка не поддерживается — потребовало поднять
  **fastapi 0.115.0 → 0.141.1** в backend и worker.
- **frontend: react-router-dom 6.26.2 → 7.18.2** — open-redirect
  (GHSA-wrjc-x8rr-h8h6) во всём диапазоне 6.0–7.17.0.
- **frontend: postcss** — path traversal (high), через `npm audit fix`.

Мажорный апгрейд starlette сломал `test_routes.py` (новая версия оборачивает
под-маршруты `include_router()` в `_IncludedRouter` вместо плоского списка) —
поймано локальным прогоном тестов до пуша, тест переписан на рекурсивный
обход. `ecdsa` (транзитивная зависимость python-jose, тайминговая атака
Minerva, апстрим не выпускает фикс) и две находки frontend
(esbuild/vite — только dev-сервер; react-router RSC-mode — проект не
использует React Server Components) задокументированы и осознанно оставлены
как неприменимые к продакшен-развёртыванию, не подавлены молча.

Добавлена CI-джоба `dependency-audit`: pip-audit блокирующий для backend и
worker (без установки тяжёлых ML-зависимостей — резолвит прямо из
requirements.txt), npm audit — информационный (`continue-on-error`).

### P0-2: Access-токен жил 12 часов без возможности отозвать (PR #11)
Крупнейший пробел, отмеченный в прошлом цикле: ТЗ 13 требует "JWT-токены с
refresh-механизмом", а access-токен жил 12 часов, отозвать его на сервере
было нельзя — удалённый пользователь сохранял доступ до истечения токена.

**Фикс:** `ACCESS_TOKEN_EXPIRE_MINUTES` 12ч → 30мин (WS/медиа проверяют токен
только при подключении — уже открытые стримы не рвутся). Новая таблица
`refresh_tokens` (хранится только sha256-хэш, не сам секрет).
`POST /api/auth/refresh` ротирует токен, `POST /api/auth/logout` отзывает
один, `POST /api/auth/change-password` отзывает все (смена пароля = сигнал
компрометации). Детекция кражи: повторное предъявление уже потраченного
ротацией токена отзывает вообще все токены пользователя.

Тест `test_logout_revokes_single_token` поймал реальный баг до мерджа:
изначальная реализация не отличала "отозван logout'ом" от "отозван
ротацией" — из-за чего выход из одной вкладки браузера обрушивал все сессии
пользователя на всех устройствах. Добавлено поле `rotated`, различающее эти
два случая.

## P1 — Стабильность 24/7

### P1-1: Не было автоматического бэкапа PostgreSQL (PR #10)
ТЗ 12 требует ежедневный автобэкап, ручной запуск, документированное
восстановление — ничего из этого не было. Новый сервис `backup`
(`postgres:16-alpine` — та же версия `pg_dump`, что и сервер, встроенный
busybox cron, без отдельного образа): расписание `BACKUP_SCHEDULE`
(по умолчанию 03:00 ежедневно), `pg_dump --clean --if-exists | gzip`,
ротация по `BACKUP_RETENTION_DAYS`. Ручной запуск —
`docker compose exec backup /backup/run.sh` или `scripts\backup_now.bat`.
`docs/BACKUP.md` — хранение на отдельном диске/сетевом хранилище,
восстановление. Осознанно не давали backend доступ к Docker-сокету ради
REST-триггера — несоразмерное расширение поверхности атаки ради редкого
административного действия.

## Не исправлено в этом цикле — и почему

1. **TLS/HTTPS не настроен по умолчанию** (ТЗ 13). Осознанный компромисс
   для однокомпьютерного Windows-развёртывания — требует решения о
   self-signed сертификате (влияет на UX первого запуска, браузерные
   предупреждения), не менял без него, как и в прошлом цикле.
2. **Парольная политика (сложность/срок действия) и авто-logout по
   неактивности** (ТЗ 13) — не входили в объём PR #11, требуют отдельной
   фронтенд-логики (таймер бездействия) и, возможно, UX-решения о
   принудительной смене пароля.
3. **P2 (раздел 18 ТЗ) не аудировался в этом цикле** — фокус был на
   оставшихся P0/P1/P3 пробелах по прямому указанию порядка приоритетов.
4. **Документация (INSTALL/USER_GUIDE/ADMIN_GUIDE/API_DOCS/ARCHITECTURE/
   CHANGELOG)** всё ещё отсутствует, кроме README и нового `docs/BACKUP.md`.
5. **Ветки `fix/*` не удалены после мерджа** — `git push --delete` получил
   HTTP 403 от прокси песочницы (то же ограничение окружения, что и в
   прошлом цикле, не архитектуры проекта). Отдельного GitHub MCP
   инструмента для удаления веток тоже нет. Затронуты: 6 веток из прошлого
   цикла (`fix/security-cors-lockdown`, `fix/security-insecure-default-secrets`,
   `fix/security-restrict-internal-service-ports`, `fix/security-rtsp-url-validation`,
   `fix/stability-rtsp-reconnect-backoff`, `fix/stability-worker-graceful-shutdown`)
   + 4 ветки этого цикла (`fix/security-dependency-audit-ci`,
   `fix/quality-pytest-coverage-ci`, `fix/stability-postgres-automated-backup`,
   `fix/security-jwt-refresh-token-rotation`). Требуют ручного удаления или
   сессии с полным доступом к git remote.
