## P0 — Безопасность

### P0-1: Публично известные секреты по умолчанию (PR #3)
`SECRET_KEY`, `RTSP_ENCRYPTION_KEY` и `ADMIN_PASSWORD` были захардкожены
одинаковыми значениями в `docker-compose.yml`, `.env.example` и
`config.py`. Любой, кто читал публичный репозиторий, знал их. Развёртывание
без ручного редактирования `.env` (например, `docker compose up` в обход
`start.bat`) работало с подделываемыми JWT и публично известным ключом
шифрования RTSP-учёток.

**Фикс:** `lifespan()` теперь отказывается стартовать (`RuntimeError`),
если `SECRET_KEY`/`RTSP_ENCRYPTION_KEY` остались значением по умолчанию.
`scripts/generate_env.ps1` + `start.bat` при первом запуске генерируют
случайные `SECRET_KEY`, валидный Fernet-ключ и пароль администратора в
`.env`, пароль печатается один раз в консоль.

### P0-2: Отсутствие валидации схемы RTSP-URL — SSRF/LFI (PR #4)
`CameraIn.rtsp_url`/`sub_rtsp_url` и `RtspTest.rtsp_url` принимали любую
строку. `POST /api/cameras/test` (только админ) передавал её напрямую в
`ffprobe -i <url>`; сохранённые URL позже открываются `ffmpeg`/OpenCV в
воркере. Протокольный слой ffmpeg понимает `file:`, `http:`, `concat:`,
`subprocess:` и т.д. — "RTSP-URL" от админа мог использоваться для SSRF по
внутренним сервисам/облачным метаданным или чтения локальных файлов через
`ffprobe`.

**Фикс:** общий pydantic-валидатор, требующий схему `rtsp://`/`rtsps://` и
хост. `sub_rtsp_url` сохранил семантику "пустая строка = очистить субпоток".

### P0-3: postgres/redis/mediamtx опубликованы на все интерфейсы (PR #7)
`docker-compose.yml` публиковал порты 5432 (postgres), 6379 (redis) и
8554/8888/8889 (mediamtx: RTSP/HLS/WebRTC) на `0.0.0.0`. Ни один из этих
сервисов не имеет собственной аутентификации:
- postgres — пароль по умолчанию `facewatch` (тот же класс проблемы, что
  P0-1);
- redis — вообще без пароля;
- **mediamtx — отдаёт видео с камер без какой-либо проверки доступа.**
  Любой в локальной сети, знающий/угадавший путь потока
  (`/hls/cam1/index.m3u8`), мог смотреть камеры живьём, вообще не заходя
  в FaceWatch. Это прямой обход авторизации для базовой функции "просмотр
  видео", хотя и найден по касательной при проверке RBAC отчётов.

Ни один из трёх сервисов не должен быть доступен снаружи хоста: backend/
worker/upscaler ходят к postgres/redis по внутренней docker-сети по имени
сервиса, worker публикует, а nginx проксирует HLS из mediamtx так же.

**Фикс:** все пять портов перевешены на `127.0.0.1` (локальная отладка
`psql`/`redis-cli`/VLC с той же машины по-прежнему работает). `backend`
(8000, свой JWT/RBAC) и `frontend` (8080, точка входа) не тронуты. Добавлен
регрессионный тест, парсящий `docker-compose.yml`.

## P1 — Стабильность 24/7

### P1-1: Нет экспоненциального бэкоффа RTSP-реконнекта + баг субпотока (PR #5)
Цикл переподключения ретраил `cv2.VideoCapture` на фиксированном таймере
2 секунды бесконечно (ТЗ явно требует экспоненциальную задержку) — камера,
недоступная часами, означала попытку подключения каждые 2 секунды без
остановки. Попутно найден реальный баг в том же блоке: реконнект открывал
`rtsp_url` (основной поток) вместо `analyze_url` (субпоток, если задан) —
после первого обрыва связи детекция для камер с двухпоточной схемой
(ТЗ 18.1) молча переезжала на анализ полноразмерного основного потока,
сводя оптимизацию на нет до перезапуска нити.

**Фикс:** `worker/backoff.py` — чистая `reconnect_delay(attempt)`
(2с→4с→8с…, потолок 60с), вынесена в отдельный модуль без cv2/insightface
для юнит-тестирования. Счётчик попыток сбрасывается при успешном чтении
кадра. Реконнект теперь открывает `analyze_url`.

### P1-2: Отсутствие graceful shutdown в воркере (PR #6)
Обработчиков сигналов не было вообще. `docker stop`/рестарт контейнера
шлёт SIGTERM и через 10с (по умолчанию) — SIGKILL, независимо от
состояния. Нити `camera_worker()` (daemon) убивались посреди
`cv2.VideoCapture.read()`: недописанные сегменты `VideoWriter` не
финализировались, процесс ffmpeg-репабликации мог оставаться "осиротевшим"
вместо `terminate()`.

**Фикс:** `worker/shutdown.py` (`shutdown_event` + обработчик SIGTERM/
SIGINT, тоже без тяжёлых зависимостей — юнит-тестируем). Цикл чтения кадров
проверяет флаг каждую итерацию (включая прерываемое ожидание во время
бэкоффа) и освобождает `cap`/`writer`/репабликацию перед выходом.
`manager()` выходит по тому же флагу и джойнит нити камер с **общим**
бюджетом 8с (не по 8с на камеру — иначе остановка 16 камер растянулась бы
на пару минут). `docker-compose.yml`: `worker.stop_grace_period: 20s`.

## Не исправлено автоматически в этом цикле — и почему

Ниже — реальные пробелы против SPEC.md, найденные при обзоре, но
сознательно оставленные вне этого цикла (риск/объём не позволяли сделать
их аккуратно и проверяемо в разумное время):

1. **Нет refresh-токенов / ротации JWT, нет server-side revocation
   (ТЗ 13).** Access-токен живёт 12 часов, refresh-эндпоинта нет.
   Эндпоинты с токеном в query (`reports`, `archive/file`,
   `system/prometheus`, `media`, `ws`) декодируют JWT напрямую и не
   проверяют, существует ли пользователь ещё в БД — удалённый пользователь
   сохраняет доступ до истечения токена. Требует новой таблицы
   refresh-токенов, эндпоинта, изменений на фронтенде (перехват 401 +
   обновление) — не помещается в объём одного PR этой сессии без риска
   сломать текущий auth-флоу непроверяемо. **Рекомендуется отдельным
   циклом с интеграционными тестами.**
2. **TLS/HTTPS не настроен по умолчанию** (ТЗ 13: "рекомендуется даже
   внутри локальной сети"). `frontend/nginx.conf` слушает на 80 без TLS.
   Для однокомпьютерного Windows-развёртывания это осознанный компромисс
   проекта — не менял без явного решения о self-signed сертификате
   (влияет на UX первого запуска, браузерные предупреждения).
3. **Нет автоматической проверки уязвимостей зависимостей** (`pip-audit`,
   `npm audit`, Dependabot) в CI.
4. **Нет автоматического ежедневного бэкапа PostgreSQL** (ТЗ 12) — ни
   cron-джобы, ни отдельного сервиса в `docker-compose.yml` не найдено.
5. **Покрытие тестами не измеряется** — нет `pytest-cov`/порога в CI,
   поэтому нельзя подтвердить целевые ≥70% (ТЗ 14).
6. Ветки `fix/*` не удалены после мерджа: `git push --delete` в этой
   песочнице получил HTTP 403 от прокси (ограничение окружения сессии, не
   репозитория/GitHub). PR замерджены, но пять веток
   (`fix/security-cors-lockdown` — с прошлой сессии,
   `fix/security-insecure-default-secrets`, `fix/security-rtsp-url-validation`,
   `fix/stability-rtsp-reconnect-backoff`, `fix/stability-worker-graceful-shutdown`,
   `fix/security-restrict-internal-service-ports`) остались в репозитории.
   Требуют ручного удаления или сессии с полным доступом к git remote.

## Рекомендации на следующие циклы (по приоритету)

1. **Refresh-токены + ротация + server-side revocation** — крупнейший
   оставшийся P0-пробел, требует отдельного цикла с бэкенд+фронтенд
   изменениями и интеграционными тестами auth-флоу.
2. **pip-audit / npm audit + Dependabot** в CI — дёшево, высокая отдача.
3. **Автоматический бэкап PostgreSQL** по расписанию (`pg_dump` + cron-
   контейнер или Windows Task Scheduler) с задокументированной процедурой
   восстановления (ТЗ 12).
4. **TLS по умолчанию** (self-signed сертификат, генерируемый при первом
   запуске аналогично секретам) — закрывает последний пункт ТЗ 13 "Защита
   данных".
5. **pytest-cov с порогом в CI**, чтобы подтверждать/удерживать ≥70%.
6. **Аудит P2** (раздел 18 SPEC.md целиком) — двухпоточность, H.265,
   ONVIF, автоопределение ускорителя, профили производительности.
7. **P3: документация** — INSTALL/USER_GUIDE/ADMIN_GUIDE/API_DOCS/
   ARCHITECTURE/CHANGELOG отсутствуют в корне, при том что ТЗ считает их
   обязательными для Tier-1.
8. Удалить смерджённые ветки `fix/*` (заблокировано правами git-прокси в
   этой сессии, не архитектурой проекта).
