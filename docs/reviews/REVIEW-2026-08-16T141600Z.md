## Что доведено до end-to-end

### 1. Экспорт фрагмента архива — [#80](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/80)

Единственный незакрытый гэп §3-13 по итогам цикла 25. Архив умел отдавать
только **файл сегмента целиком**: оператору, которому нужны две минуты
события, приходилось скачивать сегмент на 5–10 минут, а событие на стыке
двух сегментов — два файла, которые он склеивал вручную.

`GET /api/archive/export?camera_id&date_from&date_to` отдаёт один MP4 на
запрошенное окно поверх скольких угодно сегментов.

**Только remux** (`-c copy`) — §24 выносит перекодирование архива за рамки
версии. Отсюда единственное ограничение точности: вход ищется по ключевому
кадру **не позже** запрошенного времени, то есть фрагмент может начаться
на 1–2 с раньше, но никогда не позже. Для видеонаблюдения потерять начало
события хуже, чем получить лишние секунды до него; в интерфейсе это
написано рядом с кнопкой.

Три решения, которые легко сделать неправильно:

* **смещение считается внутри каждого сегмента, а не по склеенной шкале.**
  Склеенная шкала непрерывна, настенная — нет: после первой же дыры в
  записи (реконнект RTSP, перезапуск MediaMTX) смещение уезжает ровно на
  её длину, а на 10-секундном файле смещение 65 с не находится вовсе —
  кусок вышел бы пустым. Отдельный тест с 60-секундной дырой;
* **отбор сегментов идёт по пересечению с окном**, а не по «`started_at` в
  окне», как в списке сегментов: иначе терялся бы ровно тот сегмент, в
  котором лежит начало фрагмента, и экспорт молча начинался бы с середины;
* **сегмент, целиком попавший в окно, не режется**, а идёт в склейку как
  есть — на длинном фрагменте это экономит по одному проходу ffmpeg на
  каждый средний сегмент.

Границы: окно ≤ 60 минут и ≤ 64 сегментов; таймаут ffmpeg 300 с с `kill`;
временный каталог удаляется задачей ответа, то есть после отдачи файла;
пути проверяются на принадлежность `MEDIA_PATH` (список concat идёт с
`-safe 0`, собственной проверки путей ffmpeg не делает); файл, удалённый
ротацией между выборкой и сборкой, пропускается.

**Интерфейс:** блок «Экспорт фрагмента» на странице «Архив», границы
предзаполняются по выбранному сегменту. Значения берутся из ответа API как
есть и уходят обратно как есть, без преобразования часовых поясов: столбцы
`video_segments` наивные, и любой промежуточный `new Date()` сдвинул бы
окно на смещение пояса браузера.

**Аудит (§13):** операция пишется в журнал. Путь пишется **без** query
string намеренно — в ней лежит токен доступа.

## PERFORMANCE PASS (обязательная секция)

### Выбранный норматив цикла: §12 «поиск по фото ≤ 3–5 с на 100 000 лиц»

Задание требует каждый цикл брать **один** ещё не измеренный норматив из
carryover и мерить его. Взят §12 — единственный измеримый прямо в
песочнице. Замер и оказался находкой.

**Находка: production-запрос шёл мимо HNSW-индекса.**

`idx_face_events_embedding` (HNSW, `vector_cosine_ops`) создаётся при
старте приложения с самого начала. Запрос из `routers/search.py` его **не
использовал**: порядок был задан выражением-псевдонимом
(`ORDER BY similarity DESC`), а планировщик pgvector отдаёт индекс только
форме `ORDER BY <столбец> <=> <константа>`. План подтверждал
`Seq Scan on face_events`.

**Цифры до/после** — `perf/bench.py --only facesearch`, песочница
(Intel Xeon @2.80GHz, 4 ядра, AVX2 **есть**), Postgres 16 +
pgvector 0.6.0, база 100 000 эмбеддингов:

| Метрика | До | После | Дельта |
|---|---|---|---|
| время запроса, среднее | **517.6 мс** | **2.0 мс** | **−259×** |
| время запроса, p95 | 573.5 мс | 3.5 мс | −164× |
| план | `Seq Scan on face_events` | `Index Scan using idx_face_events_embedding` | — |
| строк возвращено (limit 100) | 100 | 100 | без изменений |

Сопутствующие замеры: засев 100k эмбеддингов — 57.1 с, построение
HNSW-индекса — 102.3 с (на целевом сервере будет заметно дольше, это
одноразовая операция при первом старте на непустой базе).

**Ловушка, найденная тем же замером.** HNSW отдаёт не более
`hnsw.ef_search` кандидатов, а дефолт pgvector (40) **меньше** дефолтного
`limit` эндпоинта (100). Первая версия правки молча возвращала 40
совпадений вместо 100 — оператор решил бы, что похожих больше нет.
Добавлен `SET LOCAL hnsw.ef_search` с двукратным запасом против `limit`.

**Что намеренно не переведено на индекс.** Суженный фильтрами поиск (по
датам/статусу) оставлен на точном полном проходе: индексный скан отдаёт
`ef_search` ближайших, фильтр применяется уже к ним, и на узком фильтре
выдача молча оказалась бы неполной. В pgvector 0.6.0 итеративного скана,
который это чинит, ещё нет. Полный проход стоит ~0.5 с и в норматив
укладывается — терять полноту ради этого нельзя.

## Дефекты инфраструктуры, найденные по дороге

**1. CI молча не проверял целую функцию ТЗ (#80).** Тесты экспорта
собирают и разбирают настоящие MP4 и потому пропускаются без ffmpeg
(`skipif` на `shutil.which`). На раннере GitHub ffmpeg нет: 20 тестов ушли
в skip, покрытие упало с 77.5% до 74.69%, джоба провалилась по порогу.
Опасен здесь не отказ, а сценарий без порога: прогон выглядел бы зелёным,
а функция §5 не проверялась бы вовсе. В джобу добавлена установка ffmpeg —
окружение CI приведено в соответствие с production-образом бэкенда, где
ffmpeg есть с самого начала (`backend/Dockerfile`).

**2. Ложно-зелёный тест аудита (#80).** Проверка «экспорт попал в журнал»
искала строку по пути и находила запись **предыдущего прогона** — то есть
проходила и при полностью выключенной записи экспорта в журнал. Поймано
верификацией откатом. Переписана на пользователя с уникальным именем;
записи файла снимаются за собой модульной фикстурой.

**3. Ложно-зелёный тест плана запроса (#81).** Проверка «поиск идёт через
индекс» EXPLAIN'ила **свою копию** запроса, а не production-запрос, и
оставалась зелёной при возврате к неиндексируемой форме. Тоже поймано
откатом. Запросы вынесены в константы модуля (`ANN_SEARCH_SQL` /
`EXACT_SEARCH_SQL`), тест переводит `:name` → `%(name)s` и EXPLAIN'ит
именно их — единственный источник правды.

Два ложно-зелёных теста за цикл, оба пойманы **только** верификацией
откатом и ни один — прогоном на здоровом дереве. Это второй цикл подряд
(цикл 25 нашёл один), и оба раза механизм один и тот же: **тест проверял
не то, что делает production-код, а то, что рядом с ним** (накопленную
строку журнала; копию SQL).

## Методологические заметки

### Сработало

**Начать с «что из §3-13 не работает», а не «где уязвимость».** Второй
цикл подряд это даёт весь результат: один гэп был, он и закрыт.

**Мерить норматив, а не подтверждать его.** §12 числился «есть код + есть
HNSW-индекс», и по коду всё выглядело правильно. Замер показал, что индекс
**ни разу не использовался**, — разница в 259 раз. Ни чтение кода, ни
проверка времени (517 мс укладывались в норматив 3–5 с!) этого бы не
дали: нужен был именно `EXPLAIN`. **Приём на будущее:** для любого
требования вида «≤ N секунд» смотреть не только время, но и план/профиль,
потому что норматив может выполняться «случайно», на запасе железа.

**Проверять сам production-объект, а не его копию.** Оба ложно-зелёных
теста цикла — про это. Хорошая привычка: если тест содержит копию
production-SQL, строки, конфига — вынести оригинал в константу и
импортировать, даже если ради этого приходится делать мелкий рефакторинг.

**Верификация откатом обязательна, а не желательна.** Оба ложно-зелёных
теста прошли на здоровом дереве и упали только под откатом. Прогон на
здоровом дереве в принципе не может отличить работающий тест от
бессмысленного.

### Не сработало / стоило дороже

**Синтетические данные для бенчмарка оказались вырожденными дважды.**
Первая версия засевала равномерно случайные векторы: в 512 измерениях они
почти ортогональны, порог 0.4 не прошла **ни одна** строка, и запрос
мерился на пустом результате — без сортировки, join'а и подзапроса, ради
которых его и мерят. Вторая версия ввела кластеры, но взяла разброс «на
глаз» (0.35) — шум полностью забил центроид (компоненты единичного
вектора в 512 измерениях имеют масштаб 1/√512 ≈ 0.044), схожесть вышла
0.12, и результат снова оказался пустым. Помогло только посчитать разброс
формулой `cos ≈ 1/√(1 + s²·dim)`. **Урок:** у синтетики для бенчмарка
обязательно проверять, что запрос **что-то возвращает** и что это «что-то»
похоже на боевое распределение; «0 строк» — не результат, а сломанный
замер.

**`pip install` в системный Python сломался о debian-пакет.**
`cryptography 41.0.7` установлен из apt и не удаляется pip'ом
(`RECORD file not found`). Правильный первый шаг любого будущего цикла —
сразу `python -m venv`, не пытаясь ставить requirements в системный
интерпретатор. Вместе с уроком цикла 25 (`python -m pytest`, а не
`pytest`) это два шага setup'а, которые стоит выполнять не задумываясь.

**Прогресс-лог бенчмарка ушёл в stdout и сломал разбор JSON.** `--json`
пишет результат в stdout, туда же печатался прогресс засева — файл
результата оказался невалидным JSON. Починено (прогресс в stderr), но
стоило одного 3-минутного прогона на 100k.

## Sandbox limitations

Postgres 16 + pgvector 0.6.0, Redis, nginx, ffmpeg 6.1.1 — всё через
`apt`, без демона Docker. Полный сьют бэкенда прогнан на настоящих
сервисах: **327 passed**, покрытие 78.1%.

Docker и GPU по-прежнему недоступны; GPU для базовой конфигурации по §23
**не требуется**.
