### Что сделано без изменения кода

**Закрыт (частично) carryover-пункт «конкурентный доступ к `FACE_APP`»**
(числился открытым в логах циклов 1–16 как «не проверяемо по исходному коду
одному, нужен цикл с реальным GPU + нагрузкой 16 камер»). В этом цикле
`insightface` был установлен в песочницу (`pip install --no-deps
insightface`, без тяжёлых ML-зависимостей — их не нужно ставить, чтобы
прочитать исходники) и прочитаны реализации обоих путей, которые
`camera_worker()` вызывает на общем `FACE_APP` из до 16 нитей одновременно:

- `ArcFaceONNX.get()`/`get_feat()` (распознавание, `arcface_onnx.py`) — не
  держит общего изменяемого состояния между вызовами: `blob`/`aimg`
  создаются локально на каждый вызов, `session.run()` — задокументированно
  потокобезопасный вызов ONNX Runtime для конкурентных инференсов на одной
  сессии (не изменяющих её). **Потокобезопасно.**
- `SCRFD.forward()`/`detect()` (детекция, `scrfd.py`) — держит
  `self.center_cache` (обычный `dict`), с классическим check-then-set без
  блокировки:
  ```python
  if key in self.center_cache:
      anchor_centers = self.center_cache[key]
  else:
      anchor_centers = ...  # чистая функция от key
      if len(self.center_cache) < 100:
          self.center_cache[key] = anchor_centers
  ```
  Гонка здесь реальна (GIL защищает только отдельные операции над `dict`,
  не составную последовательность), но **безобидна**: `anchor_centers` —
  чистая детерминированная функция от `key` (высота/ширина/страйд), поэтому
  два потока, одновременно промахнувшиеся мимо кэша по одному и тому же
  `key`, вычислят и запишут одинаковое значение. Худший случай — лишний
  повторный расчёт, не порча данных.

**Вывод:** на CPU-провайдере (`CPUExecutionProvider`, дефолт песочницы и
большинства текущих деплоев на N100) конкурентный вызов `FACE_APP.get()` из
нескольких нитей `camera_worker()` **корректен** — подтверждено чтением
реализации, а не только документацией ONNX Runtime. Не закрыто до конца:
поведение GPU-провайдеров (`CUDAExecutionProvider`,
OpenVINO/DirectML-эквиваленты в терминологии ТЗ) при конкурентных вызовах
на одной сессии/контексте по-прежнему не проверено — это вопрос
GPU-рантайма, а не кода проекта, и не читается из исходников `insightface`
(они одинаковы для всех провайдеров, разница — внутри `onnxruntime` и
драйверов). Также не измерялась *производительность* при конкуренции
(GIL + внутренняя многопоточность `onnxruntime` могут сериализовать
пропускную способность при росте числа камер) — это отдельный вопрос от
корректности, требует реальной нагрузки для содержательного ответа.

Изменений кода не потребовалось — вопрос был именно о безопасности
существующего кода, а не о его дефекте. Обновлён статус пункта в
`REVIEW_LOG.md` (см. ниже) с «не проверяемо» на «частично закрыто анализом
исходников; GPU-провайдеры и throughput под нагрузкой остаются открытыми».

  активности не найдено.
- **Разночтение назначенной ветки харнесса vs фактической ветки с кодом**
  — 17-й цикл подряд подтверждает паттерн: системная инструкция сессии
  назначала `claude/brave-johnson-78r2w6` (короткая история из одного
  коммита-плейсхолдера `"Create 1"`, идентичного корню `main`), тогда как
  `claude/pensive-brown-28588t`, названная в самом задании цикла, содержит
  полную историю всех 16 предыдущих циклов. Работа велась на
  `claude/pensive-brown-28588t`, как и во всех прошлых циклах. **Новое
  наблюдение этого цикла:** имя «неправильной» ветки меняется от цикла к
  циклу (`qf4jy1` → `78r2w6` и т.д.) — это не одна и та же зависшая ссылка,
  а свежее случайное имя на сессию, которое никогда не существует на
  `origin`. Похоже не на баг харнесса как таковой, а на то, что
  хранимый текст задания (промпт расписания) был написан один раз в момент
  создания расписания и с тех пор указывает статичное имя ветки, тогда как
  платформа выдаёт каждой новой сессии новое имя ветки-по-умолчанию,
  которое никогда не создаётся и не пушится — см. рекомендацию №2 ниже с

- **Удаление смерджённых веток** `fix/*` на `origin` — не проверялось в

- Docker daemon недоступен 12-й цикл подряд (циклы 6–17); тот же fallback

1. **Оркестрация сессий** (не код продукта) — без изменений к рекомендации

   подряд, тогда как харнесс каждый раз назначает новое, никогда не

   это осознанное поведение платформы, стоит либо синхронизировать
   хранимый промпт с фактическим именем сессии, либо явно документировать,
   что имя из промпта имеет приоритет, чтобы будущие циклы не тратили
   время на этот вопрос заново; (в) дать сессии право удалять смерджённые
   ветки на `origin` (сейчас HTTP 403 от прокси песочницы) либо взять эту
   уборку на себя вне сессий — список накопившихся `fix/*` веток растёт с
   цикла 12.

   будет 3 цикла без полного прохода — та же периодичность, что
   рекомендовал цикл 16).
