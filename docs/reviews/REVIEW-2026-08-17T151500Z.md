## Executive summary

Цикл сорвал план и правильно сделал. На третьем шаге пришёл репорт с
**боевого развёртывания**, и он обесценил половину таблицы «работает
end-to-end» из прошлых отчётов:

> все камеры горят как offline, со всех камер чёрный экран; когда я меняю
> режим на камере, она пишет online, но картинки с неё нету

Через двадцать минут — вторая половина репорта, со страницы «Мониторинг»:

> `MediaMTXError: GET /v3/paths/list -> HTTP 401: {"error":"authentication error"}`

**Слой записи никогда не работал на настоящем развёртывании.** MediaMTX не
пускал воркер в Control API, поэтому пути камер не заводились, MediaMTX не
тянул ни одну камеру, живой просмотр (§4) был чёрным на всей стене, архив
(§5) не наполнялся, а статусы потоков не читались — и все камеры навсегда
оставались `offline`.

Причина в конфигурации, которой не было: MediaMTX по умолчанию выдаёт
право `api` **только** пользователю с `ips: ['127.0.0.1', '::1']`, а
воркер живёт в отдельном контейнере. Секции `authInternalUsers` в
`mediamtx/mediamtx.yml` не было вовсе, значит действовал этот дефолт.

Три PR, все смерджены.

| PR | Что |
|---|---|
| [#101](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/101) | воркер получал 401 от Control API — §4 и §5 не работали целиком |
| [#102](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/102) | плитка стены объясняет, почему она чёрная |
| [#103](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/103) | §19 RTO измерен впервые за 33 цикла |

Главный вывод цикла — не про MediaMTX, а про то, **почему 34 цикла и
19 «зелёных» прогонов этого не видели**: раздел 4.

## 3. Что доведено до end-to-end

### 3.1 Слой записи: воркер не пускали в Control API — [#101](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/101)

**Три симптома, ни один из которых не указывает на причину.** Их стоит
выписать: следующий раз опознается по ним за минуту.

1. Пути камер не заводятся → MediaMTX не тянет ни одну камеру → §4 чёрный
   на **всех** камерах, §5 не наполняется.
2. Статусы потоков не читаются → воркер не пишет `Camera.status` → все
   камеры показывают `offline`. Это **значение по умолчанию** в БД, а не
   вердикт: никто их не проверял и не признавал мёртвыми.
3. Камера, переключённая в `analytics`, показывает `online` — нить
   аналитики открывает RTSP **напрямую**, мимо MediaMTX.

Третий пункт — ключ ко всей загадке. Он доказывает, что камера доступна,
учётка верна, сеть в порядке; недоступен только медиасервер. Пользователь
описал это как странность («меняю режим — пишет online, а картинки нет»),
а это был готовый диагноз.

**Замер, снявший вопрос.** MediaMTX v1.9.3 и v1.16.0, оба настоящих
бинарника, запросы с не-loopback адреса (эквивалент соседнего
контейнера):

| Конфигурация | Как | Ответ |
|---|---|---|
| `mediamtx.yml` репозитория | без пароля | `401 authentication error` |
| после починки | без пароля | `401` |
| после починки | `Authorization: Basic` | **200** |
| после починки | неверный пароль | `401` |
| после починки | `?user=&pass=` в query | `401` — Control API их не принимает |

Последняя строка стоила отдельной проверки: для HLS и WebRTC MediaMTX
query-параметры принимает, и предположение «значит, и для API» было бы
естественным и неверным.

**Починка.** Явная секция `authInternalUsers`: анонимное чтение для nginx,
пользователь `facewatch` с паролем для Control API из любой точки
внутренней сети, loopback-администратор для healthcheck. Право `publish`
не выдаётся никому — камеры MediaMTX тянет сам, публиковать в него
некому, а с этим правом любой из внутренней сети мог бы занять путь и
подменить поток. Учётка едет внутри `MEDIAMTX_API_URL` и уходит
заголовком `Authorization` **с первым же запросом**:
`HTTPBasicAuthHandler` ответил бы только после 401, то есть удвоил бы
каждый запрос синхронизации, а она идёт каждые 10 секунд.

**Три побочные находки того же PR.**

* **Пароль слоя записи показывался оператору.** Сообщение «нет связи с
  медиасервером» логировалось с `extra={"url": MEDIAMTX_API_URL}`, а
  адрес теперь несёт учётку. Строка доезжает до страницы «Мониторинг»,
  то есть пароль увидел бы любой, кому эта страница доступна. Вырезается
  (`redact_url`).
* **Образ был `bluenviron/mediamtx:latest`.** Рабочее развёртывание
  ломается от `docker compose pull`, без единого изменения в
  репозитории. Зафиксирован на `1.16.0`.
* **Синхронизация путей снова не идемпотентна.** На v1.16.0 нулевая
  длительность возвращается пустой строкой, а не `0s`, как на v1.9.3;
  `recordDeleteAfter: 0s` из-за этого считался изменившимся, и
  `sync_paths()` слала PATCH на все пути каждые 10 секунд. Это ровно тот
  дефект, который цикл 30 закрыл для v1.9.3 и который вернулся вместе с
  версией — и он же объясняет, зачем фиксировать тег.

**Сообщение об отказе теперь называет место починки.** Голое
«authentication error» видит оператор, и по нему не найти ни файла, ни
переменной. Текст 401 переписан: `authInternalUsers`, `action: api`,
`MEDIAMTX_API_URL`.

**Проверка end-to-end** — настоящий MediaMTX v1.16.0 с продовым
конфигом, обращения с не-loopback адреса, камера-двойник по RTSP:

```
sync_paths()      : {'added': 1, 'failed': 0}
идемпотентность   : {'added': 0, 'updated': 0, 'deleted': 0}
Camera.status     : 'online'
HLS index.m3u8    : 200, CODECS="avc1.42c01f", 1280x720, 15 fps
сегменты на диске : cam1_1786980771.mp4 (1 731 161 байт)
без пароля        : отказ, как и должно
```

### 3.2 Плитка стены объясняет, почему она чёрная — [#102](https://github.com/IMBANEKONTRITSYA/Claude-NVR/pull/102)

#101 починил причину; #102 делает следующий такой отказ читаемым **без
доступа к серверу**. Причину этого цикла нашли не на стене, а в карточке
«Слой записи» на другой странице — стена умела ровно один ответ, «Камера
недоступна», и под ним пряталось всё сразу.

Плейлист запрашивается **после** отказа воспроизведения (не заранее: на
здоровой стене из 16 камер это 16 лишних запросов без пользы), и по коду
ответа и объявленным кодекам плитка называет причину: 401/403 — истекла
сессия; 404 — путь не заведён слоем записи, и чёрными будут все камеры
сразу (подпись отказа Control API); 0 — медиасервер недоступен; 200 с
`CODECS="hvc1…"` в браузере без HEVC — H.265.

Ветка H.265 — не запас на будущее, см. раздел 6.

## 4. Находка цикла: почему 19 зелёных прогонов не видели сломанного §4

Это важнее самой поломки. Отчёты циклов 30–32 писали «§4 работает», «§5
работает end-to-end» — и были неправы не по невнимательности, а
системно.

### 4.1 Все проверки MediaMTX шли с loopback

Цикл 30 первым запустил настоящий MediaMTX и проверил Control API,
запись, HLS и remux. Цикл 32 замерил на нём же стоимость remux. Оба
прогона шли **с 127.0.0.1**, потому что и бенчмарк, и MediaMTX жили в
одном процессе-песочнице. С loopback дефолт MediaMTX пускает в API без
пароля — и оба цикла увидели зелёное там, где production красный.

Дефект был **не в коде, а в топологии**: единственное, что отличает
песочницу от развёртывания, — адрес, с которого приходит клиент. Ни один
тест этого не воспроизводил.

**Приём на будущее: спросить, с какого адреса придёт настоящий клиент.**
Если проверяемое взаимодействие в production идёт между контейнерами, а
в песочнице — внутри одного хоста, то loopback проверяет не ту
конфигурацию. В `verify`-скрипте этого цикла запросы принудительно
уходят с не-loopback адреса (`source_address` у `HTTPConnection`) — это
дёшево и ловит весь класс.

### 4.2 Healthcheck ходит с loopback и потому всегда зелёный

`docker-compose.yml` проверяет MediaMTX запросом
`wget http://localhost:9997/...` **изнутри контейнера**. Контейнер
здоров, статус зелёный, а воркер в это время не может сделать ни одного
вызова. Проверка, которая ходит не тем маршрутом, что рабочий трафик,
подтверждает работоспособность маршрута, которым никто не пользуется.

Закрыто не healthcheck'ом (`wget` в образе MediaMTX не умеет Basic
auth без внешних утилит), а тестом, который сверяет пароль сервиса
`mediamtx` с адресом воркера: рассогласование даёт ровно тот же 401, и
это единственная оставшаяся форма отказа.

### 4.3 «Независимость слоёв» односторонняя, и таблица гэпов это скрывала

§2 требует, чтобы отказ аналитики не влиял на запись, и это выполняется.
Обратное — отказ записи не влияет на аналитику — тоже формально
выполняется: нити аналитики работали. Но **для пользователя это выглядело
наоборот**: интерфейс показывал `online` только на аналитических камерах,
то есть слой, который должен был быть второстепенным, оказался
единственным источником признаков жизни. Строка «§2 работает» в таблице
гэпов была правдой, из которой нельзя было вывести состояние системы.

### 4.4 Что из этого следует для таблицы гэпов

Статус «работает end-to-end» отныне требует ответа на вопрос **«где
именно проверено»**, и колонка добавлена (раздел 2). Три уровня, и они
не равноценны:

1. тест на моках/конфиге — проверяет решение, а не поведение;
2. сквозной тест на настоящих Postgres/Redis/MediaMTX **в песочнице** —
   проверяет поведение в топологии песочницы;
3. проверка на развёртывании — единственное, что закрывает вопрос.

Все три предыдущих цикла ставили «работает» по уровню 2, читая его как
уровень 3.

## 5. Производительность

### 5.1 §19 «RTO ≤ 5 минут» — измерен впервые (`perf/bench_rto.py`)

Единственный числовой норматив ТЗ, к которому за 33 цикла ни разу не
подступались. Мерить его одним числом нельзя: RTO складывается из трёх
слагаемых с разными причинами роста.

    RTO = обнаружение + рестарт + прогрев

| Слагаемое | Значение | Откуда |
|---|---|---|
| Прогрев (старт до `/api/health` 200) | **1.52 с** медиана, 1.59 с худший из 5 | замерено |
| Рестарт супервизором | 5 с | `restart: unless-stopped` |
| Обнаружение **падения** процесса | ~0 с | супервизор видит выход |
| Обнаружение **зависания** | 90 с | healthcheck `interval: 30s` × `retries: 3` |

| Норматив | Факт | Дельта |
|---|---|---|
| §19 RTO ≤ 300 с (падение процесса) | **6.6 с** | запас 293 с |
| §19 RTO ≤ 300 с (зависание) | **96.6 с** | запас 203 с |

Норматив выполняется с большим запасом, и доминирует в нём **не код, а
интервал healthcheck**: прогрев занимает 1.6 % от худшего случая. Это
меняет приоритет — оптимизировать старт бэкенда ради RTO бессмысленно,
а вот `interval`/`retries` действительно определяют, сколько объект
простоит на зависшем сервисе.

Чего замер не покрывает: база песочницы пуста (на объекте миграции идут
по непустой схеме); не меряется, за сколько MediaMTX заново дотягивается
до 120 камер; Postgres и Redis считаются живыми.

### 5.2 Цепочка аналитики (сверка с прошлым циклом)

Полная цепочка `decode 720p → префильтр → детектор → эмбеддинг` на
реальной модели `buffalo_s`, группа `chain` из `perf/bench.py`:

Хост песочницы: Intel Xeon @ 2.80 GHz, 4 ядра, **AVX2 есть** — у целевого
E5-2670 его нет, поэтому числа завышены; это отмечает и сам бенчмарк.

| Этап | Этот цикл | Цикл 29 (после починки `det_size`) |
|---|---|---|
| decode 720p | 2.05 мс/кадр | — |
| префильтр MOG2 | 9.22 мс/кадр | — |
| детектор + эмбеддинг | 94.16 мс (p95 107.94) | — |
| **цепочка целиком** | **9.48 FPS/канал** | 8.39 FPS/канал |

Норматив §19 «детекция ≥ 5 FPS/канал» выполняется. Деградации нет:
+13 % к прошлому замеру, но сравнивать эти числа между собой честно
только с оговоркой — прошлое снято на артефакте CI, это на песочнице,
машины разные. Порог «деградация > 15 % → carryover P2» применим лишь к
парам замеров с одного раннера; здесь сравнение справочное.

### 5.3 Стоимость правок этого цикла

* **Basic-заголовок** на каждый вызов Control API — одна base64-строка на
  запрос; вызовов два на проход менеджера (~10 с). Неизмеримо.
* **Идемпотентность синхронизации восстановлена** — это не нейтральная
  правка, а возврат экономии: до неё на 120 камерах уходило 120 PATCH
  каждые 10 секунд, то есть **720 пишущих запросов в минуту** к Control
  API, круглосуточно. Теперь — ноль на неизменившемся списке.
* **Диагностика плитки** — один запрос плейлиста **на отказ**, не на
  показ. На здоровой стене нагрузка не меняется.

## 6. Что ещё не проверено и почему это следующий кандидат

**§1 допускает камеры с H.265, а HLS с H.265 браузеры не играют.** MediaMTX
отдаёт для такой камеры плейлист с `CODECS="hvc1.1.6.L93.90"` — снято с
работающего v1.16.0 в этом цикле, вместе с записью и статусом `online`.
Воспроизводит такой поток Safari; Chrome и Firefox — нет (в Chrome
поддержка зависит от платформы и аппаратного декодера).

Симптом при этом самый обманчивый из всех: **статус зелёный, архив
растёт, плитка чёрная**. Отличить от поломки цикла 34 можно ровно по
этому: там чёрными были все камеры **при красном статусе**.

#102 научил плитку это называть, но не решать. Решения три, и выбор — за
следующим циклом: транскод в H.264 только для просматриваемых камер
(дорого: без GPU это ~1 ядро на поток, зато запись не затрагивается);
показ субпотока, если он H.264; WebRTC вместо HLS (не помогает — H.265 в
WebRTC браузеры тоже не тянут). Ни один вариант нельзя проверить в
песочнице: нет ни H.265-камеры, ни браузера с HEVC.

## 8. Carryover

### Функциональные гэпы (по §22 — приоритет над остальным)

1. **§4 живой просмотр камер с H.265** — раздел 6. Поднялся на первое
   место: это единственный известный способ снова получить чёрную стену,
   и он ждёт ровно того объекта, где камеры настроены в H.265 (а §1
   называет H.265 типичной конфигурацией).
2. **§6 запись только при движении** — как фильтр постобработки, не
   трогая слой записи.
3. **§3 выгрузка конфигурации камер не переносит расписание детекции
   и ROI.** Уточнение этого цикла: теряется **и** `roi`, а не только
   расписание (`camera_config.FIELDS` не содержит ни того, ни другого).
   Заготовка решения: отсутствующий в строке ключ — «оставить прежнее»,
   присутствующий пустой — «очистить»; иначе файл, выгруженный до
   появления колонок, сотрёт настройки на всех камерах молча.
4. **§12 ONVIF Profile G.**
5. **§13 доступность 99.5 %** — единственный оставшийся неизмеренный
   норматив; требует наблюдения сутками, в песочнице не измерим.
   Кандидат на замер следующим циклом — **§4 «задержка live ≤ 3 с» в
   браузере**: серверная часть измерена циклом 31, браузерная нет, а
   Chromium в песочнице есть.
6. **§26 .deb + systemd + install-тест в CI.**

### Новое в carryover этим циклом

* **Приём: спросить, с какого адреса придёт настоящий клиент** (4.1).
  Если в production взаимодействие идёт между контейнерами, проверка с
  loopback проверяет не ту конфигурацию. Принудить исходный адрес дёшево:
  `HTTPConnection(host, source_address=(lan_ip, 0))`.
* **Приём: проверка, которая ходит не тем маршрутом, что рабочий
  трафик, ничего не подтверждает** (4.2). Healthcheck MediaMTX был
  зелёным весь период поломки.
* **Статус «работает end-to-end» требует указания уровня доказательства**
  (4.4) — колонка добавлена в таблицу гэпов.
* **Версии внешних образов фиксировать.** `latest` у MediaMTX дал бы
  (и, вероятно, дал) поломку рабочего развёртывания от `docker compose
  pull`. Остальные образы проверить: `postgres`, `redis`, `nginx` в
  `docker-compose.yml` — **не проверялись этим циклом**.
* **`perf/bench_rto.py` не подключён к CI**: джобе `perf` нужны
  сервис-контейнеры Postgres и Redis, которых у неё нет. Числа этого
  цикла — база для сравнения.
* **Статические репозиторные тесты скипаются вместе с Postgres.**
  Замечено в конце цикла: `test_record_layer_config.py` разбирает YAML и
  БД не касается вовсе, но при остановленном Postgres уходит в skip
  целиком (27 тестов трёх модулей разом) — общая фикстура `conftest.py`
  гасит всё. В CI Postgres есть, поэтому вреда пока нет; но если
  сервис-контейнер однажды не поднимется, джоба останется **зелёной**, а
  весь класс проверок «решение живёт в yml» молча не выполнится — ровно
  та поломка, которую этот цикл и разбирал. Развести guard: то, что не
  ходит в БД, не должно от неё зависеть.
* **Ответы MediaMTX сверять с той версией, что зафиксирована.**
  `recordDeleteAfter` вернулся как `''` вместо `0s` — форма значений
  меняется между выпусками, и двойник в тестах обязан повторять
  зафиксированную версию, иначе тест ложно-зелёный (так и было).

### Прежний carryover, оставшийся в силе

* **`recordPath` в `path_conf()` захардкожен `/media/segments/...`** и не
  читает `MEDIA_PATH` (цикл 30) — выстрелит при переходе на .deb (§26).
* **Хардкод `cameras=120` во фронтенде** (`Monitoring.tsx`,
  `StorageCalculator`) — замена есть рядом: `current.cameras_total` из
  `/api/system/autoconfig`.
* **Хардкод числа камер** (§22 «Запрещено»): `routers/system.py:308`,
  `profiles.py`, `loadtest/`, `test_loadtest_scale.py`,
  `frontend/src/api.ts`, `README.md`.
* **Локальную базу песочницы под проверки изоляции пересоздавать**
  (`DROP DATABASE` + `CREATE` + `CREATE EXTENSION vector`), а не чистить
  точечными UPDATE.
* **Сьюты бэкенда и воркера — только по очереди** на одной базе.
* **Проба `idle in transaction` слишком широкая** — сузить по
  `application_name`.
* **Гонять воркер с `REDIS_URL=redis://localhost:6379/0`** — дефолт
  указывает на docker-имя.
* **Разбор LL-HLS плейлиста**: `#EXT-X-PART` и `#EXTINF` описывают одно и
  то же медиа, суммировать оба нельзя.
* **`THUMB_CONCURRENCY = 4` не подобран под железо** — доля от
  `os.cpu_count()`.
* **CSV выгружается без BOM** — Excel под Windows читает кириллицу как
  cp1251.
* **Группа `chain` и `perf/bench_remux.py` не гоняются в CI** (тянут
  модель ~125 МБ и бинарник ~30 МБ).
* **`npm audit`**: 4 находки (react-router RSC, esbuild dev-server, два
  vite) — неприменимы к production-сборке, фикс требует мажорного бампа.
* **GPU-провайдеры ONNX Runtime при конкурентных вызовах** — нужен GPU.
* **Chromium в песочнице есть и он полезен**
  (`/opt/pw-browsers/chromium-1194/chrome-linux/chrome`); проприетарных
  кодеков в нём нет, H.264/265 не откроются.
