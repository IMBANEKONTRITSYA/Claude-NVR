## P0 — XML entity expansion ("billion laughs") в ONVIF-клиенте воркера (PR #38)

### Как найдено

Целевой построчный проход по `worker/onvif_client.py` (реализует ТЗ 18.7:
ONVIF-события, автообнаружение, получение профилей потоков — целиком
написан в циклах 6-14, но ни разу не пересматривался с точки зрения
безопасности самого парсинга XML, только с точки зрения инъекции в
исходящий SOAP-запрос — см. PR #33 цикла 12, экранирование username в
WS-Security заголовке).

### Проблема

Все пять точек разбора XML в модуле (`create_pull_point_subscription`,
`pull_messages`, `get_profiles`, `get_stream_uri`, `_parse_probe_matches`)
использовали голый `xml.etree.ElementTree.fromstring()`, который
расширяет `ENTITY`-определения из `DOCTYPE` без ограничений. Локально
проверено: 4-уровневая "billion laughs" бомба (несколько сотен байт XML)
разворачивается в строку длиной 300 000 символов за ~0.09с — на
production-уровне вложенности классической бомбы (10 уровней) итоговый
объём в памяти растёт на порядки быстрее.

Все пять точек разбора получают данные от устройств локальной сети
(ONVIF-камера по SOAP-ответу, произвольный ответчик WS-Discovery по UDP)
— не от доверенного сервера. Камера может быть скомпрометирована,
подменена (spoofing на multicast Probe) либо атакующий может быть MITM на
том же сегменте сети. Это реальный DoS-вектор на процесс воркера, попадающий
под ТЗ 13 ("инъекции... OWASP Top 10") — класс атаки, который семь
предыдущих циклов ONVIF-разработки (6-14) не рассматривали, сосредоточившись
на инъекции в исходящий запрос, а не на разборе входящего ответа.

### Фикс

Заменил `xml.etree.ElementTree` на `defusedxml.ElementTree` (идентичный
API — `fromstring` по-прежнему возвращает обычный
`xml.etree.ElementTree.Element`, импортированный отдельно только как тип
данных) во всех пяти местах. `defusedxml` запрещает `DOCTYPE`/`ENTITY`/
внешние ссылки по умолчанию и бросает `DefusedXmlException` вместо
раскрутки бомбы — обёрнуто в тот же `OnvifError`, что и обычный
`ET.ParseError`, так что вызывающий код (`onvif_poll_worker` в
`worker.py`) не изменился: невалидный/вредоносный ответ по-прежнему ведёт
к переподписке с экспоненциальной задержкой, как и любой другой битый
ответ камеры.

Добавлена чистая Python-зависимость `defusedxml==0.7.1` в
`worker/requirements.txt` и в лёгкий CI-джоб `worker` (тесты
`test_onvif_client.py` по-прежнему не тянут `cv2`/`insightface`).

### Тесты

5 новых regression-тестов в `worker/tests/test_onvif_client.py`:
billion-laughs payload для всех 4 функций, парсящих SOAP-ответ, +
проверка, что один вредоносный UDP-пакет WS-Discovery не роняет всё
обнаружение целиком (тот же паттерн, что у существующего
`test_discover_devices_ignores_garbage_packets_from_other_wsdd_devices`).
89/89 (полный набор тестов воркера после всех трёх PR цикла) проходят.

## P1 — Утечка нитей `onvif_poll_worker` при постоянно неоткрывающемся RTSP (PR #39)

### Как найдено

Фоновый агентный аудит `worker/` по 24/7-стабильности (RTSP-реконнект,
graceful shutdown, thread safety, утечки памяти — раздел не
пересматривался целиком с цикла 1, только точечно по мере новых фич —
hwaccel в цикле 11, ONVIF-эскейпинг в цикле 12). Помимо этой находки и
находки ниже, агент также подтвердил как надёжно работающие:
`backoff.py`/`shutdown.py` (корректно используются для единственного
пути, для которого спроектированы), `record_encode.py` (чистая сборка
аргументов), отсутствие unbounded-роста памяти (`last_event_at` и очередь
апскейла явно ограничены/эвиктятся), отсутствие проблем с
stdout/stderr-пайпами subprocess'ов.

### Проблема

`camera_worker()` запускал daemon-нить `onvif_poll_worker` безусловно при
входе в функцию — до проверки, что `open_capture()` вообще смог открыть
RTSP-поток аналитики. Эта нить не имеет собственного условия остановки,
кроме глобального `shutdown_event` (рассчитана на постоянный запуск на
весь срок жизни камеры), поэтому переживала любой ранний `return`
`camera_worker()`.

Для камеры с настроенным ONVIF, но постоянно неоткрывающимся RTSP-
субпотоком (частая реальная поломка — неверный URL/пароль именно
субпотока при рабочем основном потоке) `manager()` пересоздаёт
`camera_worker()` каждые ~10 секунд (нить считается "умершей" и
перезапускается). Каждый такой перезапуск плодил ещё одну независимую
ONVIF-нить со своей PullPoint-подпиской и сокетом — ни одна из них
никогда не останавливалась. Утечка нитей росла неограниченно и в итоге
исчерпывала лимит потоков процесса, валя **весь** воркер (включая все
остальные, исправно работающие камеры), а не только сбойную — прямое
нарушение ТЗ "стабильно работать 24/7 без деградации" и RTO ≤ 5 минут (в
этом сценарии сбой не восстанавливается сам вообще, нужен ручной
перезапуск воркера).

### Фикс

Старт ONVIF-нити перенесён после успешной проверки `cap.isOpened()`.
ONVIF-события всё равно потребляются только внутри цикла обработки кадров
(`onvif_healthy()`/`onvif_motion_recent()`), который не выполняется без
открытого потока — перенос не убирает функциональность, только устраняет
утечку.

### Тесты

`worker/tests/test_camera_worker_onvif_thread.py` (новый файл,
`pytest.importorskip("worker")` — импорт `worker.py` требует полный
`requirements.txt`, лёгкий CI-джоб корректно пропускает файл): негативный
контроль (5 подряд вызовов с постоянно неоткрывающимся `cap` не запускают
`onvif_poll_worker` ни разу — проверено, что тест красный без фикса и
зелёный с ним), позитивный путь (нить по-прежнему стартует после
успешного открытия) и камера без `onvif_config` (нить не стартует
вообще, было и осталось).

## P1 — Отсутствие детекта зависших RTSP-потоков (PR #40)

### Как найдено

Тот же фоновый аудит воркера. Это прямое попадание в явный пункт чек-
листа ТЗ 12 ("детект зависших потоков"), который не был закрыт ни одним
из 14 предыдущих циклов — все они добавляли backoff-реконнект (цикл 1) и
проверяли только явный `ok=False` от `cap.read()`, но не рассматривали
случай, когда `cap.read()` вообще не возвращает управление.

### Проблема

`open_capture()` не выставлял `CAP_PROP_OPEN_TIMEOUT_MSEC`/
`CAP_PROP_READ_TIMEOUT_MSEC` — ни `cap.open()`, ни `cap.read()` не имели
тайм-аута на FFMPEG-бэкенде OpenCV. Классическая поломка RTSP — TCP-сессия
формально остаётся открытой (NAT-keepalive, зависшая прошивка камеры), но
кадры не идут — блокирует демультиплексор ffmpeg внутри `cap.read()` на
неопределённое время вместо того, чтобы вернуть ошибку. В этом сценарии
существующий backoff-реконнект (`reconnect_delay()`) никогда не
срабатывает: нить считается "живой" (заблокирована ≠ мертва), `manager()`
не перезапускает её, а на shutdown `join(timeout=...)` просто истекает, не
освобождая ресурс — камера молча перестаёт работать до ручного
перезапуска воркера.

### Фикс

`RTSP_OPEN_TIMEOUT_MSEC=10000`/`RTSP_READ_TIMEOUT_MSEC=15000` выставляются
на `cap` до `cap.open()` (единственный момент, когда FFMPEG-бэкенд их
применяет). После истечения read-тайм-аута `cap.read()` вернёт `ok=False`
— уже обрабатывается существующей веткой реконнекта, изменений в
остальной логике `camera_worker()` не потребовалось. Отказ `cap.set()` на
сборках OpenCV без поддержки свойства не ломает открытие потока (тот же
паттерн отката, что уже был у `CAP_PROP_HW_ACCELERATION` в этой же
функции).

### Тесты

`worker/tests/test_open_capture_timeouts.py` (новый файл): оба свойства
выставлены корректными значениями строго до `cap.open()` (по порядку
вызовов на записывающем фейке `VideoCapture`, негативный контроль —
красный без фикса), плюс проверка отката при недоступности свойства.

## Не исправлено в этом цикле — и почему

1. **TOCTOU-гонка дублей `Person` в `find_or_create_person`**
   (`worker/worker.py`): `SELECT` ближайшего центроида → сравнение с
   порогом → `INSERT`, если нет совпадения — без `SELECT ... FOR UPDATE`/
   advisory lock/уникального ограничения. Два соседних камеры, видящие
   одного и того же неизвестного человека в одном узком окне (реалистичная
   планировка — две камеры на один коридор/вход), могут обе создать
   отдельные записи `Person` для одного и того же физического человека.
   Не исправлено в этом цикле: требует либо `pg_advisory_xact_lock` по
   хэшу центроида (неточное решение для vector-similarity), либо
   сериализации через отдельную таблицу-мьютекс, либо смирения с
   периодической ручной дедупликацией через существующий `merge_persons` —
   архитектурное решение, а не однострочный фикс, требует отдельного
   цикла с обсуждением подхода.
2. **Отсутствие backoff у авто-рестарта `ffmpeg`-republish**
   (`worker/worker.py`, строки с проверкой `republish.poll()`): проверяется
   на каждой итерации цикла чтения кадров (десятки раз в секунду), не
   throttled — при недоступном основном RTSP (при исправном субпотоке)
   может уйти в fork/connect-storm против недоступной камеры. В отличие от
   находки P1 выше (открытие потока аналитики), здесь нет уже готового
   "слота" для переиспользования `reconnect_delay()` без более широкого
   рефакторинга структуры цикла (переменная состояния retry-attempt для
   republish отдельно от `reconnect_attempt` для `cap`) — отложено на
   следующий цикл, зафиксировано как известный пробел, а не забыто.
3. **Ветки `fix/security-onvif-xml-entity-expansion` и
   `fix/stability-onvif-thread-leak` не удалены после мерджа** —
   `git push origin --delete` вернул HTTP 403 от прокси песочницы,
   пятнадцатая неудачная попытка подряд (проверено один раз за ветку, не
   повторялось сверх этого — см. цикл 6).
4. **Разночтение ветки харнесса** — не фиксится изнутри сессии, см. раздел
   выше, 15-й цикл подряд.
5. **Конкурентный запуск сессий на одной ветке** — без новых находок
   6 циклов подряд (10-15), риск остаётся вероятностным, приоритет №1 для
   стороны оркестрации без изменений.

Дополнительно зафиксировано агентом фонового аудита как **вопрос без

## Рекомендации на следующие циклы (по приоритету)

1. **Конкурентный запуск сессий на одной ветке** — без новых находок
   6 циклов подряд (10-15), приоритет №1 для стороны оркестрации без
   изменений.
2. **Разночтение назначенной ветки харнесса vs фактической ветки с кодом**
   — 15-й цикл подряд один и тот же паттерн; тривиально починить на
   стороне оркестрации.
3. **Удаление смерджённых веток** — 15-й цикл подряд 403 от прокси
   песочницы; решение только на стороне оркестрации.
4. **TOCTOU-гонка дублей `Person`** (см. раздел выше) — нужен отдельный
   цикл с явным архитектурным решением (advisory lock/мьютекс-таблица/
   смирение с ручной дедупликацией), не однострочный фикс.
5. **Backoff у auto-restart `ffmpeg`-republish** (см. раздел выше) —
   нужен небольшой рефакторинг структуры цикла `camera_worker()`.
6. **Проверка конкурентного доступа к `FACE_APP`** — нужен цикл с реальным
   железом (GPU + 16 потоков нагрузки), объединить с существующим
   carryover по ТЗ 18.2/нагрузочному тесту на реальных камерах (циклы
   9-14).
7. **npm audit (frontend)** — без изменений с цикла 13, 4 находки,
   Windows/dev-server-only, неприменимые к продакшен-конфигурации.
8. Раз построчный P0/P1-проход теперь актуален (этот цикл), следующий
   полный проход можно отложить на несколько циклов — точечный recheck
   свежеизменённого кода (как в циклах 13-14) остаётся основным режимом
   между полными проходами.
