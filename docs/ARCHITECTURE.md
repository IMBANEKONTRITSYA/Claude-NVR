# ARCHITECTURE — архитектура FaceWatch

## Обзор компонентов

FaceWatch — восемь Docker-сервисов, оркестрируемых `docker-compose.yml`,
рассчитанных на один физический хост (от Intel N100 до AMD Ryzen 9,
см. SPEC.md §«Минимальные системные требования»).

```
                              ┌─────────────┐
                    RTSP      │  IP-камеры  │
                    ┌─────────┤  (5–16 шт)  │
                    │         └─────────────┘
                    ▼
        ┌───────────────────────────┐
        │   worker (OpenCV +        │──ffmpeg copy──▶ ┌───────────┐
        │   InsightFace, детекция   │                  │ MediaMTX  │──HLS──▶ nginx ──▶ браузер
        │   + распознавание лиц)    │◀────embed-API────┤(RTSP/HLS) │
        │   embed-API :9000         │  (поиск по фото) └───────────┘
        └──────┬──────────┬─────────┘
               │          │
               │          └──Redis pub/sub──▶ faces:new, cameras:status
               │                                        │
       ┌───────▼────────┐                       ┌───────▼─────────┐
       │  PostgreSQL 16  │◀──────────────────────│  FastAPI backend │◀──HTTP/WS── nginx ◀── браузер
       │   + pgvector    │   события/персоны/    │  (REST + WS)     │
       │  (HNSW-индексы) │   камеры/аудит/settings└──────────────────┘
       └────────┬────────┘
                │
       ┌────────▼────────┐        Redis: upscale:queue
       │ /media (том)     │◀──────────────────────┐
       │ snapshots/segments│                       │
       │ /avatars/uploads │              ┌─────────▼─────────┐
       └──────────────────┘              │  upscaler (GFPGAN) │──faces:enhanced──▶ backend ──WS──▶ браузер
                                          └────────────────────┘

       ┌──────────────────┐
       │ backup (pg_dump   │  cron, раз в сутки → том backups
       │  + crond)         │
       └──────────────────┘
```

## Сервисы

| Сервис | Технологии | Роль | Лимиты (docker-compose.yml) |
|---|---|---|---|
| `postgres` | PostgreSQL 16 + pgvector | Хранение всех данных: камеры, персоны, события, аудит, настройки, refresh-токены | по умолчанию не ограничен (задать через `deploy.resources` при необходимости) |
| `redis` | Redis 7 | Pub/sub (`faces:new`, `cameras:status`, `faces:enhanced`), очередь `upscale:queue`, счётчики brute-force и alert-cooldown | — |
| `mediamtx` | MediaMTX | **Слой записи** (SPEC §2, §20): сам тянет основной поток каждой камеры, пишет remux-сегменты на диск без декодирования, отдаёт HLS/WebRTC | 4 CPU / 2 ГБ RAM |
| `backend` | FastAPI + SQLAlchemy (async) | REST API, WebSocket, аутентификация, RBAC, аудит, бизнес-логика (кроме видео) | 2 CPU / 1 ГБ RAM |
| `worker` | OpenCV + InsightFace + scikit-learn | **Слой аналитики** (SPEC §2): захват потока аналитики, детекция движения/лиц, эмбеддинги, кластеризация, embed-API для поиска. Плюс управление слоем записи: синхронизация путей MediaMTX и индексация готовых сегментов в архив | 6 CPU / 4 ГБ RAM |
| `upscaler` | GFPGAN (или OpenCV-фолбэк) | Асинхронное улучшение качества снимков лиц | 2 CPU / 3 ГБ RAM |
| `backup` | postgres:16-alpine + crond | Ежедневный `pg_dump`, ротация по сроку хранения | 0.5 CPU / 256 МБ |
| `frontend` | Nginx + React (собранный статикой) | Reverse proxy (API/WS/HLS) + отдача SPA + TLS-терминация | — |

Все сервисы: `restart: unless-stopped`, единый `x-logging` (json-file,
10 МБ × 10 файлов на контейнер), health-check там, где это осмысленно
(postgres, redis, backend, worker, backup, frontend).

## Поток данных: от камеры до события в интерфейсе

1. **Запись (независимый слой).** MediaMTX тянет основной поток каждой
   включённой камеры сам — один pull на камеру — и пишет его remux'ом в
   `/media/segments/cam{id}_{unix_ts}.mp4` сегментами по 5–10 минут, без
   декодирования и без перекодирования (SPEC §19, §20, §24). Воркер
   только приводит список путей MediaMTX к списку камер из БД через
   Control API (`worker/record_layer.py`) и заносит дописанные сегменты в
   `video_segments` (`worker/segment_index.py`). Отказ или перезапуск
   воркера запись не прерывает (SPEC §2).
2. **Захват для аналитики.** Нить аналитики поднимается **только для камер
   в режиме `analytics`** (SPEC §2, §6): `worker` открывает их поток
   аналитики (`cv2.VideoCapture`, backend FFmpeg) — субпоток, если он задан,
   иначе основной. Этот поток идёт только в детекцию, в архив с него не
   пишется ничего. Камеры в режиме `record_only` (по умолчанию) нити не
   получают вовсе: на 120 камерах детекция на всех — то, что §24 выносит за
   рамки версии. Число камер в режиме `analytics` ограничено настройкой
   `analytics_cameras_max` (по умолчанию 2, SPEC §1). Переключение режима в
   админке применяется без перезапуска слоёв: нить читает состояние камеры
   раз в 10 секунд (`load_cam_state`) и завершается сама.
3. **Префильтр движения.** Каждый обработанный кадр проходит через
   `cv2.createBackgroundSubtractorMOG2` (с учётом ROI-маски, если
   заданы полигоны). Детектор лиц запускается только при обнаруженном
   движении (кроме «Максимального» профиля — там анализируется каждый
   кадр).
4. **Детекция и эмбеддинг.** InsightFace (`buffalo_s`/`buffalo_l` в
   зависимости от профиля) находит лица и извлекает эмбеддинг 512D.
   Провайдер инференса выбирается автоматически при старте:
   CUDA → DirectML → OpenVINO → CPU (`detect_providers()` в `worker.py`).
5. **Сопоставление персоны.** Эмбеддинг сравнивается с центроидами
   существующих персон через pgvector (`<=>` — косинусное расстояние,
   HNSW-индекс). При совпадении выше порога — событие привязывается к
   существующей персоне; иначе создаётся новая («неизвестный»).
6. **Событие и снимок.** `FaceEvent` пишется в БД, кроп лица
   сохраняется в `/media/snapshots`. Публикуется в Redis
   (`faces:new`) — backend транслирует в WebSocket `/ws/faces`
   подключённым клиентам (Стена, Дашборд, LiveGrid).
7. **Появление сегмента в архиве.** Дописанный MediaMTX сегмент
   обнаруживается индексацией в цикле менеджера воркера (по имени файла и
   по тому, что файл перестал расти) и заносится строкой в
   `video_segments`. Транскода нет: файл попадает в архив ровно таким,
   каким его записала камера.
8. **Фоновый апскейл (опционально).** Если профиль/режим апскейла
   требует — `{event_id}` кладётся в `upscale:queue` (Redis list,
   ограничена 500 задачами). Сервис `upscaler` берёт задачу, улучшает
   снимок через GFPGAN, публикует `faces:enhanced` — backend
   транслирует обновление в WebSocket, интерфейс подменяет превью без
   перезагрузки.
9. **Фоновая кластеризация.** Раз в `cluster_interval_min` минут
   (профиль) отдельная нить с пониженным приоритетом (`os.nice(10)`)
   запускает DBSCAN по эмбеддингам неизвестных персон за последние 7
   дней и сливает дубликаты, которые не совпали онлайн (например, из-за
   разного ракурса).

## Стабильность и отказоустойчивость

- **RTSP-переподключение:** экспоненциальная задержка
  (`worker/backoff.py: reconnect_delay`), прерываемая через
  `shutdown_event` — при остановке системы поток не спит до полной
  задержки, а сразу освобождает ресурсы.
- **Graceful shutdown:** `SIGTERM`/`SIGINT` → `handle_shutdown_signal`
  → `shutdown_event.set()` → каждая нить камеры на следующей итерации
  закрывает `VideoCapture` и помечает камеру `offline`. `manager()` ждёт
  остановки всех нитей с общим бюджетом (8с на все камеры, не по 8с на
  каждую) — укладывается в `stop_grace_period: 20s` контейнера. Записи
  остановка воркера не касается вообще: её ведёт MediaMTX (SPEC §2),
  поэтому терять на остановке нечего.
- **Изоляция сбоев:** ошибка на одном кадре одной камеры (например,
  исключение в детекторе) логируется и не останавливает нить —
  обработка продолжается со следующего кадра; ошибка одной камеры не
  затрагивает остальные (отдельная нить на камеру).
- **Docker restart policy:** `unless-stopped` на каждом сервисе — падение
  контейнера (например, OOM) приводит к автоматическому перезапуску.
- **Ресурсные лимиты:** `deploy.resources.limits` на backend/worker/
  upscaler/backup — не позволяет одному сервису вытеснить остальные
  на памяти/CPU при аномалии (утечка, зависший кадр).

## Модель данных (основные таблицы)

| Таблица | Назначение |
|---|---|
| `users` | учётные записи, роль, bcrypt-хэш пароля, `password_changed_at` |
| `refresh_tokens` | хэши refresh-токенов, `expires_at`/`revoked_at` для ротации и отзыва |
| `cameras` | RTSP/субпоток (зашифрованы Fernet), ROI, чувствительность движения, статус |
| `persons` | имя/статус (known/unknown), `centroid` (Vector(512), pgvector), путь к аватару |
| `face_events` | привязка к камере/персоне, снимок, эмбеддинг, bbox, метка "улучшено" |
| `video_segments` | путь к файлу архива, время начала/конца, тип события (motion/face) |
| `settings` | key-value системные настройки, читаются воркером и backend |
| `audit_log` | операции пользователей: вход/выход, изменения, экспорт — без права удаления |

HNSW-индексы (`idx_face_events_embedding`, `idx_persons_centroid`)
создаются при старте backend (idempotent `CREATE INDEX IF NOT EXISTS`)
— обеспечивают поиск по 100 000 лиц за секунды, а не полный перебор.

## Почему два отдельных сервиса для лиц (worker) и апскейла (upscaler)

Апскейл (GFPGAN) — тяжёлая по CPU/памяти операция (до 200 мс/лицо), не
должна конкурировать с детекцией в реальном времени за ресурсы одного
процесса. Разделение на сервисы даёт независимое масштабирование
(лимиты ресурсов по отдельности) и то, что зависание/падение апскейла
не может остановить детекцию — они общаются только через
Redis-очередь, без прямой зависимости в рантайме.

## Развёртывание и масштабирование

Текущая версия — однохостовая (SPEC.md §16: «в текущей версии
(один сервер) — максимальная оптимизация использования ресурсов»).
Микросервисная структура (отдельные контейнеры для БД, воркера,
апскейла, backend) заложена так, чтобы в будущем можно было:
- вынести `worker`/`upscaler` на отдельный сервер с GPU, оставив
  `backend`/`postgres`/`frontend` на текущей машине (сервисы общаются
  через Redis/Postgres по сети, а не через локальные unix-сокеты);
- подключить primary-replica репликацию PostgreSQL для отказоустойчивого
  чтения (дашборд, отчёты, поиск — без нагрузки на primary);
- добавить несколько серверов-обработчиков видео с балансировкой по
  камерам (например, N воркеров, каждый обслуживает подмножество камер
  по `camera_id % N`).

Ничего из этого не требуется на одном сервере в пределах классов §20
(до 128–256+ камер записи) и не реализовано в текущей версии — заложено
архитектурно на будущее (SPEC §17).

### Модель параллелизма слоя аналитики: нити, а не процессы

Канал аналитики — это **нить** (`threading.Thread` на камеру в
`worker.manager()`), и все нити дёргают один общий `FACE_APP`. Очевидное
возражение — GIL: питоновские нити не исполняют байткод параллельно.
Возражение проверено замером (`perf/bench_scaling.py`), а не оставлено на
усмотрение: та же цепочка аналитики прогоняется K каналами одновременно
сначала нитями с общей моделью, потом процессами со своей моделью у
каждого и привязкой к ядрам.

Песочница, 4 ядра, `buffalo_s`, окно 20 с на точку:

| Режим | Каналов | Суммарно FPS | Занято ядер | FPS на ядро | RSS, МБ |
|---|---|---|---|---|---|
| нити | 1 | 5.02 | 1.06 | 4.75 | 318 |
| процессы | 1 | 4.84 | 1.00 | 4.85 | 528 |
| нити | 2 | 10.36 | 2.09 | **4.96** | 410 |
| процессы | 2 | 9.08 | 1.97 | **4.60** | 878 |
| нити | 4 | 15.30 | 3.16 | **4.84** | 618 |
| процессы | 4 | 15.86 | 3.20 | **4.95** | **1591** |

По полезной работе на ядро режимы неразличимы (4.6–5.0 в обоих), по
памяти процессы дороже в 2.6 раза на четырёх каналах — и разрыв растёт
линейно с числом каналов, потому что каждый процесс держит свою копию
весов. Причина, по которой GIL здесь ничего не решает: все три горячих
шага (`cap.read()` — FFmpeg внутри OpenCV, `MOG2.apply()`,
`session.run()` — ONNX Runtime) уходят в C и на это время GIL отпускают;
под ним остаётся только склейка между шагами.

Поэтому слой остаётся на нитях. Из этого выбора следует **привязка к
NUMA-нодам делается по нити** (`worker/cpu_affinity.py`, SPEC §17):
топология читается из `/sys/devices/system/node`, камеры `analytics`
раскладываются блоками по нодам, нить канала привязывается к ядрам своей
ноды **до открытия захвата** — политика памяти Linux first-touch, и после
первых кадров привязывать уже поздно. На односокетной машине раскладка
пуста: локальности там нет, а планировщику привязка мешает.

Плата за общую модель: `FACE_APP` загружается менеджером один раз и лежит
на его ноде, то есть часть каналов читает веса через межпроцессорную шину.
Разменяно осознанно — альтернатива стоит копии весов на канал (таблица
выше).
