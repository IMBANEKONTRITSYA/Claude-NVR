# ADMIN_GUIDE — руководство администратора FaceWatch

Мониторинг, резервное копирование, безопасность, управление
пользователями и системными настройками. Пользовательские функции
(камеры, архив, поиск) — [USER_GUIDE.md](USER_GUIDE.md). Установка —
[INSTALL.md](INSTALL.md). Архитектура — [ARCHITECTURE.md](ARCHITECTURE.md).

## Управление пользователями

**Раздел «Пользователи»** (только админ): создание/удаление учётных
записей, назначение роли (`admin` / `operator` / `viewer`, см.
матрицу прав в USER_GUIDE.md). Пароли пользователей хранятся только в
виде bcrypt-хэша — администратор не может «посмотреть» пароль, только
сбросить (пользователь сам задаёт новый при следующем входе через
смену пароля, либо администратор пересоздаёт учётку).

Требования к паролю (ТЗ 13, применяется и при создании пользователя, и
при смене пароля):
- не короче **10 символов**;
- минимум **3 из 4 классов**: строчные буквы, заглавные буквы, цифры,
  спецсимволы;
- срок действия **90 дней** — после истечения пользователь при
  следующем входе обязан сменить пароль (вход не блокируется,
  но интерфейс принудительно ведёт на страницу профиля).

## Мониторинг

**Раздел «Мониторинг»** (админ и оператор, оператору — в
ограниченном объёме): загрузка CPU и RAM, заполнение диска архива,
температура (если доступна в контейнере), число камер в сети и их
статус (`online`/`offline`/`disabled`), фактический FPS детекции по
каждой камере, длина очереди фонового апскейла.

**Экспорт метрик для Prometheus/Grafana:** `GET /api/system/prometheus`
(доступен только администратору, требует Bearer-токен). Формат —
стандартный текстовый формат экспозиции Prometheus, готов к
подключению `scrape_config` без дополнительного экспортёра.

Рекомендуемые пороги для алертинга во внешней системе мониторинга
(Prometheus Alertmanager, Grafana Alerting) в соответствии с ТЗ 12:
- загрузка CPU выше 90% продолжительное время;
- диск архива заполнен больше 90%;
- камера в статусе `offline` дольше нескольких минут (потеря сигнала);
- FPS детекции по камере ниже целевого порога профиля.

Уведомления о появлении персоны из списка наблюдения (watchlist) можно
включить точечно, без внешнего Prometheus — Telegram-бот, настраивается
ниже.

## Расчёт хранения и retention (SPEC §5, §21)

### Формула

    Мбит/с × 10.8 = ГБ/сутки на камеру

При базовой конфигурации объекта (основной поток 2048 кбит/с, SPEC §1):

| | На камеру | 120 камер |
|---|---|---|
| В сутки | 21.6 ГБ | ~2.5 ТБ (номинал) |
| 7 дней | 151 ГБ | ~18 ТБ |
| 14 дней | 302 ГБ | ~36 ТБ |
| 30 дней | 648 ГБ | ~78 ТБ |

Это **номинал**. Фактически VBR и smart-кодек дают меньше — ориентир
SPEC §21: ~1.6–2 ТБ/сутки на 120 камер вместо 2.6 ТБ. Поэтому диск под
номинал брать безопасно, а прогноз системы считается по факту (ниже).

**Калькулятор** — раздел «Мониторинг», карточка «Калькулятор хранения»
(только администратор). Задаются битрейт, число камер и глубина; ответ —
требуемый объём в ГБ и ТБ. Тот же расчёт доступен как
`GET /api/system/storage/calculator?bitrate_kbps=&cameras=&days=`.

### Прогноз «на сколько дней хватит места»

Карточка «Хранилище архива» в разделе «Мониторинг» показывает
заполнение диска, объём архива, расход за последние сутки и прогноз.

Прогноз считается **по фактическому расходу** за последние 24 часа
(сумма размеров записанных сегментов), а не по номиналу: номинал
завышен примерно в полтора раза, и прогноз по нему занижал бы срок.
Пока фактических данных нет — первые сутки после развёртывания —
показывается расчётная оценка с пометкой источника.

Строка «Калибровка» показывает отношение фактического расхода к
расчётному (SPEC §21). Значение заметно выше 100% означает, что камеры
пишут с более высоким битрейтом, чем заложено в расчёт, — стоит
проверить их настройки, иначе диска хватит на меньший срок, чем
планировалось.

### Глубина хранения

Задаётся на двух уровнях:

* **глобально** — «Настройки» → «Глубина хранения архива (дней)»,
  по умолчанию 14 (SPEC §21);
* **по камере** — поле «Глубина хранения этой камеры» в карточке камеры.
  Пустое поле означает «следовать за глобальной настройкой», и камера
  продолжит следовать за ней при её изменении. Заполненное —
  переопределяет глобальную только для этой камеры.

Ротация идёт раз в час: сегменты старше своего срока удаляются вместе с
файлами. События распознавания чистятся по **глобальному** сроку —
карточка персоны собирается из событий всех камер, и разная глубина по
камерам рвала бы её непредсказуемо.

### Циклическая перезапись при переполнении

Отдельный от retention аварийный механизм (SPEC §5, §21). Когда
свободного места остаётся меньше порога «Порог циклической перезаписи
(% свободного)» (по умолчанию 5%), удаляются самые старые сегменты по
всему архиву — **даже если их срок хранения не истёк**.

Это страховка на случай, когда расчёт не сошёлся с фактическим
битрейтом: без неё запись встала бы целиком, что хуже, чем потеря
самых старых суток. Проверка идёт каждые ~10 секунд (между часовыми
проходами ротации 120 камер успевают записать около 108 ГБ), но
удаления происходят, только когда порог действительно перейдён.

Срабатывание пишется в журнал воркера с уровнем `warning` и полями
`segments_removed`, `need_bytes`, `free_pct`. Регулярные срабатывания —
сигнал, что глубину хранения нужно уменьшить либо диск расширить.

### Алерты по заполнению

Пороги «Предупреждение о заполнении диска» (80%) и «Критическое
заполнение диска» (90%) — SPEC §14. При переходе порога воркер пишет
запись в журнал, а карточка «Хранилище архива» показывает баннер.
Повторные сообщения подавляются кулдауном (`alert_cooldown_sec`),
отдельным на каждый уровень: переход warning → critical не ждёт конца
кулдауна предупреждения.

## Telegram-оповещения

**Раздел «Настройки» → «Оповещения»**: укажите токен Telegram-бота
(получить у `@BotFather`) и chat ID получателя. Кнопка «Отправить
тестовое сообщение» проверяет, что бот и chat ID указаны верно, не
дожидаясь реального события. После настройки оповещение приходит при
обнаружении персоны с включённым флагом «оповещать» (устанавливается в
карточке персоны, см. USER_GUIDE.md) — не чаще одного сообщения за
период cooldown на персону, чтобы не заспамить чат при долгом
нахождении человека в кадре.

## Почтовые оповещения (SMTP)

**Раздел «Настройки» → «Почтовые уведомления (SMTP)»** (SPEC §11).
Заполните адрес сервера, порт, режим шифрования и — если релей требует
авторизации — логин с паролем. Пароль хранится в БД зашифрованным (тем же
ключом `RTSP_ENCRYPTION_KEY`, что и RTSP-учётки), поэтому в дампы
`pg_dump` открытым текстом не попадает.

| Поле | Что указывать |
|---|---|
| SMTP-сервер | Пусто — почта выключена целиком |
| Порт / шифрование | 587 + STARTTLS, 465 + SSL/TLS, 25 + без шифрования |
| Логин | Пусто — релей без авторизации (типично для локального) |
| Отправитель | Пусто — берётся логин |
| Получатели алертов | Через запятую; сюда идут и watchlist, и диск |

Кнопка «Отправить тестовое письмо» шлёт письмо по **сохранённым**
настройкам, поэтому сначала нажмите «Сохранить». Ошибка показывается
дословно (`SMTP: неверный логин или пароль`, `SMTP: ConnectionRefusedError`
и т.п.) — по ней видно, что именно чинить.

Что уходит на почту:

- обнаружение персоны с флагом «оповещать» (тот же кулдаун, что у
  Telegram, — один общий на оба канала, не по каналу);
- заполнение диска архива выше порогов warning/critical (SPEC §9).

Каналы независимы: неверный пароль SMTP не отменяет Telegram и наоборот.

## Звуковое оповещение

**Раздел «Настройки» → «Звуковое оповещение»** (SPEC §6). Включённый флаг
заставляет вкладку «Стена распознавания» подавать короткий сигнал при
обнаружении персоны из watchlist. Сигнал синтезируется браузером, звуковой
файл никуда не загружается.

Особенности, о которых стоит знать оператору:

- сигнал работает на **открытой** вкладке «Стена»; свёрнутое окно браузер
  может усыпить;
- первый сигнал в сессии может не прозвучать, пока по странице не кликнули
  — это политика автовоспроизведения браузера, не настройка системы;
- кнопка «Пауза» на Стене глушит и звук;
- не чаще одного сигнала в 5 секунд, даже если watchlist-персон в кадре
  несколько.

## Резервное копирование

Отдельный сервис `backup` в `docker-compose.yml` (образ
`postgres:16-alpine` со встроенным `crond`) снимает дамп PostgreSQL
автоматически по расписанию.

- **Расписание:** `BACKUP_SCHEDULE` в `.env` (cron-выражение, по
  умолчанию `0 3 * * *` — раз в сутки в 03:00).
- **Хранение:** том `backups`, срок хранения `BACKUP_RETENTION_DAYS`
  (по умолчанию 14 дней) — более старые дампы удаляются автоматически.
- **Сетевое хранилище/отдельный диск:** переопределите путь тома через
  `docker-compose.override.yml` (пример — комментарий в
  `docker-compose.yml` рядом с сервисом `backup`), чтобы бэкапы не
  зависели от диска, на котором работает сама система.
- **Ручной запуск:** `scripts\backup_now.bat` (Windows) или
  `docker compose exec backup /backup/run.sh`.
- **Восстановление:** пошаговая процедура — [docs/BACKUP.md](BACKUP.md).

Проверяйте восстановление на тестовом окружении хотя бы раз после
первичной настройки — рабочий бэкап, который ни разу не пробовали
развернуть, не гарантирует, что процедура восстановления действительно
работает.

## Безопасность

### Аутентификация

- Пароли — bcrypt с солью (`passlib`).
- JWT: access-токен живёт **30 минут**, refresh-токен — **14 дней**,
  ротация refresh-токена при каждом обновлении access-токена. Смена
  пароля отзывает **все** refresh-токены пользователя (сигнал
  компрометации — если пароль сменили, старые сессии на других
  устройствах не должны оставаться живыми).
- Защита от подбора пароля: не более **10 попыток входа** в скользящем
  окне на связку логин+IP, дальше — временная блокировка на уровне
  Redis-счётчика.
- Автоматический выход при бездействии — 15 минут (см. USER_GUIDE.md).

### Секреты

`.env` должен содержать реальные, не публичные значения:

| Переменная | Назначение |
|---|---|
| `SECRET_KEY` | подпись JWT (HS256) |
| `RTSP_ENCRYPTION_KEY` | Fernet-ключ шифрования RTSP-учёток в БД |
| `ADMIN_PASSWORD` | пароль учётки `admin`, создаваемой при первом старте |
| `POSTGRES_PASSWORD` | пароль БД |

`start.bat` генерирует `SECRET_KEY`/`RTSP_ENCRYPTION_KEY`/`ADMIN_PASSWORD`
автоматически при первом запуске (`scripts/generate_env.ps1`). Backend
**отказывается стартовать**, если обнаруживает публично известные
значения по умолчанию из репозитория (проверка `insecure_secret_problems()`
в `backend/app/config.py`) — это намеренная защита, не баг: свежее
развёртывание без нормального `.env` не должно тихо подняться с
учёткой `admin`/`admin`.

Для локальной отладки (не для продакшена!) эту проверку можно
отключить переменной `ALLOW_INSECURE_DEFAULT_SECRETS=true`.

RTSP-учётные данные камер шифруются Fernet (AES) перед записью в БД —
даже при прямом доступе к дампу базы пароли камер не читаются в
открытом виде.

### TLS/HTTPS

При первом запуске `frontend`-контейнер (`docker-entrypoint.sh`)
автоматически генерирует самоподписанный TLS-сертификат на 10 лет,
сохраняет его в томе `frontend_certs` (переживает пересоздание
контейнера). Nginx слушает `443` рядом с `80`, доступно как
`https://localhost:8443`.

Редирект с `80` на `443` **не выполняется принудительно** — это
осознанное решение для однокомпьютерной LAN-системы: жёсткий редирект
на самоподписанный сертификат добавил бы предупреждение браузера при
каждом обычном заходе, не давая реального выигрыша в безопасности
локальной сети. HTTPS доступен как осознанный шаг администратора: если
нужен постоянный HTTPS, откройте `https://localhost:8443`, примите
предупреждение браузера (самоподписанный сертификат) один раз и
пользуйтесь этим адресом.

Для production-развёртывания с доверенным сертификатом (Let's Encrypt
и т.п.) замените содержимое тома `frontend_certs` или настройте
внешний reverse proxy перед FaceWatch.

### Сетевая безопасность

- CORS ограничен списком `CORS_ALLOWED_ORIGINS` из `.env` (не `*`) —
  в production фронтенд и API идут через один nginx (same-origin),
  список нужен только для локальной разработки с отдельным dev-сервером.
- Postgres, Redis и MediaMTX опубликованы в `docker-compose.yml` только
  на `127.0.0.1` (loopback) — недоступны из локальной сети, только с
  того же ПК (для отладки через `psql`/`redis-cli`/VLC).
- Ограничение доступа к админ-панели по IP — настраивается на уровне
  внешнего firewall/reverse proxy перед FaceWatch (например, правило
  брандмауэра Windows или ACL на корпоративном маршрутизаторе); сам
  FaceWatch не выступает публичным интернет-сервисом.

### Аудит действий

**Раздел «Аудит»** (только админ): журнал входов/выходов, просмотра
камер, изменения настроек, экспорта данных — каждая операция с
привязкой к пользователю, времени и IP. Экспорт в CSV/XLSX для внешнего
хранения. Журнал доступен только на чтение из веб-интерфейса — удаление
записей через API не реализовано ни для одной роли, включая
администратора (защита от удаления, ТЗ 13).

### Проверка уязвимостей зависимостей

CI (`dependency-audit` job в `.github/workflows/ci.yml`) на каждый push
прогоняет `pip-audit` по `backend/requirements.txt` и
`worker/requirements.txt`, а также `npm audit` по фронтенду. Найденные
уязвимости с обоснованием, почему они не применимы к продакшен-сборке
(если такие есть), задокументированы прямо в workflow-файле рядом с
соответствующим шагом.

## Нагрузочное тестирование

SPEC.md §14 требует сценарий нагрузочного теста на 16 камер. Скрипт —
`loadtest/locustfile.py` (locust), нагружает API-слой, которым реально
пользуется браузер при просмотре 16 камер (снепшоты живой сетки,
дашборд, архив, отчёты, аудит); границы теста (что не покрывается без
реальных камер/GPU) и как читать результаты — `loadtest/README.md`.
Запуск вручную, не часть обычного CI (`ci.yml` намеренно не запускает
его на каждый push — нагрузочный прогон не должен быть источником
случайных красных билдов):

```bash
pip install locust
locust -f loadtest/locustfile.py --headless -u 16 -r 4 -t 5m \
    --host http://localhost:8000
```

## Системные настройки и профили производительности

**Раздел «Настройки»** (только админ):

- **Хранение:** глубина хранения архива в днях, циклическая перезапись.
- **Детекция:** порог движения, порог схожести эмбеддингов (используется
  при слиянии персон онлайн), cooldown события на персону/камеру.
- **Профиль производительности** (ТЗ 18.9) — переключение между
  «Экономный» / «Стандартный» / «Максимальный» одной кнопкой, с
  возможностью затем вручную донастроить любой параметр индивидуально:

  | Параметр | Экономный | Стандартный | Максимальный |
  |---|---|---|---|
  | FPS детекции | 5 | 10 | 15 |
  | Пропуск кадров | каждый 4-й | каждый 2-й | без пропуска |
  | Префильтр движения | включён | включён | выключен |
  | Модель распознавания | buffalo_s (MobileFaceNet-класс) | buffalo_s | buffalo_l |
  | Апскейл | только вручную | аватары в фоне | вся галерея в фоне |
  | Кластеризация | раз в 60 мин | раз в 15 мин | раз в 5 мин |

  Смена модели/разрешения детекции применяется воркером без перезапуска
  контейнера (см. `manager()` в `worker/worker.py` — сверяет текущий
  профиль на каждой итерации цикла).

- **Кодек записи:** H.264 (совместимость с браузером) или H.265
  (экономия места до 50%, часть браузеров может не воспроизвести
  экспортированный фрагмент напрямую — рекомендуется для архива, не для
  живого просмотра).

### Аппаратное ускорение декодирования (ТЗ 18.2)

Воркер автоматически пробует декодировать субпоток аналитики через
доступный GPU-ускоритель (Intel QuickSync/VAAPI, NVIDIA NVDEC) и прозрачно
откатывается на программное декодирование, если ускоритель не найден или
не подошёл конкретной камере — вручную ничего выбирать не нужно. Чтобы
GPU реально был виден внутри контейнера воркера, на Linux-хосте с Intel
iGPU добавьте проброс устройства в `docker-compose.yml`:

```yaml
  worker:
    devices:
      - /dev/dri:/dev/dri
```

(не включено по умолчанию — на хостах без `/dev/dri`, включая большинство
CI-раннеров, `docker compose up` с обязательным `devices:` завершится
ошибкой, если путь не существует). Для NVIDIA нужен `nvidia-container-toolkit`
и `runtime: nvidia`. Если аппаратный путь конкретной камеры ведёт себя
нестабильно (артефакты, разрывы), можно принудительно вернуться на
программное декодирование переменной окружения воркера
`FACEWATCH_HW_DECODE=0`.

## Обновление системы

```powershell
git pull
docker compose up -d --build
```

Пересборка не затрагивает данные в именованных томах. Перед крупным
обновлением рекомендуется сделать ручной бэкап
(`scripts\backup_now.bat`).

## Восстановление после сбоя

- Упавший сервис поднимается автоматически (`restart: unless-stopped` в
  `docker-compose.yml`).
- Воркер переподключается к RTSP с экспоненциальной задержкой при
  потере сигнала камеры — не требует вмешательства администратора.
- Если контейнер не поднимается сам, `docker compose up -d` пересоздаёт
  его с сохранением данных в томах.
- Восстановление БД из бэкапа — [docs/BACKUP.md](BACKUP.md).

Целевое время восстановления (RTO) — не более 5 минут для большинства
сценариев (перезапуск контейнера, переподключение камеры); полное
восстановление из бэкапа БД занимает дольше и описано отдельно в
BACKUP.md.
