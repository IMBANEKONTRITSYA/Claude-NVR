## Цикл 50 — 2026-08-22

### Соответствие
- **§24 «возможность удаления данных по требованию» появилась впервые.**
  До этого цикла в системе не было пути, который убирал бы биометрию
  человека: `DELETE /api/persons/{pid}` снимал карточку, а внешний ключ
  `face_events.person_id` объявлен `ON DELETE SET NULL` — снимки лица и
  эмбеддинги 512D оставались в базе. Поиск по фото
  (`POST /api/search/face`) идёт по `face_events.embedding` и на
  `person_id` не смотрит, поэтому «удалённый» человек продолжал
  находиться собственной фотографией со всеми своими кадрами. Диалог
  подтверждения в интерфейсе при этом обещал «удалить персону **и все её
  снимки**».
- **`DELETE /api/persons/{pid}/biometrics`** (только админ, отдельная
  строка в журнале аудита) сносит карточку вместе с её событиями,
  эмбеддингами и файлами снимков и отвечает числом снятого — им и
  подтверждают исполнение требования. Файл, на который ссылается
  выжившая строка (аватар после слияния), остаётся на диске.
- **В карточке персоны теперь две кнопки** — «Удалить карточку» и
  «Удалить с биометрией», и каждая говорит ровно то, что делает.

### Производительность
- **§19 «0 пропущенных сегментов при штатной работе» измерено впервые:
  0 с потерь на двух переворотах, покрытие 100 %.** Из нормативов §19 этот
  оставался неизмеренным дольше всех: остальные меряются одним процессом,
  а этот требует, чтобы настоящий MediaMTX несколько раз перевернул
  сегмент на настоящем потоке — норматив нарушается **на стыке** файлов.
  `perf/bench_segment_continuity.py` считает секунды, а не файлы: имя
  сегмента даёт начало, ffprobe — фактическую длительность, разница на
  стыке — потерянное видео. Замер подключён к джобе `perf` и валит её
  ненулевым кодом возврата: пропуски записи не видны ни в одном
  функциональном тесте.

## Цикл 46 — 2026-08-22

### Развёртывание
- **Production-упаковка §26 появилась впервые: .deb + systemd.** До этого
  цикла единственным способом поставить FaceWatch был Docker Compose,
  который SPEC §26 прямо называет не-production режимом; .deb был
  единственным полностью отсутствующим пунктом ТЗ. Пакет несёт
  переносимый CPython 3.11, по venv на сервис, статический бинарник
  MediaMTX, собранный фронтенд и вложенные веса модели распознавания —
  системного `python3` он не касается. PostgreSQL с pgvector, Redis,
  nginx и ffmpeg приходят зависимостями из репозитория дистрибутива.
  Установка — одна команда `apt install ./facewatch_*.deb`; секреты,
  роль и база PostgreSQL, самоподписанный TLS-сертификат и каталоги
  данных создаются скриптом первого запуска, идемпотентным по
  требованию §26.
- **Четыре systemd-юнита плюс oneshot-подготовка**, собранные в
  `facewatch.target`, с `Restart=always` (§13) и лимитами
  CPUQuota/MemoryMax, взятыми из `deploy.resources.limits`
  docker-compose, чтобы стенд и объект вели себя одинаково. Жёстких
  зависимостей между слоями нет: §2 требует, чтобы отказ аналитики не
  влиял на запись, и systemd-связка это требование нарушала бы.
- **`apt purge` не удаляет ни архив, ни базу.** Удаляется только
  конфигурация, как требует политика Debian. Записи инцидента бывают в
  единственном экземпляре, и пакетный менеджер — не тот инструмент,
  которым их стирают.
- **Install-тест на раннере с systemd** (`packaging/install-test.sh`,
  джоба `deb` в новом workflow `package.yml`): установка, `active` без
  CrashLoop (по счётчику `NRestarts`, иначе `Restart=always` маскировал
  бы падение), вход `admin` с проверкой, что токеном действительно
  открывается защищённый эндпоинт, миграции — запросом в саму базу, а не
  по строчке в логе, идемпотентная переустановка и сохранность данных
  при purge. На тег `v*` собирается полный профиль, на PR, трогающий
  упаковку, — `core`.
- **Скачиваемое пинуется по sha256** (`packaging/versions.env`), версия
  MediaMTX сверяется с `docker-compose.yml` — разъехавшись, пакет вёз бы
  на объект сервер записи не той версии, против которой гоняются тесты
  слоя записи.

### Документация
- `docs/INSTALL_LINUX.md` — установка на объекте, обновление, вынос
  архива на отдельный массив, боевой TLS, удаление. SPEC §23 требует от
  INSTALL «Windows + Linux»; Linux-половины не было.
- `packaging/README.md` — состав пакета, сборка, профили, обоснование
  двух отступлений от §26 (`dpkg-deb` вместо nfpm/fpm, ffmpeg из
  репозитория вместо статической сборки).
- `docs/DEPLOY_CHECKLIST.md` — раздел 0.1 про первую установку пакета на
  объекте: перезагрузка сервера, апгрейд поверх работающего объекта,
  лимиты systemd под 120+ камер, архив на отдельном массиве.

## Цикл 29 — 2026-08-17

### Производительность
- **Слой аналитики ускорен в 6 раз (SPEC §19).** `FaceAnalysis`
  создавался без `allowed_modules`, поэтому insightface поднимал пять
  моделей и прогонял четыре из них **на каждое лицо каждого кадра**:
  detection, landmark_3d_68, landmark_2d_106, genderage, recognition.
  Воркер читает из результата ровно два поля — `bbox` и
  `normed_embedding`; возраст, пол и лицевые точки не используются нигде.
  Замерено на полной цепочке (buffalo_s, det_size 640, один поток, кадр с
  шестью лицами): **697.9 → 106.8 мс** на детектор с эмбеддингом,
  цепочка целиком **1.39 → 8.39 FPS/канал**. Норматив §19 «детекция ≥ 5
  FPS/канал» до этой правки **не выполнялся**, после — выполняется с
  запасом 1.7×. Регрессию сторожит `worker/tests/test_face_modules.py`:
  без `allowed_modules` система остаётся корректной и просто становится
  в шесть раз медленнее, то есть иначе откат был бы невидим.

### Измерено
- **Норматив §19 «детекция ≥ 5 FPS/канал» — впервые измерен на реальной
  модели.** Прошлые циклы держали его в known gaps («нужна реальная ONNX-
  модель»): `buffalo_s` тянется из сети, и вместо неё мерилась
  синтетическая сеть по частям. Новая группа бенчмарка
  `perf/bench.py --only chain` гоняет цепочку целиком и в том же порядке,
  что `worker.camera_worker()`, на клипе с настоящими лицами из состава
  insightface. Числа получены на хосте песочницы с AVX2 — на целевом
  E5-2670 его нет, поэтому пункт остаётся в чек-листе развёртывания.

### Добавлено
- **Шаблоны отчётов и автоматическая отправка по расписанию (SPEC §8).**
  Раздел требовал и то, и другое; работала только выгрузка по кнопке.
  Шаблон — сохранённый набор параметров (вид отчёта, формат, период
  выборки, получатели), который можно отправить кнопкой или включить в
  расписание: ежедневно, еженедельно (день недели) или ежемесячно (число
  1–28) в заданное время. Отчёт уходит вложением на тот же SMTP, что и
  алерты. Планировщик — фоновая задача в процессе бэкенда, без внешнего
  брокера: §26 требует пакет из четырёх systemd-юнитов, а не из пяти.
  Два свойства планировщика вынесены в чистые функции и покрыты тестами
  на фиксированных датах, потому что ломаются они беззвучно: слот
  отрабатывает **ровно один раз** (перезапуск в 08:00:30 не шлёт отчёт
  повторно) и **не теряется** при простое (бэкенд лежал с 07:50 до 08:10 —
  отчёт уйдёт при старте, и ровно один, а не по письму за каждые
  пропущенные сутки). Неудачная отправка не закрывает слот и показывает
  причину в карточке шаблона — иначе «отчёт не приходит» диагностировался
  бы только по логам сервера.
- **Почтовые уведомления (SPEC §11, §6, §9)** — SMTP отсутствовал во всём
  дереве, хотя его требуют три раздела ТЗ сразу: §6 (алерты при детекции),
  §8 (авто-отправка отчётов) и §11 (настройки уведомлений). Добавлен
  транспорт `mailer` (только stdlib, копия в воркере сверяется по AST),
  настройки `smtp_*` и `alert_email_to` в админке, кнопка «Отправить
  тестовое письмо» (`POST /api/settings/test-email`). Пароль SMTP хранится
  зашифрованным наравне с токеном Telegram и пишется в журнал аудита при
  проверке. Письма уходят при обнаружении watchlist-персоны и при
  заполнении диска архива выше порогов.
- **Звуковой алерт на Стене распознавания (SPEC §6)** — третий канал
  оповещений наравне с Telegram и почтой. Сигнал синтезируется WebAudio
  (без внешнего файла — строгий CSP nginx и §24 о лицензиях), звучит
  только по watchlist-персоне и не чаще раза в 5 секунд. Включается
  флагом `alert_sound_enabled`; интерфейсу он отдаётся новым
  `GET /api/settings/client` — белым списком несекретных настроек,
  доступным любой роли, в отличие от admin-only `GET /api/settings`.
- В сообщение `type: "face"` веб-сокета `/ws/faces` добавлено поле
  `alert` (персона в watchlist).

### Исправлено
- **Кулдаун оповещений снимается один раз на событие и общий для каналов.**
  Реализация «каждый канал берёт свой `SET nx=True`» выглядит правильной
  и молча ломает почту при включённом Telegram: первый канал забирает
  ключ, второй видит занятый и выходит.
- **Форма настроек больше не отправляет `NaN`** на ключах, которых нет в
  БД (развёрнутой до появления настройки): `JSON.stringify` превращал их
  в `null`, и бэкенд отвечал 422 на сохранение всей формы из-за поля,
  которого администратор не касался. Запасное значение подставляется
  только вместо неразобранного числа, а не по `||`: ноль — законное
  значение у `frame_skip` («каждый кадр») и `motion_prefilter`
  («префильтр выключен»), и `||` подменял бы их молча.

## Разработка Tier-1 (до начала циклов автономного аудита)

Дальнейшая разработка после MVP — в один непрерывный поток коммитов,
без отдельных PR/тегов:

- Профили производительности («экономный»/«стандартный»/«максимальный»),
  двухпоточная работа с камерами (основной поток + субпоток для
  детекции), мониторинг системы (ТЗ 18, ТЗ 12).
- Нейросетевой апскейл лиц (GFPGAN) как отдельный сервис, поиск похожих
  лиц по фото через pgvector.
- Ручное создание персон, заметки, watchlist с Telegram-оповещениями.
- pgvector HNSW-индексы, лимит попыток входа (rate limiting логина),
  постраничная выдача на сервере, экспорт журнала аудита.

  камеры, ROI-маска в детекции, фоновая DBSCAN-перекластеризация.

- Базовый функционал: подключение IP-камер по RTSP, мозаичный просмотр,
