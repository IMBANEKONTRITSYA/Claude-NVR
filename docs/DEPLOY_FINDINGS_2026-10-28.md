# Проверка на компьютере пользователя — 28.10.2026

Ветка: `claude/pensive-brown-28588t`, исходный коммит `8c04b8d`.
Среда: Windows, Docker Desktop/WSL2, 32 ГБ RAM, 16 логических CPU.
Результаты ниже относятся к стендовому Compose-развёртыванию, не к production .deb/systemd.

## D01. Healthcheck MediaMTX не исполняется в официальном образе

**Серьёзность:** средняя, ложный unhealthy и невозможность выполнить критерий готовности.

**Воспроизведение:** запустить исходный Compose; его healthcheck использует
`CMD-SHELL` и `wget` в `bluenviron/mediamtx:1.16.0`.

**Ожидалось:** HTTP-запрос к локальному Control API подтверждает работоспособность сервиса.

**Получено:** образ не содержит `/bin/sh`; отдельный запуск этой команды воспроизвёл
`exec: "/bin/sh": stat /bin/sh: no such file or directory`. Бинарник `/mediamtx --version` работает и возвращает `v1.16.0`.

**Исправление:** `mediamtx/Dockerfile` переносит тот же бинарник из закреплённого
официального образа в Alpine с BusyBox; Compose собирает этот образ. Версия сервера сохранена.

## D02. CRLF ломает entrypoint веб-сервера и резервного копирования

**Серьёзность:** высокая, веб-интерфейс недоступен, резервное копирование не запускается.

**Воспроизведение:** клонировать проект на Windows с `core.autocrlf=true`, выполнить
`docker compose up -d --build`.

**Ожидалось:** frontend и backup запускаются.

**Получено:** оба контейнера перезапускаются с кодом 255; журналы содержат
`exec /docker-entrypoint.sh: no such file or directory` и
`exec /backup/entrypoint.sh: no such file or directory`.
Файлы существуют; начало entrypoint в hex — `23 21 2F 62 69 6E 2F 73 68 0D 0A`.
Причина — CRLF в shebang: ядро ищет `/bin/sh\r`.

**Исправление:** `.gitattributes` дополнен `*.sh text eol=lf`; шесть Linux-скриптов
нормализованы в рабочем каталоге. Frontend пересобирается, backup использует исправленный bind mount.

## D03. MediaMTX v1.16.0 падает на реальных RTCP-пакетах — исправлено обновлением

**Серьёзность:** критическая, одновременно прерывает запись всех камер и просмотр.

После подключения 49 источников контейнер перезапустился 9 раз за несколько минут.
Стек: `panic: runtime error: integer divide by zero`,
`gortsplib/v5@v5.3.0/pkg/rtpreceiver/receiver.go:143`.
В момент рестарта Control API теряет runtime-пути, воркер восстанавливает конфигурацию,
а интерфейс показывает чёрные плитки. Это не OOM: `OOMKilled=false`.

Совпадает с [upstream issue #5407](https://github.com/bluenviron/mediamtx/issues/5407)
и [исправлением gortsplib #994](https://github.com/bluenviron/gortsplib/pull/994).
Закреплена ближайшая патч-версия MediaMTX **1.16.1** (gortsplib 5.3.1).
После замены — 49/49 ready, 0 рестартов в оставшейся части короткого теста.
Совместимость: 94 модульных и 12 интеграционных тестов записи прошли в Linux-контейнере.
CI и проверка закреплённой версии адаптированы к образу-обёртке.

## D04. H.265: чёрные плитки и ошибочная причина 404 — остаётся

**Серьёзность:** высокая для живого просмотра.

Шаги: открыть «Камеры онлайн», мозаика 16, выбрать H.265-камеры.
Ожидалось: живое видео либо корректный диагноз и работающий запасной снимок.
Получено: HLS возвращает 404/500; журнал MediaMTX содержит
`muxer error: unable to extract DTS: invalid DeltaPocS0`.
При этом runtime-путь существует и ready, мониторинг показывает «пишется».
Значит, текст «Поток не заведён в медиасервере» для этого 404 неверен.

Дополнительно `/api/cameras/3/snapshot` и `/api/cameras/32/snapshot` возвращают 404:
снимки создаёт только нить аналитики, которой нет у `record_only`.
Запасной путь из README для большинства таких камер фактически отсутствует.
У двух analytics-камер снимки доступны (200).

Контроль: H.264-камеры #32/#33 отдают HLS 200; в браузере #32 играет в 1280×720,
`readyState=4`, время воспроизведения растёт. Кодеки рабочих камер не менялись.
Нужны отдельное решение совместимости H.265, правильная диагностика отказа муксера
и получение preview для record_only без включения распознавания на всём парке.

## D05. Архив приписывает файлу отсутствующее видео; экспорт получается коротким — остаётся

**Серьёзность:** высокая: шкала и контроль пропусков могут скрывать потерянные секунды.

После сбоев MediaMTX сегмент #1163 камеры #32 имеет начало 11:24:26 UTC,
следующий #2223 — 11:24:39 UTC. В БД первому назначены 13 секунд, хотя
`ffprobe` показывает **7.601 секунды**. Второй файл корректный — **300.120 секунд**.

`worker/record_layer.py:collect_complete_segments` вычисляет конец по началу
следующего файла, а не по фактической длительности видео. После обрыва это
превращает отсутствие видео в фиктивное покрытие архива.

Воспроизведение экспорта: камера #32, окно **2026-10-28 11:24:34–11:24:44 UTC**,
граница сегментов #1163/#2223. API отвечает 200 за 0.241 с, но скачанный MP4
имеет длительность **5.800 с вместо 10 с**. Об успешности по одному HTTP 200 судить нельзя.
Мониторинг в этот момент показывает «Пропусков записи: 0».
Нужны фактическая длительность закрытых файлов, корректные границы/пропуски и
проверка длительности результата экспорта.

## D06. Норматив аналитики ≥5 FPS не выполнен на двух выбранных камерах

В нескольких замерах: камера #1 — примерно **1.9–3.17 FPS**, #2 — **0.96 FPS**.
У #1 используется субпоток 720×576; у #2 субпоток 640×360 ниже порога,
и мониторинг подтверждает переход на основной поток.
Это результат текущего профиля и выделенных ресурсов на этом ПК, не универсальная
оценка проекта. Подменять его скоростью синтетического теста нельзя.
`perf/bench.py --json` выполнен; его inference использует синтетическую сеть,
что прямо указано в JSON. Распознавание на реальных лицах не подтверждено: в тесте нет эталонного набора.

## D07. Свободное место Docker-тома не равно месту на диске Windows

**Эксплуатационный риск:** мониторинг сообщает около 925 ГБ свободно из 1007 ГБ,
тогда как на единственном физическом томе C: до сборки было около 378 ГБ.
Видно виртуальную ёмкость WSL2, а не фактический предел расширения VHDX на Windows.
Прогноз «хватит на сотни суток» после нескольких минут записи также нельзя
принимать за суточную калибровку. Нужны контроль хостового диска и отдельный том архива.

## D08. Frontend ложно unhealthy из-за IPv6 localhost — исправлено

Финальная проверка обнаружила `unhealthy` при работающем интерфейсе.
Healthcheck использовал `wget --spider http://localhost/`; в контейнере BusyBox
выбирал `::1`, а nginx слушал только IPv4. В журнале healthcheck — `Connection refused`.
Контрольный запрос к `127.0.0.1:80` вернул 200, к `[::1]:80` — отказ.
Healthcheck изменён на `http://127.0.0.1/`; сам nginx и настройки камер не менялись.

## D10. JWT попадает в журнал backend через WebSocket URL

При открытом интерфейсе строка подключения /ws/faces?token=… в журнале uvicorn содержит полный JWT. Значение намеренно не приводится. Редактирование query в nginx не защищает собственный журнал backend. Доступ к журналу позволяет получить действующий токен до истечения срока. Нужна фильтрация параметра token в backend-логировании и регрессионная проверка WebSocket handshake.

## D11. Фото-поиск с датой и часовым поясом возвращает HTTP 500

Воспроизведение: POST /api/search/face, стандартное тестовое JPEG, поле date_from=2026-10-28T00:00:00+05:00. Ожидалось приведение даты к UTC и корректная выдача. Получено HTTP 500, asyncpg DataError: cannot subtract offset-naive and offset-aware datetimes. Причина: search.py передаёт datetime с tzinfo в параметры запроса к колонке timestamp without time zone без нормализации, которая используется в архивном экспорте. Три отдельных повторения дали HTTP 500; следующие корректные запросы limit=1 в каждом повторе дали HTTP 200.

В первом прогоне сразу после 500 наблюдался одиночный 502 с recv() failed (104: Connection reset by peer) в nginx; в трёх повторениях 502 не воспроизвёлся, поэтому самостоятельная устойчивая ошибка limit=1 не заявляется. Пункт поиска с фильтрами остаётся открытым из-за воспроизводимой ошибки часового пояса.
