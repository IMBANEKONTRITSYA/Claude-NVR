# Чек-лист первого развёртывания на реальном сервере

Этот файл — про то, **что проверяется только глазами на живом железе**.
Всё, что можно проверить тестом, проверено тестом; здесь остаётся то, чего
песочница разработки дать не может: нет Docker-демона, нет GPU, нет
сотни камер, нет диска на десятки ТБ и нет процессора верхнего класса
объектов (2× Xeon E5-2670 **без AVX2** — любой современный хост даёт
завышенные числа).

Каждая строка ведётся как открытый пункт до тех пор, пока её не проверил
человек на сервере. Проверенное — вычёркивать (`~~строка~~`) с датой, а не
удалять: следующий цикл должен видеть, что именно уже подтверждено.

**Класс объекта (SPEC §20).** Редакция «Production NVR Edition»
(2026-08-16) сняла единственный целевой сервер и задала три класса:
малый (12–32 камеры, N100/Celeron, 8–16 ГБ), средний (32–128, i3–i5,
32–64 ГБ), большой (128–256+, Xeon/EPYC, 64–256 ГБ). Числа ниже
проверялись против большого класса — 2× Intel Xeon E5-2670 (32C/64T),
128 GB DDR3, без GPU, RAID на десятки ТБ, сеть 1 Gbps.

**Способ развёртывания (SPEC §26).** Production — это **.deb-пакет +
systemd**, Docker Compose остаётся режимом разработки, тестирования и CI.
Пакет есть с цикла 46 (`packaging/`, инструкция —
[INSTALL_LINUX.md](INSTALL_LINUX.md)), и install-тест на раннере с
systemd гоняется в CI (джоба `deb`). **Проверять на объекте надо именно
его** — раздел 0.1 ниже. Раздел 0 (Docker Compose) остаётся для стенда.

## 0. Перед запуском

- [ ] `.env` заполнен из `.env.example`; **`SECRET_KEY`, `ADMIN_PASSWORD`,
      `RTSP_ENCRYPTION_KEY` заменены** на собственные значения.
      `ALLOW_INSECURE_DEFAULT_SECRETS` в проде **не выставлять**.
- [ ] Каталог `/media` смонтирован на большой том (не на системный диск) и
      доступен на запись контейнерам.
- [ ] **Раздел с базой и раздел с архивом зашифрованы (LUKS).** §24
      требует хранить биометрию в зашифрованном виде, и на уровне
      приложения это требование закрыть нельзя: эмбеддинги лежат в
      колонке `vector(512)`, по ней идёт HNSW-поиск, а зашифрованный
      вектор не сравнивается — шифрование поля стоило бы норматива §19
      «поиск по фото ≤ 3-5 с». Значит, носитель: `lsblk -o NAME,FSTYPE`
      — под разделами PostgreSQL (`/var/lib/postgresql`) и архива
      (`/var/lib/facewatch`) обязан быть `crypto_LUKS`. Снимки лиц лежат
      файлами в архиве, поэтому одного шифрования базы мало.
- [ ] Часы сервера синхронизированы (NTP). Столбцы `video_segments`
      наивные и хранят UTC; расхождение часов ломает и границы экспорта
      фрагмента, и выборку архива.
- [ ] `docker compose up -d` отработал; `docker compose ps` — все сервисы
      `healthy`, включая `mediamtx`.

## 0.1. Production-установка: .deb + systemd (SPEC §26)

Этот раздел заменяет раздел 0 на объекте: там Docker Compose, здесь пакет.
Всё, что перечислено, проверяется в CI на раннере с systemd
(`packaging/install-test.sh`, джоба `deb`), но раннер — не объект: у него
нет ни отдельного массива под архив, ни камер, ни суток аптайма.

- [ ] `sudo apt install ./facewatch_*.deb` прошёл без ошибок и **без
      вопросов про conffiles**. Вопрос про изменённую конфигурацию на
      первой установке означал бы, что пакет правит собственный conffile —
      этого быть не должно.
- [ ] `systemctl status facewatch.target` — все четыре сервиса `active
      (running)`, `facewatch-first-run` — `active (exited)`.
- [ ] Через 5 минут после старта `systemctl show -p NRestarts
      facewatch-worker facewatch-backend facewatch-mediamtx` — везде 0.
      Ненулевое значение при внешне живом сервисе — CrashLoop, который
      `Restart=always` маскирует.
- [ ] `journalctl -u facewatch-backend -n 50` — структурированный JSON, а
      не голый текст: логи объекта уходят в journal (SPEC §26), и парсер
      сборщика логов рассчитывает на JSON.
- [ ] Вход `admin` паролем из `/etc/facewatch/ADMIN_PASSWORD` работает;
      **пароль сменён в интерфейсе, файл удалён**.
- [ ] `sudo -u postgres psql -d facewatch -c '\dt'` — таблицы созданы;
      `select extversion from pg_extension where extname='vector'` — не
      пусто.
- [ ] **Архив на отдельном диске.** `MEDIA_PATH` в
      `/etc/facewatch/facewatch.env` и `recordPath` в
      `/etc/facewatch/mediamtx.yml` указывают в один и тот же каталог, и
      это точка монтирования массива, а не корневой SSD. Владелец —
      `facewatch:facewatch`. Разъехавшись, они дают растущие файлы при
      пустом `video_segments` (класс дефекта цикла 39).
- [ ] Лимиты systemd не режут объект: `systemctl show -p CPUQuotaPerSecUSec
      -p MemoryMax facewatch-worker`. Значения пакета взяты из
      docker-compose (6 ядер / 4 ГБ на аналитику, 4 / 2 ГБ на запись) и
      рассчитаны на средний класс §20; на 120+ камерах их **надо поднять**
      через `systemctl edit facewatch-worker`, иначе MemoryMax убьёт
      воркер под нагрузкой, а CPUQuota просто не даст ему считать.
- [ ] Перезагрузка сервера: `reboot`, после загрузки все сервисы поднялись
      сами и запись возобновилась. Это единственная проверка `WantedBy`,
      порядка `After=` и того, что `facewatch-first-run` переживает
      старт, когда PostgreSQL поднимается одновременно с ним.
- [ ] Апгрейд на объекте: поставить следующую версию пакета поверх, после
      чего — секреты те же (`/etc/facewatch/facewatch.env` не изменился),
      старая сессия в браузере не разлогинилась, архив на месте, в
      `video_segments` нет разрыва длиннее перезапуска сервисов.
- [ ] Профиль сборки — `full`. Апскейл лиц (§15) в профиле `core` не
      работает: `journalctl -u facewatch-upscaler` покажет
      `ModuleNotFoundError: No module named 'gfpgan'`.
- [ ] Если объект изолирован: веса модели лежат в
      `/var/lib/facewatch/.insightface`, и в журнале воркера есть «модель
      готова», а не сообщение о неудачной загрузке.
- [ ] TLS: самоподписанный сертификат заменён на боевой (SPEC §26), nginx
      перезагружен, браузер не ругается.
- [ ] Дефолтный сайт nginx отключён установкой — убедиться, что на этой
      машине он не был нужен под что-то ещё.

## 1. Слой записи: MediaMTX (SPEC §2, §20)

Самый важный блок. С цикла 39 часть его проверяется автоматически: джоба
CI `record-layer-live` поднимает **настоящий** MediaMTX (статический
бинарник, Docker для него не нужен — это выяснилось только в цикле 39,
до того пункт много циклов числился как «в песочнице нет Docker») и
сверяет заведение пути, идемпотентность синхронизации, каталог и имя
сегмента, remux вместо транскода и отбор дописанного сегмента.

Ниже остаётся то, чего раннер дать не может: настоящие камеры объекта, их
битрейты, их число и диск. Всё это проверяется первым.

- [ ] **Воркер вообще пускают в Control API.** Проверять ПЕРВЫМ: если
      здесь отказ, все пункты ниже провалятся сразу, а симптомы на
      причину не указывают. С хоста (loopback пускают без пароля):
      `curl -s http://127.0.0.1:9997/v3/config/paths/list` — должен быть
      JSON, а не `{"error":"authentication error"}`. Из контейнера
      воркера, то есть так, как ходит он сам:
      `docker compose exec worker python -c "import os;from record_layer
      import MediaMTXClient;print(MediaMTXClient(os.environ['MEDIAMTX_API_URL']).runtime_paths())"`.
      **HTTP 401 здесь — это цикл 34:** права `action: api` в
      `authInternalUsers` не выданы адресу, с которого пришёл воркер, либо
      `MEDIAMTX_API_PASSWORD` в `.env` разошёлся между сервисами
      `mediamtx` и `worker`. Healthcheck контейнера при этом зелёный — он
      ходит с loopback и отказа не видит. Внешние признаки: все камеры
      «offline», чёрный экран на всей стене, пустой архив; камера,
      переключённая в `analytics`, показывает `online` (нить аналитики
      открывает RTSP мимо MediaMTX) — это и есть подпись отказа.
- [ ] **Версия MediaMTX — та, что в docker-compose.yml.**
      `docker compose exec mediamtx /mediamtx --version`. Тег
      зафиксирован осознанно: между выпусками менялись и набор прав
      Control API, и форма значений в ответе (`recordDeleteAfter: 0s` в
      v1.9.3 против `""` в v1.16.0 — из-за этого синхронизация путей
      патчила все пути каждые 10 с). После смены версии прогнать
      `worker/tests/test_record_layer*.py` и этот раздел заново.
- [ ] **Путь появился в конфигурации.** На сервере:
      `curl -s http://127.0.0.1:9997/v3/config/paths/list | jq '.items[].name'`
      — по пути на каждую включённую камеру.
- [ ] **Поток реально читается.**
      `curl -s http://127.0.0.1:9997/v3/paths/list | jq '.items[] | {name, ready, tracks}'`
      — `ready: true` у камер, которые в сети.
- [ ] **Каталог записи и каталог архива — один и тот же.** Первым делом,
      до всего остального: в журнале воркера при старте есть строка
      `слой записи: каталоги сегментов` с полями `mediamtx_record_path` и
      `indexer_scan_dir`. Они обязаны указывать в одно место.
      `journalctl -u facewatch-worker | grep 'каталоги сегментов'` (режим 2
      §26) либо `docker compose logs worker | grep 'каталоги сегментов'`.
      До цикла 39 путь MediaMTX был захардкожен `/media/segments`
      независимо от `MEDIA_PATH`, и вынос архива на отдельный диск (§5)
      давал пустой `video_segments` при растущих файлах на старом диске.
      Если задан `MEDIAMTX_MEDIA_PATH` (MediaMTX видит том по своему
      пути), на карточке «Слой записи» висит оранжевое предупреждение —
      убедиться, что оба пути ведут на один том, и только тогда его
      игнорировать.
- [ ] **Сегменты растут на диске.** `ls -la $MEDIA_PATH/segments/` дважды с
      интервалом в минуту: файлы `cam{N}_{unix_ts}.mp4` появляются и
      увеличиваются. Имя и путь заданы `recordPath`, который воркер
      выводит из `MEDIA_PATH` (`worker/record_layer.py:record_path_template`).
- [ ] **Строки доезжают в БД.**
      `SELECT camera_id, count(*), max(started_at) FROM video_segments GROUP BY 1;`
      — растёт для каждой пишущей камеры. Пустая таблица при растущих
      файлах означает, что до БД не доходит именно индексация сегментов.
- [ ] **Карточка «Слой записи»** в разделе «Мониторинг» показывает то же
      самое: число активных потоков из общего числа камер, и статус
      `пишется` у конкретной камеры. Если карточка говорит «данных нет» —
      не работает воркер (данные кладутся им в Redis с TTL 120 с), а не
      запись.
- [ ] **Реконнект.** Выдернуть питание/сеть у одной камеры: статус
      уходит в `offline`, в журнале появляется алерт потери потока,
      после возврата поток поднимается без перезапуска сервисов.
      Норматив «≤ 5 с» — из **§19**, а не §26 (§26 — про способы
      развёртывания). Цикл 40 замерил 6.6 с (не выполнялся), цикл 43
      добавил супервизор восстановления и замерил **3.59 с худшее** —
      норматив выполняется в песочнице; на объекте перепроверить, см.
      раздел 6.
- [ ] **Статус камеры на обрыве действительно меняется.** Проверять
      именно глазами и именно на обрыве: до цикла 43 слой записи читал
      живость потока из поля `online` Control API, а оно у пути со
      статическим источником **не падает никогда** — потерянная камера
      оставалась «пишется» до бесконечности, алерта §14 не было, и
      «Принято» показывало 0 МБ на закреплённой v1.16.0. Если на объекте
      это вернулось (например, после обновления MediaMTX) — смотреть
      `record_status.path_live()` и поля `available`/`ready` в
      `curl .../v3/paths/list`.
- [ ] **Супервизор восстановления работает и не шумит.** В журнале
      воркера на старте — `супервизор восстановления потоков запущен`;
      на обрыве и возврате камеры — ровно одна строка
      `поток записи: камера ответила, пересоздаю путь` на камеру, а не
      поток таких строк. Много пинков подряд по одной камере означает,
      что камера отвечает по RTSP, а MediaMTX её всё равно не тянет
      (сменился пароль/путь в URL/кодек) — чинить надо это, а не пинки.
      Выключатель на объекте: `RECORD_RECOVERY_INTERVAL=0`.
- [ ] **Массовый обрыв: моргнуть коммутатором, а не одной камерой.**
      Норматив §19 написан ровно про этот отказ, и мерить его надо на нём:
      снять питание с коммутатора, вернуть, засечь, за сколько поднимется
      **последняя** камера. В песочнице проход опроса стал неблокирующим
      (цикл 48): 600 «камер» опрашиваются одним потоком за 2.09 с против
      4.12 с пулом нитей, восстановление 2.50 с против 6.40 с (§19
      нарушался). На объекте иначе: между воркером и камерами настоящая
      сеть, и обрыв даёт не «молчание», а смесь молчания, ICMP-отказов и
      подвисших TCP. Проверить, что `probes_failed` в карточках камер
      растёт, а не стоит, и что журнал не сыплет пинками (строка выше).
- [ ] **Лимит дескрипторов воркера.** Опрос держит по сокету на камеру в
      обрыве (до `PROBE_SOCKETS_MAX` = 1024). На объекте больше 700 камер
      сверьте `LimitNOFILE` юнита воркера с числом камер плюс запас на
      захваты аналитики и соединения с БД: `systemctl show
      facewatch-worker -p LimitNOFILE`.
- [ ] **«Камера отвечает» на карточке камеры соответствует правде.** На
      мониторинге у потерянной камеры теперь есть строка «камера
      отвечает по RTSP» / «камера не отвечает по RTSP». Сверить с
      фактом: физически выключенная камера обязана показывать вторую.
- [ ] **Запись не перекодируется.** `ffprobe` любого сегмента: кодек тот
      же, что у камеры (H.265), битрейт близок к 2048 kbps. Любой признак
      перекодирования — нарушение §24 и мгновенный перерасход CPU.
- [ ] **Только основной поток.** Субпоток в архив попадать не должен
      (§20): в `/media/segments` не должно быть файлов с CIF-разрешением.

### 1.1 FPS и битрейт потоков на «Мониторинге» (SPEC §9)

Столбцы появились в цикле 52: до него из трёх величин, которые §9
называет поимённо («онлайн/оффлайн, FPS, битрейт»), слой записи отдавал
одну. Обе новые считаются в песочнице на настоящем MediaMTX, но
правдивость чисел на боевом парке проверяется только глазами.

- [ ] **Битрейт совпадает с тем, что настроено на камере.** Открыть
      «Мониторинг» → «Все потоки» и сверить столбец «Битрейт» с профилем
      камеры (обычно 2048 кбит/с на 720p H.265). Расхождение вдвое и
      больше — либо камера отдаёт не тот профиль, либо в архив идёт не
      основной поток. **Это и есть та величина, ради которой столбец
      заведён:** камера, отдающая 200 кбит/с вместо четырёх мегабит, по
      прежнему столбцу «Принято, МБ» неотличима от исправной.
- [ ] **Суммарный «Входящий поток» сверить с §16.** Карточка показывает
      сумму по измеренным камерам и их число. Когда измерены все, сумма —
      это фактическая нагрузка на сеть; §16 требует канал с запасом 10 %.
      Сразу после старта воркера часть камер ещё не измерена — смотреть
      надо на подпись «измерено камер: N из M», а не на саму сумму.
- [ ] **FPS появляется не сразу и это норма.** Он снимается с последнего
      **дописанного** сегмента, поэтому у только что добавленной камеры
      стоит прочерк до первого переворота файла (5-10 минут по §20).
      Прочерк на камере, которая пишется давно, — уже симптом: смотреть
      `ffprobe` руками по её последнему сегменту.
- [ ] **`ffprobe` доступен воркеру.** Без него столбец «FPS» навсегда
      останется прочерком **на всех камерах**, и ничего больше не
      сломается — отказ, который сам о себе не сообщает. Проверить так,
      как ходит сам воркер: `systemctl show facewatch-worker -p
      ExecStart` и затем `sudo -u facewatch ffprobe -version`. В .deb
      `ffmpeg` объявлен зависимостью пакета, в docker-режиме лежит в
      образе воркера.
- [ ] **«Данных нет» на камере со статусом «онлайн».** Красная пометка
      рядом с нулевым битрейтом означает: путь заведён и MediaMTX считает
      его живым, а байты не идут. До появления битрейта это состояние в
      интерфейсе не отображалось вовсе. Если оно висит — смотреть
      раздел 1 сверху, начиная с прав в Control API.

## 2. Live-просмотр (SPEC §4, §19)

- [ ] **Задержка ≤ 3 с.** Секундомер (или телефон с бегущими секундами) в
      кадре камеры против картинки в браузере. Мерить на сетке и в
      полноэкранном режиме. *Норматив §26 в песочнице не измерялся — нужен
      реальный RTSP-поток и браузер.*
- [ ] **Мозаика 1/4/9/16 (§4)** переключается кнопками, страницы листаются,
      и на экране действительно не больше выбранного числа плееров. Проверить
      на объекте целиком: до цикла 28 стена поднимала плеер на **каждую**
      камеру, и на сотне камер вкладка вставала. Смотреть в диспетчере задач
      браузера: память вкладки не должна расти при листании страниц —
      уходящие плитки обязаны отдавать HLS-соединение.
- [ ] **Цифровой зум (§4)**: колесо мыши на плитке увеличивает кадр,
      кадр тянется мышью и не уезжает за край, бейдж кратности
      сбрасывает зум. Рамки лиц на камере `analytics` должны
      увеличиваться **вместе** с кадром, а не оставаться на месте.
      *Логика проверена тестами vitest, поведение в браузере на живом
      HLS-потоке — нет.*
- [ ] **PTZ-управление (§4)** — реализовано (цикл 30), но ни разу не
      работало против настоящей поворотной камеры: в песочнице проверен
      только протокол по спецификации ONVIF PTZ. Что смотреть глазами:
      - пульт появляется **только** у развёрнутой камеры с настроенным
        ONVIF и только если камера поворотная (у фиксированной его не
        должно быть вовсе — это ответ `supported: false`, а не ошибка);
      - стрелки двигают купол в ту сторону, которая на них нарисована.
        Перепутанный знак `tilt` — самая вероятная разница между
        прошивками, и логикой она не ловится;
      - **удержание и отпускание**: пока кнопка нажата, движение
        непрерывное (без рывков на границе 500 мс), после отпускания
        камера встаёт сразу, а не доезжает;
      - **страховка от «зависшего» поворота**: зажать стрелку и закрыть
        вкладку не отпуская. Камера обязана остановиться сама в пределах
        ~2 с (`PTZ_MOVE_TIMEOUT_SEC` в ONVIF-команде). Если продолжает
        крутиться — прошивка игнорирует `Timeout` в ContinuousMove, и это
        надо знать до сдачи объекта;
      - пресеты: «Запомнить» сохраняет позицию **в самой камере** (она
        переживает перезапуск FaceWatch), переход по списку наводит на
        неё;
      - наблюдателю пульт не показывается, а прямой запрос к
        `/api/cameras/{id}/ptz/move` отвечает 403.
- [ ] **Один pull с камеры на всех зрителей** (§4): открыть одну камеру в
      трёх вкладках и убедиться по `/v3/paths/list`, что число читателей
      растёт, а подключений к самой камере — нет.
- [ ] Bounding box'ы видны только на камерах в режиме `analytics`.

### 2.1 Расписание детекции (SPEC §6)

- [ ] **Окно закрывается.** Задать камере `analytics` окно, которое
      кончается через пару минут, и дождаться границы. Ожидаемое: в логе
      воркера «вне окна расписания детекции, аналитика приостановлена»,
      `worker:fps` по камере обнуляется, а **статус камеры остаётся
      прежним** — алерта о потере потока (§9) быть не должно. Запись при
      этом не прерывается: сегменты в `/media/segments` продолжают расти.
- [ ] **Окно открывается само.** Дождаться начала окна не перезапуская
      воркер: аналитика обязана возобновиться в пределах ~30 с
      (`SCHEDULE_POLL_SEC`), в логе — «окно расписания открылось».
- [ ] **Ночное окно.** Завести 22:00–06:00 и убедиться, что детекция идёт
      и до полуночи, и после неё. Это главный риск функции: наивная
      реализация не срабатывает ни одной ночи, а выглядит это как «камера
      ничего не видит», а не как ошибка расписания.
- [ ] **Часовой пояс сервера.** Окна считаются по локальному времени
      процесса воркера (как и расписание отчётов §8). Сверить `date` на
      сервере с ожиданиями администратора объекта до настройки окон.
- [ ] **Экономия ресурсов.** Снять `top`/`htop` по процессу воркера внутри
      окна и вне его — вне окна должен уходить не только детектор, но и
      декодирование (захват отпускается). Это же и есть способ измерить
      §19 «CPU ≤ 80 %» на реальном парке камер.

### 2.2 Запись только при движении (SPEC §6)

Режим включается галочкой в форме камеры `analytics` («Хранить только
запись с движением»). Он **удаляет уже записанное**, поэтому проверять его
надо на одной камере и на коротком горизонте, а не сразу на парке.

- [ ] **Отметки наблюдения пишутся.** Через 2–3 минуты после старта
      аналитики: `SELECT camera_id, count(*), max(ended_at) FROM
      motion_windows GROUP BY 1` — строки идут по минуте на камеру.
      Пусто — значит нить камеры не доходит до префильтра (смотреть логи
      воркера), и в этом состоянии режим ничего не удаляет (так и
      задумано).
- [ ] **Движение отмечается тем, что им является.** Пройти перед камерой,
      затем `SELECT started_at, motion FROM motion_windows WHERE
      camera_id = N ORDER BY started_at DESC LIMIT 5` — окно с проходом
      обязано иметь `motion = true`. Если у камеры включён ONVIF, движение
      берётся из событий камеры, а не из MOG2: проверить, что события
      вообще приходят (иначе весь архив будет считаться пустым).
- [ ] **Пустые фрагменты уходят, фрагменты с движением остаются.**
      Оставить камеру на час в пустом помещении, затем сверить
      `video_segments` с фактическим содержимым: сегменты со временем
      прохода должны остаться, соседние — исчезнуть. Уборка идёт раз в
      5 минут и судит только сегменты старше 5 минут.
- [ ] **Простой аналитики не стирает архив.** Остановить воркер на 10–15
      минут при работающем MediaMTX, поднять обратно и убедиться, что
      сегменты за время простоя **остались**: «не смотрели» не то же
      самое, что «движения не было». Это главный риск режима, и проверять
      его нужно именно так — отдельным опытом, а не наблюдением.
- [ ] **Фактическая экономия диска.** Сравнить суточный расход камеры с
      режимом и без (раздел «Мониторинг» → расход за сутки). Ожидание по
      §16 не задано: экономия целиком определяется тем, сколько на объекте
      реального движения.

## 3. Слой аналитики (SPEC §15, §19)

- [ ] **Детекция ≥ 5 FPS/канал** на камерах `analytics` — раздел
      «Мониторинг», фактический FPS по камере. *В песочнице цепочка целиком
      (decode → префильтр → детектор → эмбеддинг, реальная `buffalo_s`,
      один поток, кадр с шестью лицами) даёт **8.4 FPS/канал** — норматив
      выполняется с запасом 1.7×. Но у хоста песочницы есть AVX2, а у
      E5-2670 нет, и запас в 1.7× он может съесть целиком: это первый
      норматив, который стоит перемерить на сервере.*
- [ ] **Проверить, что запас не съеден числом лиц в кадре.** Замер сделан
      на шести лицах одновременно — заведомо тяжёлый план. Эмбеддинг
      считается на каждое лицо, поэтому проходная с толпой дороже, чем
      коридор с одним человеком. На объекте смотреть фактический FPS на
      самой людной камере, а не на средней.
- [ ] **Бенчмарк на самом сервере:** `python perf/bench.py --json` прямо на
      целевом железе. Строка `AVX2: НЕТ` подтверждает, что числа наконец
      сняты с нужного процессора. Сравнить с таблицей последнего отчёта
      цикла — числа обязаны просесть, вопрос насколько.
- [ ] **Пересчёт профилей производительности под целевой CPU (§19).**
      Числа внутри `economy`/`standard`/`maximum` (`backend/app/profiles.py`)
      подобраны как связные наборы «дешевле/дороже», а НЕ выведены из замера:
      инференс на E5-2670 без AVX2 в песочнице не воспроизводится. Сняв
      фактические ms/лицо предыдущим пунктом, проверить на реальной нагрузке,
      что «Максимальный» (детектор по каждому кадру, `buffalo_l`, кадр 960 px)
      укладывается в бюджет §23 — 2–3 ядра на аналитику при общем потолке
      20% CPU (§26). Если не укладывается — правится словарь `PROFILES`,
      подписи в `routers/settings.py` при этом не трогаются: они описывают
      поведение, а не железо.
- [ ] Смена профиля **не влияет на запись** (§19, §2): переключить профиль
      при работающей записи и убедиться, что сегменты продолжают расти без
      пропусков.
- [ ] Известные лица распознаются, неизвестные заводятся автоматически;
      лента «Стены» наполняется только с `analytics`-камер.
- [ ] Отказ аналитики **не влияет на запись** (§2): остановить воркер и
      убедиться, что сегменты продолжают расти.

## 4. Архив, хранение, retention (SPEC §5, §7)

- [ ] Плеер играет сегмент; фильтры по камере/дате/персоне работают.
- [ ] **Поиск по архиву ≤ 5 с на 500 000 сегментов (§7)** на боевой базе.
      В песочнице измерено (2026-08-16) на 504 000 сегментах — объёме
      самого норматива, а не выведенном из числа камер: худший фильтр
      21.6 мс при нормативе 5 с. На сервере число будет выше — слабее single-thread и
      диск под нагрузкой записи 120 потоков, — но запас двухпорядковый.
      Повторить замер: `BENCH_DATABASE_URL=... python perf/bench.py --only archive`.
      Смотреть не только на секунды, но и на пометку `Seq Scan` в выводе:
      фильтр по типу события идёт полным перебором, и если объём вырастет
      против расчётного, просядет первым.
- [ ] **Экспорт фрагмента** (§5): выбрать окно, накрывающее **границу двух
      сегментов**, скачать и открыть файл. Проверить, что фрагмент один,
      играется целиком и по длительности близок к запрошенному (начало
      может быть на 1–2 с раньше — рез идёт по опорным кадрам, §24
      запрещает перекодирование). *В песочнице проверено на синтетических
      MP4; на реальных H.265-сегментах MediaMTX не проверялось.*
- [ ] **Покадровый просмотр в плеере (§5).** Логика проверена и юнит-тестами,
      и в **настоящем Chromium** (Playwright, 2026-08-17): 10 нажатий
      «вперёд» и 10 «назад» дали ровно по одному кадру, картинка менялась
      на каждом шаге. Но проверка шла на **VP9/WebM**: у Chromium в
      песочнице нет проприетарных кодеков (`canPlayType` для H.264 пуст),
      а архив пишется в H.264/H.265. На сервере проверить на настоящем
      сегменте:
      - кнопки «◀ кадр» / «кадр ▶» и стрелки ← → двигают **ровно на один
        кадр** в обе стороны, картинка меняется на каждом нажатии.
        Топтание на месте означает, что замер длительности кадра не
        набрался (нет `requestVideoFrameCallback` или сегмент открыт на
        паузе с самого начала) — тогда шаг идёт от запасных 1/15 с;
      - подпись «N.NNN с · кадр K» — **оценка**: точной частоты кадров у
        системы нет, в `video_segments` её не хранится. Смотреть надо на
        то, что номер меняется на единицу, а не на его абсолютное
        значение;
      - скорости 0.25×–4× переключаются и звук/картинка не рассыпаются;
      - H.265 с длинным GOP: шаг **назад** — самая дорогая операция для
        декодера (перемотка к опорному кадру и проигрывание вперёд). Если
        на объекте он ощутимо медленный, это ограничение кодека, а не
        логики.
- [ ] **Миниатюры кадров в выдаче архива (§7).** В песочнице измерено
      (2026-08-17) на синтетическом 720p H.265: холодная миниатюра
      112 мс, кэш-хит 2 мкс, JPEG 5.5 КБ. На сервере смотреть три вещи:
      - картинка **осмысленная**, а не чёрный прямоугольник. Кадр берётся
        на 1-й секунде сегмента именно ради этого (первый кадр часто снят
        в момент переключения ИК-подсветки), но у конкретных камер
        установление экспозиции может занимать дольше — тогда
        `THUMB_OFFSET_SEC` в `backend/app/services/thumbs.py` поднять;
      - каталог `<media>/thumbs/` **не растёт бесконечно**: миниатюра
        удаляется вместе со своим сегментом ротацией воркера. Проверить
        после первого срабатывания retention — `du -sh` до и после;
      - потолок `THUMB_CONCURRENCY = 4` (одновременных ffmpeg). Это
        осознанно консервативно ради §19 «CPU ≤ 80 %»: полностью холодная
        страница из 200 строк заполняется за 10 с. Реально браузер тянет
        только видимые строки (`loading="lazy"`), то есть ~15 штук. Если
        на объекте прокрутка выдачи ощутимо отстаёт, а запас CPU есть —
        поднимать этот потолок, **сверяясь с нагрузкой слоя аналитики**:
        §2 требует, чтобы слои не отнимали ресурсы друг у друга.
- [ ] **Прогноз места** («на сколько хватит») в разделе «Мониторинг»
      правдоподобен после суток работы.
- [ ] **Калибровка после 24 ч** (§21): строка «Калибровка» в карточке
      «Хранилище архива». Отклонение факта от номинала сильно выше 100%
      означает, что камеры отдают битрейт выше расчётного.
- [ ] **Retention удаляет старые сегменты** — и глобальный срок, и
      переопределение по камере.
- [ ] **Циклическая перезапись на настоящем переполнении.** Логика
      проверена только на подменённом `disk_usage`. На сервере — смотреть
      в журнале воркера `warning` с полями `segments_removed` / `free_pct`.
- [ ] Алерты о заполнении диска приходят на 80% и 90%.

## 5. Поиск по фото (SPEC §15, §19)

- [ ] **≤ 3–5 с на базе до 100 000 лиц.** *Измерено в песочнице
      (2026-08-16): 517 мс до перехода на HNSW-индекс, 2.0 мс после, при
      100 000 эмбеддингов.* На сервере проверить на **реальной** базе: под
      нагрузкой записи 120 камер и на более слабом CPU числа будут выше.
- [ ] `EXPLAIN` production-запроса на сервере не содержит
      `Seq Scan on face_events` — то есть индекс действительно
      используется на боевых данных, а не только на засеянных.
- [ ] Поиск **с фильтрами** (по датам/статусу) идёт точным путём и не
      теряет совпадения — выдача не должна быть подозрительно короткой.

## 6. Ресурсы под полной нагрузкой (SPEC §19, §20)

- [ ] **Все камеры объекта на запись + камеры analytics, прогон 24 ч.**
      Без физических камер —
      генератор: `ffmpeg -re -stream_loop -1 -i sample.mp4 -c copy -f rtsp ...`
      на нужное число путей.
- [ ] **Удельная стоимость записи §19 «CPU ≤ 0.04 ядра/камера».**
      Готовый замер: `MEDIAMTX_BIN=/usr/local/bin/mediamtx python
      perf/bench_remux.py 1 16 64 120` — поднимает настоящий MediaMTX,
      публикует N потоков и меряет CPU **только его процесса**.
      В песочнице (цикл 32, 4 ядра, push вместо pull, без читателей live)
      вышло **0.007–0.011 ядра на камеру** при 1–16 камерах, то есть в
      3.6–5.5 раза ниже норматива. На сервере проверить именно с
      `pull` (`source: rtsp://камера`) и при работающем live-просмотре —
      ни того, ни другого замер песочницы не покрывает.
- [ ] **CPU ≤ 80 % при полной нагрузке, RAM ≤ 80 % доступной (§19).**
      Норматив сменился вместе с редакцией ТЗ: прежние «CPU ≤ 20 %» сняты,
      теперь §19 требует запас в 20 %, а не потолок в 20 %. Разложить по
      слоям и сверить с формулами §16: запись ~0.02–0.04 ядра на камеру,
      камера analytics ~0.5–1.5 ядра при 5 FPS, RAM ~50–100 МБ на камеру
      записи и 0.5–2 ГБ на камеру analytics.
- [ ] **0 пропущенных сегментов** за прогон: провалы во времени в
      `video_segments` по каждой камере.
- [ ] Диск переваривает sustained write ~30 MB/s (§20) без роста
      io-wait.
- [ ] Сеть: ~270 Mbps при базовой конфигурации (§22) — меньше трети
      гигабитного линка.
- [ ] **NUMA-привязка каналов аналитики (§17) — теперь в коде, но ни разу
      не проверена на двухсокетной машине.** Воркер сам читает топологию из
      `/sys/devices/system/node`, раскладывает камеры `analytics` блоками по
      нодам (§17: «камеры 1–60 на node 0, 61–120 на node 1» — но без
      зашитых чисел, границы считаются от фактического числа камер и нод) и
      привязывает нить каждого канала к ядрам её ноды перед первым кадром.
      `numactl` не нужен. Что проверить глазами:
      * **строка в журнале** `раскладка аналитики по NUMA` при старте
        воркера: `journalctl -u facewatch-worker | grep NUMA` (или
        `docker compose logs worker`). В ней `numa_nodes` обязано быть
        **2** на двухсокетном сервере, `cameras_per_node` — распределение
        камер. `numa_nodes: 1` на 2× Xeon означает, что сервис заперт в
        cpuset одной ноды (проверить `CPUAffinity=`/cgroup) — привязка
        тогда не нужна, но и §17 не выполняется;
      * **фактическая аффинность нитей:**
        `for t in /proc/$(pidof -s python3)/task/*; do taskset -cp
        ${t##*/}; done` — нити камер должны показывать ядра одной ноды,
        а не полный список;
      * **что это дало.** Снять FPS канала до и после: выключить привязку
        (`ANALYTICS_NUMA=off` в окружении воркера, перезапуск) и сравнить
        «Мониторинг → фактический FPS» на тех же камерах. **В песочнице и
        на раннерах CI выигрыш измерить невозможно — там ровно одна
        NUMA-нода**, и раскладка намеренно пуста. Это единственное число
        §17, которое существует только на объекте;
      * **веса модели остаются общими.** `FACE_APP` один на все каналы и
        лежит на ноде менеджера, то есть половина каналов читает веса
        через QPI. Разменяно на память: копия модели на канал — это
        ~430 МБ × число каналов (замерено, `perf/bench_scaling.py`). Если
        на объекте окажется, что это и есть узкое место, замер
        `bench_scaling.py --modes processes` показывает верхнюю границу
        альтернативы.
- [ ] **RTO ≤ 5 минут (§13, §19) на боевой базе.** Готовый замер:
      `python perf/bench_rto.py` — печатает разложение
      «обнаружение + рестарт + прогрев», а не одно число: слагаемые
      растут по разным причинам. В песочнице (цикл 34, пустая БД) вышло
      **6.6 с** при падении процесса и **96.6 с** при зависании, при
      нормативе 300 с. Что проверять именно здесь:
      * **прогрев на непустой схеме** — миграции идут по таблице
        `video_segments` в сотни тысяч строк; в песочнице она пуста;
      * **`docker compose kill backend`** и секундомер до первого
        успешного `/api/health` — сверить с расчётом;
      * **зависание, а не падение** — см. отдельный раздел 6.2 ниже.
        Здесь доминирует не healthcheck (Docker по нему контейнер не
        перезапускает), а пороги сторожа живости;
      * **восстановление MediaMTX** — в замер не входит вовсе: §19
        отдельно требует ≤ 5 с на восстановление потока, и после
        рестарта медиасервера надо засечь, за сколько поднимутся все
        пути (`/v3/paths/list`, поле `online`).

- [ ] **Восстановление потока ≤ 5 с после обрыва (§19) — в песочнице
      норматив выполняется с цикла 43; перепроверить на объекте.** Замер:
      `MEDIAMTX_BIN=... python perf/bench_recovery.py` (в CI — джоба
      `perf`, файлы `perf-recovery.txt` и `perf-recovery-baseline.txt`).
      Песочница, Intel Xeon @2.80GHz, одна камера 720p, MediaMTX v1.16.0:

      | обрыв, с | цикл 40 (без супервизора) | цикл 43 (супервизор) |
      |---|---|---|
      | 2 | 4.58 | 3.58 |
      | 5 | 6.58 | 2.51 |
      | 15 | 6.57 | 2.53 |
      | 30 | 6.60 | 3.59 |
      | **худшее** | **6.60 — не выполняется** | **3.59 — выполняется** |

      Восстановление считается от момента, когда камера **снова отдаёт
      поток**, до момента, когда её файл снова растёт, — то есть это
      добавка системы сверх самого обрыва.

      Откуда бралось прежнее число: MediaMTX повторяет попытку
      подключения к статическому источнику **раз в 5 секунд**, паузу эту
      настроить нельзя (в `mediamtx.yml` такого ключа нет), и она одна
      равна всему бюджету §19 — 5 с ожидания плюс ~1.6 с на подключение.
      Что изменилось: воркер опрашивает камеру сам
      (`worker/stream_recovery.py`, DESCRIBE без учётных данных) и, как
      только она ответила, пересоздаёт путь через `delete`+`add`, не
      дожидаясь очередной попытки сервера. Остаток 2.5–3.6 с — это пауза
      опроса (потолок 2 с) плюс те же ~1.5 с на подключение.

      **Экспоненциальная задержка §2/§13** — с цикла 43 есть, и на двух
      величинах: пауза опроса камеры растёт 0.25 → 2 с (потолок задан
      бюджетом §19), пауза пересоздания пути — 5 → 60 с (защита от
      бесконечных пинков по камере, которая отвечает, но не пишется).
      До цикла 43 её не было вовсе.

      Что проверить именно на объекте:
      * **то же число на настоящей камере.** В песочнице «обрыв» — это
        пропажа публикатора на localhost; на объекте пропадает сеть, и
        TCP-таймаут к недоступному хосту добавляет своё сверху;
      * **сколько на самом деле теряется архива.** Норматив ограничивает
        секунды, а оператору важны кадры: снять `ffprobe` по двум
        соседним сегментам вокруг обрыва и посчитать дыру;
      * **пачка реконнектов.** Мигнувший коммутатор роняет не одну
        камеру, а все; 120 путей, переподключающихся одновременно раз в
        5 секунд, — нагрузка, которой в замере одной камеры нет. С
        супервизором к ней добавляется опрос: до 120 DESCRIBE каждые 2
        секунды через пул из 16 нитей (`PROBE_WORKERS`). Снять в этот
        момент CPU воркера и убедиться, что пул не забит намертво
        молчащими камерами (каждая держит нить до `PROBE_TIMEOUT_SEC`);
      * **камера, отвечающая на RTSP, но не отдающая поток MediaMTX**
        (сменили пароль, профиль, кодек). Ожидаемое поведение: пинки
        затухают с 5 до 60 с, а в интерфейсе у камеры стоит «камера
        отвечает по RTSP». Если пинки идут чаще — задержка не работает.

### 6.1 Автоконфигурация §16 — сверка предложения с фактом

Экран «Автоконфигурация» (Мониторинг, только админ) считает пределы по
формулам §16 от **фактических** ресурсов сервера. Проверять его надо не
на «красиво ли выглядит», а на том, совпало ли предложение с тем, что
сервер вывез за сутки прогона выше — числа §16 это вилки из ТЗ, а не
замер на E5-2670 без AVX2.

- [ ] **Предложение прочитано до заведения камер.** На чистой установке
      панель показывается с меткой «первый запуск»; записать, что она
      предложила (камер записи / камер аналитики / профиль) — сравнивать
      с фактом будет уже не с чем, когда камеры заведут.
- [ ] **Связывающий ресурс назван верно.** На большом объекте ожидается
      «упирается в диск» (remux дёшев по CPU). Если панель говорит «в
      CPU» или «в оперативную память» — считать это сигналом, что
      `APP_CORES`/`APP_RAM_MB` (вычет под слой приложения,
      `services/autoconfig.py`) не отражают реальный расход
      PostgreSQL+Redis+nginx на этом сервере, и поправить их по факту.
- [ ] **Предложенное число камер записи против факта.** После суточного
      прогона: столько ли камер реально пишется без пропусков сегментов.
      Расхождение вниз (обещано больше, чем вывезло) — правка вилок §16 в
      `autoconfig.py` в сторону увеличения удельного расхода.
- [ ] **Предложенное число камер аналитики против факта**: держится ли
      детекция ≥ 5 FPS/канал (§19) на предложенном числе камер. Вилка §16
      «0.5–1.5 ядра на камеру» снята для MobileFaceNet на обычном CPU;
      на E5-2670 **без AVX2** фактический расход может оказаться выше
      верхней границы — тогда `ANALYTICS_CORES_PER_CAMERA` поднимать.
- [ ] **Предложение больше 16 камер аналитики — это ожидаемо, а не сбой.**
      До цикла 47 и предложение, и само поле «Камер в режиме аналитики»
      были ограничены числом 16, унаследованным от удалённой редакции ТЗ
      («2-3 ядра на аналитику»), хотя §22 запрещает хардкодить
      количество аналитики, а §1 делает его настройкой. На сервере из
      §20 калькулятор теперь предлагает столько, сколько проходит по
      ресурсам (на 2× E5-2670 со 128 ГБ — около 29). **Это число не
      проверено на живой аналитике ни разу**: замеры песочницы идут на
      1–4 каналах. На объекте включать аналитику не сразу на всё
      предложенное число, а ступенями (4 → 8 → 16 → предложенное),
      сверяя на каждой ступени фактический FPS по каналам в
      «Мониторинге» и темп сегментов в архиве (§2: аналитика не имеет
      права просадить запись). Ступень, на которой FPS упал ниже 5, и
      есть фактический предел этого сервера — его и выставить в
      настройке.
- [ ] **Совет про ускоритель показывается с 20 камер (§20).** Если
      предложение выше 20, рядом обязана быть строка «§20 рекомендует
      ускоритель свыше 20 камер». Её отсутствие означает, что расчёт
      считает ускоритель уже найденным (`detect_gpu()` нашёл
      `/dev/dri/*` там, где пригодного для инференса ускорителя нет), —
      тогда пределы по CPU завышены в 15 раз (§16: 0.1 ядра с GPU
      против 1.5 без).
- [ ] **Рекомендованный профиль против выбранного вручную.** Пороги
      (`PROFILE_CORES_MAXIMUM = 3.0`, `PROFILE_CORES_STANDARD = 1.5`)
      выведены из вилок §16 умножением на прикидочные множители
      профилей, а не измерены. Если оператор объекта в итоге работает на
      другом профиле, чем предложила система, — пороги врут, поправить.
- [ ] **Физические ядра посчитаны как ядра.** Панель показывает
      «N физ. ядер (M потоков)»: на 2× E5-2670 это должно быть
      «32 физ. ядра (64 потоков)». Если оба числа равны 64 — psutil на
      этом ядре Linux не различает HT, и все пределы завышены вдвое.
- [ ] **Кнопка «Применить» на живой системе**: профиль и предел камер
      аналитики доехали до воркера (~10 с), запись при этом не
      прерывалась ни на одной камере (§2 о независимости слоёв).

### 6.2 Сторож живости: класс отказа «сервис жив и не отвечает» (SPEC §13, §19)

До цикла 38 этот класс отказа не закрывал никто, и это стоит понимать
прежде, чем проверять. **Docker не перезапускает контейнер по красному
healthcheck** — он лишь метит его `unhealthy`; на `restart: unless-stopped`
это не влияет. Заблокированный сервис оставался в этом состоянии сколько
угодно, то есть настоящий RTO этого класса был бесконечным. У воркера было
хуже: его `/health` отвечал безусловным `{"ok": true}` из отдельной нити
uvicorn и не краснел вовсе, пока менеджер стоял.

Теперь перезапуском заведует сторож **внутри процесса**: он видит, что
менеджер (воркер) или цикл событий (бэкенд) не отмечался дольше бюджета,
сваливает стеки всех нитей в журнал и выходит с кодом **17**; на выход уже
реагирует `restart: unless-stopped`.

**Что проверить глазами:**

1. **Не срабатывает на здоровой системе.** Главное и самое скучное: за
   первые сутки в журнале не должно быть ни одной записи «этап менеджера
   превысил бюджет» и ни одного выхода с кодом 17
   (`docker inspect --format '{{.State.ExitCode}}' facewatch-worker`,
   `docker compose logs worker | grep -c 'превысил бюджет'`). Ложное
   срабатывание здесь опаснее отсутствия механизма: оно перезапускает
   работающую систему по кругу.
2. **Бюджеты этапов против фактических времён объекта.** Самое вероятное
   расхождение. В журнале воркера видны этапы; сравнить с бюджетами в
   `worker/liveness.py`:
   `record_layer_sync` 600 с — на 120+ путях MediaMTX; `cleanup` и
   `disk_quota` 900 с — часовая уборка архива это десятки тысяч `unlink()`
   по HDD. Если этап штатно подходит к бюджету — поднимать бюджет, а не
   отключать сторожа.
3. **Срабатывает, когда должен.** Проверять надо **не** `docker compose
   pause`: он останавливает SIGSTOP'ом весь контейнер вместе с нитью
   сторожа, и тот не сработает — это ничего не докажет. Достоверная
   проверка — блокировка внутри процесса: остановить контейнер Postgres
   правилом файрвола (`iptables -A INPUT -p tcp --dport 5432 -j DROP`) и
   убедиться, что воркер сначала краснеет по `/health` с именем этапа, а
   затем перезапускается с кодом 17 и стеками в журнале.
4. **Отсрочка против «рассасывающихся» зависаний.** Если на объекте
   архивный том иногда встаёт на минуту-другую (сетевое хранилище), поднять
   `WORKER_WATCHDOG_KILL_GRACE_SEC` — иначе сторож будет менять простой на
   рестарт там, где можно переждать.

**Остаточный риск, который песочница закрыть не может:** у бэкенда
клиентские TCP-keepalive не выставлены — asyncpg их не поддерживает
(в отличие от psycopg2 в воркере, где они заданы). Запрос, уже ушедший в
молча умерший сокет Postgres, там ничем не оборван; его ловит только
сторож, когда таких запросов накопится достаточно, чтобы встал цикл
событий. Если на объекте между бэкендом и Postgres стоит NAT или файрвол с
коротким сроком записи о соединении — задать на нём keepalive со стороны
сети либо сократить `pool_recycle` (сейчас 1800 с).

### 7.0 Резервное копирование в production (SPEC §11, §26)

До цикла 47 в production-режиме (.deb + systemd) бэкапа не существовало
вовсе: дамп снимал только cron-контейнер docker-compose, который §26
прямо называет НЕ production-режимом. Пакет заводил каталог
`/var/lib/facewatch/backups`, и никто никогда ничего туда не писал.
Теперь расписание держит `facewatch-backup.timer`, а ручной запуск живёт
в интерфейсе. В CI это проверено install-тестом на раннере с systemd
(таймер включён, дамп снялся, в дампе есть схема, бэкенд его видит);
на объекте остаётся проверить то, чего в CI нет, — время и объём.

- [ ] `systemctl status facewatch-backup.timer` — включён, показывает дату
      следующего запуска. **Дождаться срабатывания по расписанию**, а не
      только запустить руками: `Persistent=true` и `RandomizedDelaySec`
      проверяются только временем.
- [ ] **Сколько занимает дамп базы объекта и сколько он идёт.** В
      песочнице база пустая; на объекте после недели работы это сотни
      тысяч строк `face_events`. Если дамп идёт дольше получаса или
      съедает диск, поднимайте `BACKUP_RETENTION_DAYS` вниз, а каталог
      выносите на отдельный том.
- [ ] **`BACKUP_PATH` указывает на диск, отличный от диска СУБД.** Копия
      рядом с оригиналом умирает вместе с ним; по умолчанию пакет кладёт
      её в `/var/lib/facewatch/backups` на системном диске.
- [ ] «Настройки» → «Резервное копирование»: возраст последней копии
      обновился после ночного запуска; кнопка «Создать копию сейчас»
      работает; скачивание отдаёт файл целиком (проверьте размер).
- [ ] **Восстановление на запасной машине из скачанного файла**, а не
      только чтение дампа глазами. Процедура — `docs/BACKUP.md`.
- [ ] Ротация: после `BACKUP_RETENTION_DAYS` старые копии исчезают, а
      диск не растёт бесконечно (посмотреть через две-три недели).
- [ ] `graceful shutdown`: `docker compose stop` не оставляет осиротевших
      процессов ffmpeg и не рвёт запись на середине файла.

### 7.1 Оповещения (SPEC §6, §9, §11)

- [ ] **Кнопка «Отправить тестовое письмо» доходит до почты объекта.**
      В песочнице проверен весь путь до SMTP-сервера, но на настоящем
      релее добавляются вещи, которых там нет: сертификат
      (`SSLCertVerificationError` при самоподписанном на релее), политика
      SPF/DKIM и фильтр, который может положить письмо в спам вместо
      отказа. Проверять именно доставку в ящик, а не код ответа 200.
- [ ] Порт и режим шифрования соответствуют релею: 587+STARTTLS,
      465+SSL, 25 без шифрования. Несовпадение даёт таймаут, а не
      внятную ошибку, — это самая частая причина «письма не ходят».
- [ ] **Реальный watchlist-алерт** доходит по обоим каналам сразу
      (Telegram и почта) на одном событии — кулдаун общий, и регрессия
      «первый канал забрал ключ» видна только при обоих включённых.
- [ ] Алерт по заполнению диска приходит письмом (проверяется временным
      снижением `disk_warn_pct` до текущего заполнения).
- [ ] **Звук на Стене** в браузере оператора: сигнал слышен на живом
      watchlist-событии. Автовоспроизведение блокируется до первого клика
      по странице — проверить, что после клика сигнал есть, и что на
      видеостене (окно свёрнуто/вкладка неактивна) поведение устраивает
      заказчика.
- [ ] Пароль SMTP в `pg_dump` — только шифротекстом (`enc:v1:`), в
      journald при отказе отправки его нет.
- [ ] **Отчёт по расписанию (§8) реально приходит в срок.** Слот считается
      по времени СЕРВЕРА: проверить, что часовой пояс сервера тот, в
      котором думает заказчик, иначе «отчёт в 8 утра» придёт со сдвигом.
      Быстрая проверка без ожидания суток — поставить слот на ближайшие
      2–3 минуты и дождаться письма.
- [ ] Вложение открывается в Excel на машине заказчика (кириллица в
      заголовках, даты не превратились в числа).
- [ ] **Три алерта §9 доходят до дежурного, а не только до страницы
      «Мониторинг».** До цикла 50 оповещение уходило только по диску;
      потеря потока и пропуск записи писались в лог. Проверять настоящим
      обрывом **одной** камеры (выдернуть патч-корд или закрыть порт):
      письмо и сообщение в Telegram приходят, в теле — её номер, а после
      восстановления повторов нет.
- [ ] **Кулдаун подобран под объект** (`alert_cooldown_sec`, «Настройки»).
      Он покамерный, и обе крайности плохи по-своему: слишком короткий на
      парке с сезонными помехами превращает алерты в фон, который перестают
      читать; слишком длинный скрывает развитие аварии — вторая и третья
      камера, отвалившиеся следом, промолчат. Ориентир — время, за которое
      дежурный успевает дойти до камеры.
- [ ] **Массовый обрыв даёт ОДНО сообщение, а не сто двадцать.** Проверить
      на выключении коммутатора: в письме число камер и список номеров с
      усечением. Если пришла пачка писем — смотреть, не разошлась ли
      группировка (`send_record_layer_alert`), потому что именно так
      администратор объекта и отключает уведомления навсегда.

### 7.2 ONVIF Profile G — интеграция с внешним VMS (SPEC §12)

Сервер Profile G (поиск и воспроизведение записей для сторонних VMS)
**выключен по умолчанию** (`ONVIF_G_ENABLED=false`). Его контракт SOAP
покрыт тестами (`test_onvif_profile_g.py`: GetServices, GetRecordings,
GetRecordingSummary, Find/Results/EndSearch, GetReplayUri, WS-Security), но
взаимодействие с **конкретным** VMS в песочнице не воспроизвести — только
на объекте.

- [ ] Включать только при необходимости: `ONVIF_G_ENABLED=true`,
      `ONVIF_G_USERNAME`/`ONVIF_G_PASSWORD` заданы. **Без пароля сервер
      отказывает всем** (fail-closed), не пускает анонимно.
- [ ] Точка SOAP закрыта сетью/nginx так же, как Control API MediaMTX:
      она раздаёт метаданные архива (когда и что писалось). WS-Security
      UsernameToken проверяется, повтор перехваченного токена отбраковывается
      кэшем nonce (цикл 39). Проверить на сервере два следствия этого кэша:
      он живёт в **Redis**, поэтому при недоступном Redis Profile G
      отказывает целиком (fail-closed, осознанно — поиск на нём и так
      стоит); и он отбраковывает повтор пары (nonce, Created), поэтому VMS,
      который шлёт один и тот же заголовок дважды, получит отказ на втором
      запросе — это его ошибка, но выглядит как отказ сервера.
- [ ] Реальный VMS (Milestone/Genetec/NX Witness и т. п.) добавляет
      устройство по адресу `/onvif/device_service`, видит записи в списке
      recordings и их границы во времени. Если VMS строгий к форме ответа —
      расхождение искать здесь, сверяя с ONVIF Recording/Search WSDL.
- [ ] **Воспроизведение (Replay) — с цикла 44 работает своим сервером.**
      MediaMTX ONVIF-replay по времени не отдаёт и отдавать не будет,
      поэтому воспроизведение обслуживает отдельный RTSP-слушатель в
      процессе бэкенда (`backend/app/services/rtsp_replay.py`, порт
      `ONVIF_G_REPLAY_PORT`, по умолчанию **8555**). `GetReplayUri` теперь
      отдаёт его адрес, а `ter:NotSupported` остался только для случая, когда
      воспроизведение выключено явно (`ONVIF_G_REPLAY_BUILTIN=false`).
      На объекте проверить глазами:
      - [ ] порт 8555 открыт для VMS и **закрыт для всех остальных** — по
            нему отдаётся архив; авторизация Digest той же учёткой
            `ONVIF_G_USERNAME`/`ONVIF_G_PASSWORD`, без пароля сервер не
            поднимается вовсе (строка журнала «ONVIF replay не поднят»);
      - [ ] адрес из `GetReplayUri` разрешается **со стороны VMS**: хост в
            нём берётся из `Host` SOAP-запроса, и если VMS ходит через
            прокси с другим именем — задать `ONVIF_G_REPLAY_URI_BASE` явно;
      - [ ] VMS играет **запрошенный интервал**, а не живой поток, и время
            на его шкале совпадает с настенным. Время едет к VMS в
            RTP-расширении ONVIF (`0xABAC`); если шкала «поехала» — смотреть
            сюда, а не в архив;
      - [ ] воспроизведение **через дыру в записи** (реконнект, перезапуск
            слоя записи): после дыры время обязано остаться настенным.
            В песочнице это покрыто тестом, на боевом H.265 — глазами;
      - [ ] H.265. Стенд песочницы — H.264: `sprop-vps/sps/pps` для HEVC
            берутся из файла тем же путём, но на боевом кодеке не проверялись;
      - [ ] после закрытия окна VMS на сервере **не остаётся процессов
            ffmpeg** (`pgrep -af 'rtp://127.0.0.1'` пуст). Сессия без
            команд бросается через `SessionTimeout` (60 с).

### 7.3 Удаление биометрии по требованию (SPEC §24, 152-ФЗ)

Появилось в цикле 50: до него в системе не было пути, который убирал бы
биометрию человека. Проверять на объекте обязательно и на живых данных —
в песочнице и в CI кадры синтетические, а здесь важна именно связка
«файл на диске ↔ строка в базе ↔ выдача поиска» на боевом архиве.

Сценарий целиком, на **тестовой** персоне (не на настоящем человеке из
архива объекта — действие необратимо):

- [ ] в разделе «Персоны» открыть карточку, запомнить `avatar_path` и
      несколько кадров галереи, найти их файлы на диске:
      `ls -l /var/lib/facewatch/media/snapshots/` (в docker-режиме —
      `/media/snapshots/`);
- [ ] **до удаления** загрузить фотографию этого человека в «Поиск по
      фото» и убедиться, что кадры находятся. Без этого шага проверка
      бессмысленна: «не нашёл после» и «не находил никогда» выглядят
      одинаково;
- [ ] нажать **«Удалить с биометрией»**. Тост обязан назвать числа:
      сколько событий снято и сколько файлов удалено. Ноль файлов при
      непустой галерее — признак того, что `MEDIA_PATH` сервиса бэкенда
      и каталог, куда пишет воркер, разошлись (тот же класс, что
      расхождение каталога записи в разделе 1);
- [ ] тот же поиск по фото **после** удаления не находит ничего;
- [ ] файлы с диска исчезли (`ls` по запомненным именам — «No such
      file»);
- [ ] в журнале аудита появилась строка **«Удалена биометрия персоны по
      требованию»** с именем администратора — именно ей подтверждают
      исполнение требования гражданина;
- [ ] соседняя кнопка **«Удалить карточку»** ведёт себя иначе и это
      нормально: кадры остаются в архиве без владельца. Проверить на
      второй тестовой персоне, что после неё поиск по фото кадры
      по-прежнему находит, — оператор объекта должен понимать разницу
      между двумя кнопками до того, как понадобится первая.
