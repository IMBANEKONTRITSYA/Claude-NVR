# Нагрузочное тестирование

Реализует SPEC.md §14 ("CI/CD и DevOps"): *"Нагрузочное тестирование:
сценарий на 16 камер, проверка стабильности FPS и задержек"*.

## Что тестируется, а что нет

`locustfile.py` нагружает **HTTP/WS API-слой backend'а** запросами,
которые реально шлёт браузер при работе с мозаичной сеткой на 16
камерах: опрос снепшотов, дашборд KPI, просмотр архива, экспорт
отчётов, журнал аудита. Сценарий сам досеивает БД тестовыми камерами до
`LOCUST_FW_CAMERAS` (по умолчанию 16), если их там ещё нет — не
полагается на то, что в целевой БД уже настроен парк камер.

**Не покрывается** этим тестом (нужны реальные IP-камеры и/или GPU,
которых нет в CI/песочнице — тот же физический ограничитель, что у
carryover-пункта "аппаратное декодирование/инференс на реальном GPU" в
`docs/reviews/REVIEW_LOG.md`):
- реальная RTSP-декодировка 16 потоков воркером;
- инференс детекции лиц и его фактический FPS;
- HLS-видеопоток через nginx/MediaMTX.

Для полной проверки "стабильности FPS и задержек" живого видео нужен
отдельный цикл на реальном железе с реальными или эмулированными RTSP-
источниками (например, `ffmpeg -re -stream_loop -1 -i sample.mp4 -f rtsp
rtsp://...` на 16 портов).

## Запуск

```bash
pip install locust

# headless, 16 виртуальных клиентов (по числу камер сценария), 5 минут
locust -f loadtest/locustfile.py --headless \
    -u 16 -r 4 -t 5m \
    --host http://localhost:8000 \
    --csv loadtest/results/run1

# интерактивно, с графиками в браузере
locust -f loadtest/locustfile.py --host http://localhost:8000
# -> http://localhost:8089
```

Переменные окружения:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LOCUST_FW_USERNAME` / `LOCUST_FW_PASSWORD` | `admin` / `admin` | Учётка для входа — сид-админ dev/CI-окружения. **Не использовать реальный пароль прод-администратора** в этом файле/логах теста. |
| `LOCUST_FW_CAMERAS` | `16` | Сколько тестовых камер держать в БД (см. SPEC.md §14). |

Результаты (`--csv`) не коммитятся в репозиторий — `loadtest/results/`
в `.gitignore`.

## Как читать результаты

Основные ориентиры из SPEC.md:

- **Задержка трансляции ≤3 сек** — прямо этим тестом не измеряется (см.
  границы теста выше), но `snapshot_poll` — тот же путь, которым живая
  сетка обновляет превью; устойчиво растущая p95/p99 задержка этого
  запроса под нагрузкой — красный флаг ещё до реальных камер.
- **Поиск по архиву ≤5 сек** — `archive_segments`, прямое соответствие.
- **24/7 без деградации** — главная цель прогона: ни один эндпоинт не
  должен деградировать по мере роста числа одновременных клиентов, и ни
  один запрос **не должен решать латентность за счёт блокировки
  остальных** (см. пример находки ниже).

### Пример находки этого сценария (2026-08-04, цикл 13)

Первый же прогон на 16 клиентах вскрыл реальную деградацию: `POST
/api/auth/login` вызывал `verify_password()` — синхронный CPU-bound
bcrypt — напрямую в async-обработчике, блокируя единственный event loop
uvicorn на время подсчёта хэша (сотни мс). Под нагрузкой это било не
только по самому login, но и по вообще всем остальным конкурентным
запросам — p99 `/api/stats/kpi` подскакивал с ~10мс до ~900мс, пока
несколько логинов пересекались по времени. Реалистичный триггер —
пересменка: несколько операторов логинятся почти одновременно, пока
другие уже смотрят живую сетку. Исправлено переносом bcrypt в threadpool
(`asyncio.to_thread`, см. `backend/app/auth.py::verify_password_async` /
`hash_password_async`) — после фикса тот же сценарий: p99
`/api/stats/kpi` ~40мс, `/api/cameras` ~90мс (было ~540мс),
`/api/archive/segments` ~13мс (было ~530мс). Регрессионный тест —
`backend/tests/test_auth_async_bcrypt.py` (включая негативный контроль,
доказывающий, что тест чувствителен к самой блокировке, а не проходит
всегда).
