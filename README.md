# FaceWatch

Локальная система видеонаблюдения с распознаванием лиц для IP-камер по RTSP.
Развёртывание на Windows 10/11 Pro одной командой через Docker Desktop.

## Возможности

- Подключение до 16 IP-камер по RTSP (добавление через веб-интерфейс, проверка подключения)
- Просмотр в реальном времени (мозаика + полноэкранный режим), bounding box'ы лиц с именами
- Детекция движения и лиц (InsightFace), извлечение эмбеддингов 512D
- **Нейросетевой апскейл лиц** (GFPGAN) — асинхронная очередь, улучшает скриншоты и аватары
- **Поиск похожих лиц по фото** (reverse search через pgvector) с порогом и фильтрами
- Автоматическая кластеризация неизвестных персон в карточки (онлайн + фоновый DBSCAN)
- Видеоархив с записью только при событиях, автоудаление через N дней
- Стена распознавания (live feed через WebSocket, бесконечный скролл истории, подмена на улучшенное фото)
- Дашборд: KPI, графики по дням/часам, топ персон, тепловая карта; live-обновление через WebSocket
- Зоны детекции (ROI) — рисование полигонов поверх реального кадра
- Отчёты Excel/CSV: появления, сводка по персонам, активность по камерам, результаты поиска
- Роли: администратор, оператор, наблюдатель (bcrypt, JWT), смена пароля
- Настройки из UI: глубина хранения, FPS детекции, пороги движения и схожести
- RTSP-учётки шифруются в БД (Fernet/AES), rate-limiting логина
- pgvector HNSW-индексы для быстрого поиска по эмбеддингам
- Русский интерфейс, тёмная тема

## Стек

- **Бэкенд:** Python 3.11 + FastAPI + SQLAlchemy + WebSocket
- **Воркер:** OpenCV + InsightFace (buffalo_s, CPU) + scikit-learn + embed-API
- **Апскейл:** отдельный сервис на GFPGAN (CPU), OpenCV-fallback
- **БД:** PostgreSQL 16 + pgvector
- **Кэш/очереди/PubSub:** Redis 7
- **Медиасервер:** MediaMTX (RTSP/HLS/WebRTC)
- **Фронтенд:** React 18 + TypeScript + Vite + Recharts
- **Веб-сервер:** Nginx (alpine)
- **Оркестрация:** Docker Compose (8 сервисов)

## Запуск под Windows

### Что нужно установить

1. **Docker Desktop for Windows**
   https://www.docker.com/products/docker-desktop/
   После установки запустите Docker Desktop и дождитесь зелёного индикатора.

### Старт системы

1. Распакуйте проект в любую папку (например, `C:\FaceWatch`).
2. Дважды кликните на `start.bat`.
3. Скрипт:
   - проверит наличие Docker;
   - создаст `.env` из шаблона (если ещё нет);
   - выполнит `docker compose up -d --build` (первая сборка занимает ~10 минут — скачиваются образы и модели InsightFace);
   - откроет браузер на http://localhost:8080.
4. Логин: `admin`, пароль: значение `ADMIN_PASSWORD` из `.env` — его печатает `start.bat` при первом запуске, когда генерирует случайные секреты. Значения из `.env.example` (включая `ADMIN_PASSWORD=admin`) для запуска **не подходят**: бэкенд намеренно отказывается стартовать на публично известных секретах из репозитория, поэтому вход с ними не заработает.

### Остановка

Запустите `stop.bat` или выполните `docker compose down` в папке проекта.

### Обновление версии

```
git pull
docker compose up -d --build
```

Данные (база, архив, снимки) хранятся в docker-томах и при пересборке не теряются.

### Замечание про кодек камер

Live-просмотр в браузере (HLS) требует **H.264**. Если камера отдаёт H.265/HEVC,
плитка автоматически переключится на обновляемые снимки, а детекция и архив
продолжат работать. Рекомендуется включить H.264 на камере (обычно substream).

### Логи

```
docker compose logs -f backend
docker compose logs -f worker
docker compose logs -f frontend
```

## Добавление камеры

1. Войдите как админ.
2. **Управление камерами → Добавить камеру**.
3. Укажите название, RTSP URL вида `rtsp://user:pass@192.168.1.10:554/Streaming/Channels/101`, локацию.
4. Сохраните. Воркер в течение 10 секунд подхватит камеру и начнёт обработку.

## Архитектура

```
[ IP-камеры ] --RTSP--> [ Worker (OpenCV + InsightFace) ] --ffmpeg--> [ MediaMTX ] --HLS-->
                                  │  embed-API :9000 (поиск по фото)
                                  ├──> PostgreSQL+pgvector (персоны, события, сегменты)
                                  ├──> Redis: pub/sub (faces:new, faces:enhanced) + очередь upscale:queue
                                  └──> /media (snapshots, segments)
                                          │
[ Upscaler (GFPGAN) ] <--upscale:queue---┘  улучшает снимок → faces:enhanced

[ Браузер ] <--HTTP/WS--> [ Nginx ] --> [ FastAPI backend ] --> Postgres / Redis / Media
                                  └--/hls/--> MediaMTX        └--/embed--> Worker (поиск по фото)
```

### Поток нейросетевого апскейла
1. Воркер сохраняет исходный скриншот лица и кладёт `{event_id}` в `upscale:queue`.
2. Сервис `upscaler` берёт задачу, прогоняет через GFPGAN (или OpenCV-fallback),
   сохраняет улучшенную версию, обновляет `snapshot_path`/аватар, публикует `faces:enhanced`.
3. Бэкенд транслирует событие в WebSocket → Стена и карточки персон подменяют фото на лету.
   Оригинал сохраняется (`orig_snapshot_path`) на случай артефактов.

### Поиск похожих лиц
Бэкенд принимает фото → отправляет в embed-API воркера (InsightFace) → получает эмбеддинг →
pgvector-поиск по `face_events` с сортировкой по косинусной схожести и фильтрами (порог, дата, статус).

## Поток в реальном времени

MediaMTX сам тянет основной поток каждой включённой камеры (один pull на камеру,
SPEC §2) — воркер только заводит пути через его Control API:
- внутренний адрес: `rtsp://mediamtx:8554/cam{id}`
- HLS-плейлист: `http://localhost:8080/hls/cam{id}/index.m3u8` (проксируется nginx-ом)

Тот же поток MediaMTX пишет в архив remux'ом, без декодирования (SPEC §20):
`/media/segments/cam{id}_{unix_ts}.mp4`, сегменты по 5–10 минут (настраивается).

Браузер играет поток через `hls.js`; задержка обычно 2–4 секунды. Если HLS не доступен, плитка
автоматически переключается на последний снимок камеры (обновляется воркером каждые 2 сек).

## Ограничения текущей сборки

- ROI-редактор использует последний снимок камеры; при сильном изменении сцены имеет смысл нажать
  «Сбросить текущий» и перерисовать полигон.
- Кластеризация работает в двух режимах одновременно: онлайн (ближайший центроид) + фоновый DBSCAN
  раз в час (объединяет дубликаты неизвестных за последние 7 дней).

## Профили производительности (SPEC §19)

Профиль задаёт связный набор параметров обработки; любой из них можно
доопределить вручную в «Настройках».

**Профиль применяется только к слою аналитики.** Запись всех камер идёт через
MediaMTX без декодирования (remux) и от профиля не зависит — это требование
§19 и §2 о независимости слоёв. «Камер» в таблице ниже — это камеры в режиме
`Аналитика` (по умолчанию 2), а не 120 камер записи.

| Профиль | FPS детекции | Пропуск кадров | Префильтр движения | Модель | Кадр | Апскейл | Кластеризация |
|---|---|---|---|---|---|---|---|
| Экономный | 5 | каждый 4-й кадр | включён | buffalo_s | 640 px | только вручную | раз в 60 мин |
| Стандартный | 10 | каждый кадр из отобранных | включён | buffalo_s | 640 px | аватары в фоне | раз в 15 мин |
| Максимальный | 15 | без пропуска | **выключен** | buffalo_l | 960 px | вся галерея | раз в 5 мин |

Марки процессоров в таблице намеренно не указаны. Целевой сервер задан в
§23 — 2× Xeon E5-2670 (64 потока, без GPU, без AVX2), — и профиль выбирается
по тому, сколько ядер отдано аналитике (§23 отводит ей 2–3 из 64 при общем
потолке 20% CPU), а не по названию чипа. «Максимальный» дороже прочих:
детектор идёт по каждому кадру без префильтра, на тяжёлой модели и большем
кадре. Фактические ms/лицо на целевом железе снимаются при первом
развёртывании — см. `docs/DEPLOY_CHECKLIST.md`, раздел 3.

Дополнительные механизмы экономии ресурсов:

- **Режим камеры.** `Только запись` (по умолчанию) или `Аналитика`. Запись ведётся
  в обоих режимах, распознавание лиц — только во втором; число таких камер
  ограничено настройкой (по умолчанию 2). Переключение применяется на лету,
  без перезапуска сервисов.
- **Двухпоточность.** У камеры можно указать RTSP субпотока — детекция идёт по нему
  (640×360), основной поток используется только для записи и просмотра. Слой
  аналитики к записи не прикасается вовсе: она идёт в MediaMTX независимо.
- **Префильтр движения.** Детектор лиц запускается только на кадрах с движением
  (отключается в «Максимальном» профиле).
- **Адаптивная частота.** После 20 секунд без движения частота падает до `idle_fps`,
  при первом же движении мгновенно возвращается к полной.
- **Аппаратное ускорение.** При старте воркер выбирает лучший доступный провайдер
  ONNX Runtime: CUDA → DirectML → OpenVINO → CPU (виден в логах воркера).
- **Запись без декодирования.** Архив пишется remux'ом как есть — ни один кадр
  записи не декодируется и не перекодируется (SPEC §19, §24), поэтому слой записи
  почти не расходует CPU независимо от числа камер.
- **Фоновые задачи** (апскейл, кластеризация) выполняются с пониженным
  приоритетом процесса, чтобы не конкурировать с детекцией.

## Мониторинг

Раздел «Мониторинг» (админ и оператор): загрузка CPU и RAM, заполнение диска архива,
температура, число камер в сети, фактический FPS детекции по каждой камере, длина
очереди апскейла. Метрики для Grafana — `GET /api/system/prometheus` (только админ).

## Резервное копирование

Сервис `backup` (образ `postgres:16-alpine` + cron) снимает дамп PostgreSQL
раз в сутки (по умолчанию 03:00, `BACKUP_SCHEDULE` в `.env`) в том `backups`,
хранит `BACKUP_RETENTION_DAYS` (по умолчанию 14) дней и удаляет более старые
дампы автоматически. Ручной запуск: `scripts\backup_now.bat` (Windows) или
`docker compose exec backup /backup/run.sh`. Подробности и процедура
восстановления — [docs/BACKUP.md](docs/BACKUP.md).

## Разработка

```bash
# Бэкенд: тесты безопасности (шифрование RTSP, JWT, пароли)
cd backend
python -m venv .venv && .venv/bin/pip install -r requirements.txt pytest aiosqlite
.venv/bin/pytest -q

# Фронтенд: сборка и проверка типов
cd frontend
npm ci --legacy-peer-deps
npm run build
```

CI (GitHub Actions, `.github/workflows/ci.yml`) на каждый push прогоняет тесты бэкенда
и сборку фронтенда.

## Безопасность

- Пароли пользователей: bcrypt (passlib).
- JWT с истечением через 12 часов.
- RTSP-строки шифруются Fernet перед записью в БД.
- Доступ к медиа и архивам — только по валидному токену.
- В production: смените `SECRET_KEY`, `RTSP_ENCRYPTION_KEY`, `ADMIN_PASSWORD`, поставьте Nginx за HTTPS.
